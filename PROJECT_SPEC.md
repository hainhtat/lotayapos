# SME Delivery ERP System & Rider Mobile App

**Status:** Proposed implementation specification  
**Date:** 2026-08-10  
**Primary languages:** English and Myanmar (`en`, `my`)  
**Platforms:** Web Admin/ERP, Rider Mobile App, Backend API

## 1. Project Overview

This system manages a high-trust cash-on-delivery delivery operation. The company advances COD value to Online Shops (OS) when parcels are picked up. A normal delivered parcel is a rider/cash collection; the explicit paid-to-OS workflow records OS credit when the OS receives the delivered parcel money. The system compensates riders according to each rider’s configured pay model (percentage commission, fixed salary, or salary plus percentage), and settles every monetary movement through a strict double-entry ledger.

The ERP is the operational and financial source of truth. Superadmin, Operations Manager, and Dispatcher may set all parcel statuses from the ERP Dispatch Queue to correct rider errors; the rider app still exposes only the rider's assigned work and permitted delivery-outcome actions. All money, status changes, settlements, adjustments, and overrides must be attributable to a user, timestamped, auditable, and reversible through compensating entries or append-only audit rather than destructive edits.

## 2. Goals

- Maintain an accurate parcel lifecycle from pickup through delivery, rejection, pending return, and return to OS.
- Track OS advances, OS credits, rider cash collections, delivery fees, deductions, and OS settlements without relying on spreadsheet arithmetic.
- Treat explicitly paid-to-OS `DELIVERED` as an OS-credit event for COD (and for the delivery fee only when that fee is included in OS credit)—never as rider COD debt. When the fee is not included, the rider still owes a fee-only receivable for the fee collected from the customer. Standard rider cash collections create rider receivable/outstanding (COD and fee) and require a separate evening rider settlement.
- Reconcile rider collections across Cash, KBZ Pay, and Wave Pay at daily close.
- Calculate rider compensation under the rider’s pay model, with percentage commission only for successful deliveries when commission applies, and make the calculation explainable per parcel, per way, and per settlement period.
- Give operations real-time visibility into failed/partial deliveries and overdue return queues, including ERP status actions for the dispatch/ops and return queues.
- Provide daily/monthly operational, cashbook, profitability, OS, batch, and rider reports, and surface gross profit with visible components on Finance/Reports and/or Dashboard.
- Support English/Myanmar UI and API messages without duplicating business logic.

## 3. Scope

### In scope (Phase 1)

- Organization, hub, users, roles, OS accounts, rider profiles, zones, batches, parcels, package assignment, status history, and reason codes.
- COD/advance/fee/rider-compensation/settlement accounting with Cash, KBZ Pay, and Wave Pay wallets.
- OS pickup advances, paid-to-OS credits, and physical-return credits that reduce the next batch's advance requirement and carry any surplus forward.
- Rider assignment manifests, mobile delivery updates, daily rider settlement, and cashbook day-close.
- Alerts for Partial and Failed statuses, return queue timers, manual extensions, audit trail, localization, JWT authentication, PDF assignment manifests, a combined OS handover PDF from the dedicated Return to OS workspace, and reports.

### Out of scope (Phase 1)

- Customer-facing tracking, online payment gateway, route optimization, live GPS tracking, payroll, tax filing, procurement, warehouse barcode hardware integration, and automated bank reconciliation.
- Custom parcel sticker printing and barcode/QR generation. Phase 2 instead adds an authenticated OS parcel-tracking portal that continues to use the existing tracking-number identity.

## 4. Assumptions and Decisions

- A **parcel** is one delivery obligation and has one COD amount, one delivery fee due/collected amount, and one assigned rider at a time.
- A **way** is one rider delivery attempt. When the rider’s pay model includes percentage commission, daily commission is the configured % of delivery fees for that day’s successful (`DELIVERED`) ways, using the rider's commission percentage effective on the way/settlement date.
- “Partial” means the delivery was not fully completed and requires an operations decision; it does not automatically count as successful or commissionable. A `FAILED` outcome records its configured reason and any required rider/operations note first, then requires an explicit operational decision: retry tomorrow, reschedule for a specified date, or send it to OS. The failed outcome and the later decision are separate attributable status-history events; a parcel may remain `FAILED` while a decision is pending. Cancellation maps to `REJECTED` and enters the Return to OS workflow.
- Only `DELIVERED` parcels create rider commission (when the pay model includes percentage commission). The explicit paid-to-OS action creates OS credit for COD (plus the delivery fee only when included) and never creates rider COD debt; when the fee is not included in OS credit, create a rider receivable for the delivery fee only, with commission recognized as for other `DELIVERED` parcels. Standard rider cash collection creates the corresponding rider receivable/outstanding for COD and fee. `REJECTED`, `FAILED`, and `RETURNED` earn zero commission unless a future policy explicitly creates another payable status. Fixed salary components are independent of individual way outcomes.
- Rider pay models: `PERCENTAGE` earns daily commission as a configured % of delivery fees for that day’s successful (`DELIVERED`) deliveries; `SALARY` is a monthly fixed salary in integer MMK minor units; `SALARY_PLUS_PERCENTAGE` is monthly fixed salary plus the same daily percentage commission. At daily rider settlement, salary-bearing models deduct a pro-rata daily share `floor(monthlySalary / daysInMonth)` for the settlement business date’s calendar month from the amount collected from the rider; that deduction must appear as auditable settlement/cashbook day movement with the day’s cash inflows/outflows (not a silent net). Percentage commission continues to use existing Rider Commission Expense/Payable vocabulary; fixed salary is posted through rider settlement / cashbook day movement with auditable `RIDER_RECEIVABLE` lines without inventing a new account code unless a later finance policy requires one.
- Legacy parcel records retain their per-parcel advance values. For a newly created automatic-accounting batch, the pickup advance is entered once at batch creation as an optional Cash/KBZ Pay/Wave Pay split, and the three wallets must equal the actual advance paid. The saved batch and its wallet movement are one atomic, idempotent action. Only the wallets with a positive selected split receive a credit entry; an insufficient selected wallet may become negative and no other wallet is used to cover it. It does not create an OS COD obligation or reserve OS credit until the batch is explicitly finalized after parcel entry. The entered advance may be less than, equal to, or greater than the finalized batch COD; any excess becomes carry-forward OS credit rather than being silently netted away.
- A Pending Return timer starts when a parcel enters `PENDING_RETURN`, defaults to four calendar days in the hub timezone, and may be extended only with a reason and audit record.
- Posted journals remain non-destructive: corrections use void/reversal or append-only audit / compensating adjustment rather than silent overwrite. Draft OS settlement lines are editable before post; posted OS settlement lines remain editable only with a full attributable audit trail (see §6.6).
- A batch is identified by exact pickup date and OS, with a human-readable label such as `snmd 15.06.2026`; the database key is not the label.
- Monetary values are stored as integer minor units (MMK kyats unless configured otherwise); percentages are stored with explicit precision. No floating-point arithmetic is used for money.

## 5. Users and Roles

| Role | Purpose | Scope |
|---|---|---|
| Superadmin | Full administration, configuration, reversals, user/role management, all reports | All hubs and organizations |
| Operations Manager | Manage OS, batches, parcels, zones, assignments, exceptions, return extensions, operational reports, and record batch-creation pickup advances | Assigned hub(s) |
| Finance/Cashier | Record pickup advances while creating batches, settle OS balances, record wallet movements, day-close, financial reports | Assigned hub(s) |
| Dispatcher | Create/import parcels, group batches, assign riders, print manifests | Assigned hub |
| Rider | View own assignments, update allowed delivery outcomes, submit collection/settlement evidence | Own rider account |

| Auditor/Read-only | View ledger, reports, status history, and audit logs | Explicitly granted scope |

Use deny-by-default authorization. Role permissions are checked server-side on every API, with hub/OS/rider ownership constraints applied after role checks.

## 6. Functional Requirements

### 6.1 Identity and access

- Register users only through authorized admin flow or invite flow; never expose open public registration in production unless explicitly enabled.
- Login with email/phone and password; return an access token and server-side session/refresh mechanism according to deployment policy.
- Verify the current token/session on app bootstrap and expose canonical user information.
- Support logout, token expiry, refresh rotation where enabled, password reset hooks, account disablement, and audit events.
- Enforce password policy, rate-limit login, avoid account enumeration, and never log credentials or tokens.
- **Phase 2 OS portal:** an authorized admin creates or invites an Online Shop User linked to exactly one `OnlineShop`. Server-side authorization must scope every portal query and parcel-detail read to that linked shop; a client-supplied shop identifier must never widen access. This operational login is distinct from the OS financial account and exposes no balance, payment, settlement, wallet, or ERP write capability.

### 6.2 OS and commercial configuration

- Create and maintain OS legal/display name, contact details, settlement terms, default advance policy, active status, and preferred language.
- Configure per-OS or global delivery fee rules, default rider commission percentage per way (overridable by rider pay model), and effective dates.
- Show OS receivable/payable balance with a transaction-level explanation.

### 6.3 Zones, riders, and assignments

- Create zones and assign riders to one or more active zones with effective dates.
- Maintain rider status, contact, payment identifiers, compensation/pay-model policy, and hub.
- Rider compensation is configurable **per rider** as one of:
  - `PERCENTAGE` — daily commission = configured % of delivery fees for successful (`DELIVERED`) deliveries that day (examples: 40%, 50%).
  - `SALARY` — monthly fixed salary amount in integer MMK minor units.
  - `SALARY_PLUS_PERCENTAGE` — monthly fixed salary plus the same daily percentage commission on delivery fees.
- Settings rider create/edit must capture pay model and the applicable commission % and/or monthly salary fields. Salary ledger treatment follows §4 / §6.7 / §7 (daily pro-rata deduction from rider remittance at settlement with visible `RIDER_RECEIVABLE` lines; percentage commission uses Rider Commission Expense/Payable vocabulary).
- **Implementation note:** Rider `payModel`, `commissionRateBps`, and `monthlySalary` are persisted on `Rider`; Settings create/edit captures them. Delivery and settlement commission use `resolveCommissionRateBps`: `SALARY` → 0 bps (no percentage commission); percentage-bearing models use the rider’s stored rate when positive, otherwise the env default. Rider settlement applies `calculateDailySalaryDeduction` (`floor(monthlySalary / daysInMonth)` for `SALARY` / `SALARY_PLUS_PERCENTAGE` on the settlement business date), expected remittance `cod + fees - commission - salaryDeduction`, preview field `salaryDeduction`, and visible `RIDER_RECEIVABLE` settlement journal lines when `salaryDeduction > 0` (no new account codes)—see §6.7 / §7.
- Dispatch Queue provides an explicit **Delivered — paid to OS** action in addition to the standard rider/cash delivered workflow. It displays the resulting OS credit before confirmation: parcel COD plus the full configured delivery fee when the OS agreement includes it. This creates no rider COD debt and no wallet receipt. When the delivery fee is not included in OS credit, the rider collected that fee from the customer—create a rider receivable for the delivery fee only (not COD) and recognize commission as for other `DELIVERED` parcels; at settlement the rider remits fee − commission (for example, a 4,000 fee at 50% remits 2,000). When the fee is included in OS credit, create no rider fee receivable. A member of a linked group may be paid to OS individually for its COD, but cannot include the delivery fee in that OS credit: the adjusted shared linked-group fee remains rider-collected and is posted only once when every group member is delivered. Paid-to-OS parcels remain `DELIVERED` and must not enter Return to OS / `PENDING_RETURN` queues. The dedicated **Return to OS** workspace (`/operations/returns`) presents physical-return candidates and date/shop/rider-filtered Paid-to-OS deliveries in separate focused sections, then downloads one combined **OS Handover Report** PDF through `POST /operations/parcels/os-handover/pdf`. The report visibly separates physical returns from Paid to OS rows; it may include either or both, has a 500 selected-physical-return cap, and is role-readable by SUPERADMIN, OPERATIONS_MANAGER, DISPATCHER, FINANCE, and AUDITOR. Downloading is non-mutating; only the separate physical-return Received confirmation changes parcel status or finance state. Dispatch Queue remains the place for dispatch and status actions and no longer renders this return-document workflow. Available OS credit automatically reduces a finalized batch's outstanding position in the same OS/hub and carries any unused amount forward. Standard rider cash collection creates the rider-side collection obligation; actual remittance is recorded later through a manual rider settlement that may split the declared amount across Cash, KBZ Pay, and Wave Pay, and the remaining cash-collection outstanding balance stays visible until that settlement is posted. Unfulfilled parcel outcomes such as `FAILED`, `RETURNED`, `REJECTED`, `PARTIAL`, and `PENDING_RETURN` remain separate operational statuses and do not by themselves imply payment receipt or payment settlement.
- Generate a daily assignment manifest by batch, zone, rider, and date; view on-screen or export/print as PDF. `POST /operations/parcels/manifest/preview` returns JSON sections + status/COD totals and each preview row's parcel id; `POST /operations/parcels/manifest` returns the same selection as PDF. Both accept optional `riderIds` (empty = all riders in hub scope; Superadmin without `hubId` is organization-wide, max 50), `statuses`, `dateFrom`/`dateTo` (status **activity** date: parcels that have a `statusHistory` row with `toStatus` in the selected statuses and `createdAt` in the inclusive range—not batch `pickupDate`), and optional Superadmin `hubId`. Default statuses when omitted remain dispatch-ready `ASSIGNED` / `OUT_FOR_DELIVERY` / `PICKED_UP`. Caps: 500 parcels / 50 riders → `400 BATCH_TOO_LARGE`. Bulk assign shares the 500-parcel cap. Finance and Auditor may preview/download for settlement review. Dispatch manifest PDF embeds `NotoSansMyanmar-Regular` from `backend/assets/fonts/` so Myanmar customer/township text renders; production deploy must rsync `assets/` with the backend package. Return-to-OS handover PDFs use a landscape table with wrapped customer, address, and reason/note text; their fee and total columns include a delivery fee only when that parcel has the persisted paid-to-OS fee-included decision.
- Provide a dispatcher bulk-dispatch workspace (ERP **Dispatch Queue**, `/operations/dispatch`) with a multi-select parcel table and filters for batch (dropdown of batches, not free-text batch id), rider, assignment status, zone/township, customer name, order ID, tracking number, and inclusive date range. Parcel-list text filters for township, customer name, order ID, and tracking number are case-insensitive (PostgreSQL `mode: insensitive`; SQLite uses case variants). The primary Dispatch Queue parcel label (OS Order ID when present, otherwise tracking number), Return to OS tracking rows, and Reports daily-delivery preview tracking rows open one reusable, read-only parcel-details modal. It calls scoped `GET /parcels/:id` and presents parcel, customer/contact, batch/shop, rider, collection/COD/fee, status, and status-history data without allowing an edit. **Dispatch Queue / `GET /parcels` `dateFrom`/`dateTo` still filter by batch `pickupDate`**—distinct from manifest/Reports daily delivery status, which use status activity date. The Dispatch Queue always requests `GET /parcels?excludeVoided=true`; the server excludes `VOIDED` parcels before applying pagination, sorting, and every focused-queue condition. By default it also excludes `DELIVERED` and `RETURNED` before pagination through its completed-parcels filter. A **Show delivered and returned** checkbox includes those statuses and composes with every other Dispatch Queue filter; it does not change generic parcel-list semantics. The generic parcel list can omit `excludeVoided` and explicitly request `status=VOIDED` for audit, while Batch Detail retains voided entries. The parcel list is paginated (`pageSize` 100 in the Dispatch Queue UI; API max 100) with previous/next controls. Its focused queues are **To assign** (`CREATED`/`PICKED_UP`), **With riders** (`OUT_FOR_DELIVERY` only), **Rescheduled** (date-change reason, excluding delivered, returned, and pending-return parcels), **Return to OS** (`PENDING_RETURN`/`REJECTED`), and **3+ days in hand** (any unresolved parcel based on its first recorded timestamp). `ASSIGNED` is planning/overnight assignment, not proof of physical rider handover; it enters With riders only after the handover/status update changes it to `OUT_FOR_DELIVERY`. Bulk assignment accepts eligible parcel IDs and a target rider, validates the complete selection atomically, preserves assignment history, and generates a PDF manifest for the action (including multi-rider manifest download). A bulk reschedule records the planned delivery date and reason without moving the parcel from its original batch or resetting its age. Return-document preparation has moved out of Dispatch Queue into the dedicated Return to OS workspace. A distinct physical-handoff confirmation, with business date and idempotency key, transitions eligible parcels to `RETURNED` and creates the applicable OS credit. Paid-to-OS `DELIVERED` parcels are not on the physical-return queue, but appear in the focused Return to OS reporting section for the combined OS Handover Report. Edit actions (inline rider/status, multi-edit, assign, reschedule, and physical-return confirmation) are role-gated to Superadmin, Operations Manager, and Dispatcher, except Finance may participate in physical-return confirmation as specified in §6.6.
- **Implementation detail:** the staff parcel-details modal renders status history as a human-readable journey timeline for both ordinary and exceptional paths, including delivery attempts, failed reasons/notes, retry/reschedule/return decisions, and final delivery. A failed-decision reschedule history note begins with the selected `YYYY-MM-DD` date so the intended delivery date can be rendered unambiguously; legacy notes remain readable.
- Prevent assignment of inactive riders, duplicate active assignment, cross-hub mismatch, or parcels already terminally settled without an override.
- Allow authorized dispatcher/operations users to reassign with a reason and preserved assignment history.

### 6.4 Batches and parcels

- Create/import a batch using OS and exact pickup date. The system must allow duplicate OS `Order ID` values within the same batch, including multi-day pickups and multi-box orders, and must not reject duplicate imports on that basis.
- Capture the parcel identifiers currently supported by the implementation, including `trackingNumber` as the unique parcel identifier, OS `Order ID` as a non-unique searchable reference, and optional OS order date when provided by the source system. Preserve customer name/phone/address, COD amount, delivery fee, advance amount, zone, notes, and optional external reference.
- Capture the delivery collection mode: standard **rider cash collection** or explicit **paid by OS**. The API enum retains `CASH_RECEIPT_EXCEPTION` for the former mode as a compatibility detail; it does not mean cash collection is exceptional in the business workflow. Per-OS configuration determines whether a paid-by-OS credit includes the full configured delivery fee. When the fee is not included, OS credit remains COD-only and the rider owes a fee-only receivable for the fee collected from the customer; when the fee is included, OS credit covers COD and fee and no rider fee receivable is created. The selected mode and included-fee decision must be auditable with the delivered outcome.
- `trackingNumber` remains the package identity and lookup key in the current implementation; the backend accepts it as the unique parcel identifier, while `Order ID` is preserved as the original OS reference and may repeat within the same OS, batch, or day-reset OS order stream. Parcels generated as `LTY-<number>` also retain a nullable numeric `trackingSequence` to support numeric tracking sort; legacy or non-generated identifiers remain sortable through the tracking-number fallback.
- **Entered in error correction:** A parcel that the OS never physically supplied is retained and marked `VOIDED` with reason code `ENTERED_IN_ERROR`; it is not a physical return. Only Superadmin or an Operations Manager in scope may request it, with a 3–500 character reason and UUID idempotency key. The server permits only an unassigned, unlinked `CREATED`, `PICKED_UP`, or `ASSIGNED` parcel with no package assignment, delivery way, OS-return credit, unreversed parcel money journal, or historical OS settlement. The current batch-detail UI exposes the action for eligible `CREATED` entries. The correction clears return/planned-delivery dates and appends attributable status history containing actor, reason, and request key; it does not delete the parcel.
- In a draft automatic-accounting batch, a voided entry is excluded from the COD snapshot used at finalization. Any actual pickup advance remains posted; if it exceeds the finalized COD, the excess becomes same-OS/hub carry-forward OS credit. In a finalized batch, the server reduces the batch OS obligation by the parcel's **current** COD only when the batch obligation exists and its outstanding balance and original COD are each at least that amount; it posts one balanced `PARCEL_ENTERED_IN_ERROR` journal on the current hub business date and requires the cashbook to be open. Existing advance, applied-credit, or payment allocations make the automated correction unavailable until reconciled. A prior zeroing on a finalized record therefore produces a zero-value void correction; it does not recover an earlier value through the void flow. The finalized-void dialog displays the previewed outstanding balance before and after the proposed reduction, plus posted advance and available OS credit. When field audit shows the latest edit that set COD or delivery fee to zero, the preview also displays the affected field's audited prior value; that edit history is not proof that the value was posted to the OS balance.
- Provide batch totals: parcel counts by status, COD, advances, delivery fees, paid-by-OS credit, physical-return credit, rider cash collections, commissions, deductions, and outstanding balances.
- **Batch Detail 3+ days in hand:** `GET /operations/batches/:id` returns a server-authoritative `threeDaysInHand` snapshot: qualifying parcel IDs, the earliest next threshold (`nextDueAt`), and its calculation time (`calculatedAt`). It includes unresolved parcels whose `createdAt` is at least 72 hours old and excludes `DELIVERED`, `RETURNED`, and `VOIDED`, matching the Dispatch Queue rule. The batch summary shows the count. When the count is nonzero, **Show these parcels** moves to the Saved parcels table and applies its **3+ days in hand** view; the table can switch back to **All parcels**. The client schedules a batch-detail refresh at `nextDueAt`; while an older API deployment does not return the snapshot, it derives the same view from the returned parcel rows. The view does not change parcel state.
- New batches use automatic accounting: create the batch with the optional actual-advance wallet split, add/import parcels while it is a draft, then finalize it to atomically create its OS COD obligation and apply only the needed available same-OS/hub credit. Finalization freezes further parcel additions and financial parcel edits (COD, delivery fee, and township); it is idempotent and concurrency-safe. The older explicit pickup-advance endpoint remains only for non-automatic legacy batches.
- Search/filter by OS, batch, tracking number, order ID, customer name, OS order date, rider, zone, township, status, date (batch pickup date on parcel list), and exception reason. Township, customer name, order ID, and tracking number contains-filters are case-insensitive as implemented. Dispatch list sorting is server-side and applies across every page; allowed fields are order ID, tracking number, pickup date, shop name, customer name, township, delivery fee, COD amount, rider name, and status. The default list order remains most recently updated first with ID as the deterministic tie-breaker. An explicit sort uses ID as its deterministic final tie-breaker; tracking-number sorting first uses `trackingSequence` (nulls last) then the full tracking string in the requested direction.
- Import must validate rows, show an error report, and commit atomically or explicitly mark partial import; no silent row loss.
- Import validation must not treat duplicate `Order ID` values as a uniqueness violation, and no unique or composite-unique constraint may involve `Order ID`.

### 6.5 Parcel lifecycle

Statuses:

`CREATED → PICKED_UP → ASSIGNED → OUT_FOR_DELIVERY → DELIVERED`

Exception branches:

`OUT_FOR_DELIVERY → PARTIAL`, `OUT_FOR_DELIVERY → FAILED`, `OUT_FOR_DELIVERY → REJECTED`, `PARTIAL/FAILED/REJECTED → PENDING_RETURN → RETURNED`

- Status transitions are server-validated against the allowed status enum and recorded with actor, source (`admin`/`rider`), timestamp, location/device metadata when available, reason code, note/reason when required, and previous/new values. Money side-effects remain those already specified for the destination status (collections, commission eligibility, return timer, OS offsets).
- Superadmin, Operations Manager, and Dispatcher may edit/set **all** parcel statuses from the ERP **Dispatch Queue** (`/operations/dispatch`) to correct rider errors (broader than rider-allowed transitions). Server validation, status history attribution (actor, from/to, note/reason when required), and ledger side-effects still apply. Deny-by-default remains for other roles.
- Rider may update only assigned parcels and only permitted delivery-outcome transitions while the way is open.
- Status override that leaves a money-bearing status (`DELIVERED` or `PARTIAL`) while **unreversed** money journals exist is rejected with `409 MONEY_POSTED`; there is no automatic reversal—Finance must reverse posted entries before the status correction. The sole implemented collection-mode exception is an authorized ERP correction of an already `DELIVERED`, linked rider-cash parcel to COD-only `PAID_BY_OS`: it requires a correction note, reverses only that parcel's unreversed `LINKED_RIDER_RECEIVABLE_COD` journal and its rider-receivable projection, creates one COD-only OS credit, and records `PAID_TO_OS_CORRECTION` status history. It preserves the linked group's shared delivery-fee and commission records, and retrying the same corrected request is non-duplicating. Other delivered collection-mode changes are rejected with `409 DELIVERY_COLLECTION_CORRECTION_REQUIRED`. The gate considers: (1) parcel-scoped sources `RIDER_COMMISSION`, `RIDER_RECEIVABLE_RECOGNITION`, `PARTIAL_RETURN_COLLECTION`, `OS_PARTIAL_RETURN_ADJUSTMENT`, `DELIVERY_COLLECTION`, and `LINKED_RIDER_RECEIVABLE_COD`, matching `sourceId` equal to the parcel id or starting with `parcelId:`; (2) when the parcel is linked, group-scoped `LINKED_DELIVERY_COLLECTION` / `LINKED_RIDER_COMMISSION` / `LINKED_RIDER_RECEIVABLE_RECOGNITION` / `LINKED_RIDER_RECEIVABLE_FEE` / `LINKED_OS_SHORTFALL`, matching `sourceId` equal to the link group id or starting with `groupId:`. Journals that already have a matching `LEDGER_REVERSAL` (reversal `sourceId` = original entry id) do not block the override. After reversal, re-post of money events uses free versioned journal `sourceId`s via `nextVersionedJournalSourceId` (`baseId` or `baseId:uuid`) for `RIDER_COMMISSION`, `RIDER_RECEIVABLE_RECOGNITION`, `PARTIAL_RETURN_COLLECTION`, `OS_PARTIAL_RETURN_ADJUSTMENT`, `DELIVERY_COLLECTION` / `LINKED_DELIVERY_COLLECTION`, `OS_SHORTFALL` / `LINKED_OS_SHORTFALL`, `BATCH_PICKUP_ADVANCE` (batch id), and the linked receivable/commission/`LINKED_*` sources above so the unique source key can be reused.
- `VOIDED` is an entered-in-error terminal state rather than a rider or physical-return outcome. It is excluded from unresolved dispatch, reschedule, link-parcel, and overdue queue/calculation paths, cannot receive later status changes, and its status history remains readable. Retrying the same void request returns the original result without a second journal or history row; a different request is rejected.
- For automatic-accounting batches, parcel COD, delivery fee, and township remain editable while the batch is a draft even though its actual pickup advance has posted; these fields are locked with `409 BATCH_FINALIZED` after finalization. Legacy batch edits remain subject to the unreversed `BATCH_PICKUP_ADVANCE` guard (`409 ADVANCE_POSTED`); after Finance reverses that advance, `listBatches` reports `advancePosted: false` and a new advance may be posted under a versioned `sourceId`.
- On `OUT_FOR_DELIVERY` and on delivery outcomes (`DELIVERED` / `PARTIAL` / `FAILED` / `REJECTED`) for an assigned rider, the server keeps exactly one primary open (or completed) `DeliveryWay`: prefer the current rider’s open way, else the oldest open way. Any other still-open ways for that parcel are closed with outcome `SUPERSEDED`. When recording a delivery outcome, the primary way is completed with the real outcome; if none exists (legacy data, ERP override that skipped `OUT_FOR_DELIVERY`, etc.), the server creates a completed way so ERP transitions such as `OUT_FOR_DELIVERY → DELIVERED` succeed without a prior rider-started way.
- **Implementation note:** Dispatch Queue provides inline rider assign/reassign and inline/all-status editing across the status enum (with reason prompts where required), plus parcel edit modal and selected-row multi-edit, in addition to Partial Return and link-parcels. Edit affordances are role-gated to Superadmin / Operations Manager / Dispatcher. OS Order ID is the primary display identifier in the Dispatch Queue parcel table (tracking number shown as secondary mono text); this is UI prominence only—API identity remains `trackingNumber`.
- Partial and Failed require a reason code and optional/required note according to reason configuration. They immediately create ERP alerts for Superadmin and Operations Manager. The ERP failed-delivery flow is one adaptive two-step modal: it first saves `FAILED` with its reason/note, then offers retry tomorrow, reschedule to a chosen date, or Return to OS with a separate required decision explanation. Saving the failure and saving the decision remain distinct server-side status-history events. Closing after the first step leaves the parcel `FAILED` and its alert intact so operations can decide later. An unacknowledged Failed alert opens the Dispatch Queue directly at that decision step when the parcel is still `FAILED`; viewing the alert does not acknowledge it. When the reason code is a date-change/reschedule code (`DATE_CHANGE`, `DELIVERY_DATE_CHANGE`, or `RESCHEDULE`), the alert `type` is `DATE_CHANGE` (message notes the customer requested another delivery day); otherwise the alert `type` matches the destination status (`PARTIAL` / `FAILED`). Dispatch Queue also surfaces an inline date-change badge when the parcel’s current `reasonCode` matches those codes.
- A Partial Return outcome requires Actual COD Collected. The API validates that the value is non-negative and does not exceed Original COD, calculates the shortfall, and records the bounded OS settlement offset for the uncollected advanced COD in a balanced journal transaction. `PARTIAL_RETURN_COLLECTION` and `OS_PARTIAL_RETURN_ADJUSTMENT` use `nextVersionedJournalSourceId` on the parcel id so, after Finance reverses those journals, a later Partial outcome can re-post under `parcelId:uuid` without colliding with the unique source key.
- Rejected requires a reason code, earns zero commission, and represents cancellation for the Return to OS workflow.
- Selecting `PENDING_RETURN` in Dispatch Queue opens one dialog with a required free-text return reason (minimum three characters). It records `RETURN_TO_OS` with that note in status history; no reason-code picker or second dialog is used for this action. The retained reason/note is included on the Return to OS handover PDF.
- The current implementation requires a unique `trackingNumber` field for parcel identity, but the Phase 1 parcel lifecycle does not require any specific branded numbering policy, counter concurrency rule, or import-time numbering guarantee beyond uniqueness of the stored tracking number field.
- Delivery confirmation may require customer name/OTP/signature/photo in a later policy; keep the model extensible but do not require unavailable evidence in Phase 1.
- A parcel cannot be marked Delivered after Return without an authorized reopen/reversal workflow.

### 6.6 Advance and OS settlement ledger

For a new automatic-accounting batch, a Superadmin, Finance user, or Operations Manager may save the actual pickup advance as a Cash/KBZ Pay/Wave Pay split that exactly equals `advancePaid`; the balanced `BATCH_PICKUP_ADVANCE` wallet movement is posted in that same idempotent transaction. It credits only the selected nonzero wallets, so a selected wallet may go negative without drawing from the other wallets. The draft accepts parcel entry, but creates neither an OS batch COD obligation nor an OS-credit allocation. Explicit finalization acquires the same-OS/hub allocation lock, creates the batch obligation from the saved parcel COD, and applies only the existing same-OS/hub credit needed after actual advance. It then freezes parcel additions and COD, delivery-fee, and township edits. Repeated/concurrent finalization returns the single finalized result without duplicate obligation, allocation, or carry-forward-credit records. The operational OS account is a per-OS, per-hub list of these batch obligations, not a new editable settlement statement. The older explicit pickup-advance endpoint remains available for legacy non-automatic batches.

**Advance payment breakdown:** Batch Detail returns each active (unreversed) `BATCH_PICKUP_ADVANCE` journal for that batch as its Cash, KBZ Pay, and Wave Pay wallet split, together with its business date and posting timestamp. It shows the recorder when the entry can be attributed to the recorded batch creator; older legacy entries may show the recorder as unavailable. The Batch Detail view presents this breakdown so staff can audit how the displayed total advance was paid.

For each obligated batch, the displayed balance is calculated as:

`position before credit = max(0, original COD + approved opening adjustment − posted advance)`

`applied OS credit = min(position before credit, available same-OS/hub credit)`

`outstanding = position before credit − applied OS credit − posted OS-payment allocations`.

If posted advance exceeds finalized original COD, the difference is created once as carry-forward OS credit for that same OS/hub. Existing credit is not reserved at draft creation; a legacy draft that already contains a pre-allocation retains only the amount needed at finalization, releasing any excess.

An OS credit is created either by an explicit paid-to-OS delivery or by confirmed physical return to OS. A paid-to-OS delivery credits its COD and includes the full configured delivery fee only where that fee is marked as included by the OS. Linked parcels are COD-only paid-to-OS deliveries: their shared delivery fee cannot be included. When the fee is not included, OS credit is COD-only and a rider receivable is created for the delivery fee only for non-linked parcels (commission still posts on `DELIVERED` as for other successful deliveries); linked groups instead post their adjusted shared fee/commission once when all members are delivered. When the fee is included, create no rider fee receivable. Physical-return credit is COD-only; a returned parcel's delivery fee is not an OS credit or a return deduction unless its persisted paid-to-OS fee-included decision says the OS had already paid that fee. The same fee rule is used in legacy OS-settlement components and return-handover totals. Paid-to-OS `DELIVERED` parcels stay off Return to OS / `PENDING_RETURN` queues; physical Return to OS remains a separate workflow with its own handover PDF. If the expression is negative, the excess remains available OS credit rather than a negative payable. Available credit is applied oldest-first at automatic-batch finalization for the same OS and hub, with any surplus carried forward. Credit consumption and cash payments allocate oldest-first across selected outstanding batches, are hub-scoped, and are recorded atomically with idempotency protection. Payments may be split across Cash, KBZ Pay, and Wave Pay. A wallet payment cannot exceed the selected payable after available credit.

Superadmin and Finance may void a payment with a reason and idempotency key, which posts an opposite journal and marks the original payment `VOIDED`; they may correct a payment by atomically voiding it and posting a replacement. History retains payments, return credits, and legacy settlement records.

The Finance OS-account table provides a per-batch **Settle** action. Its modal starts with that batch only, shows the amount remaining after available OS credit, accepts an integer Cash/KBZ Pay/Wave Pay split, and explains each save blocker in the modal (invalid date or amount, missing/oversized note or correction reason, oversized reference, no batch, or amount above payable). A submitted payment retains its exact request and idempotency key in per-user browser session storage for retry after an uncertain transport/server result, including after refresh. While that request is unresolved, the user cannot create or edit another OS payment; a definitive client rejection clears it. Successful posts refresh OS, wallet, ledger, batch, and account-history views.

**Return to OS:** Superadmin, Finance, and Operations Manager may use `POST /finance/os-returns/receive` to confirm physical return. It accepts `FAILED`, `REJECTED`, `PENDING_RETURN`, or `PARTIAL`, atomically changes the parcel to `RETURNED`, and creates OS credit for that batch. It does not post a wallet credit. The operation is idempotent and is intentionally permitted as Finance recovery rather than a normal Ops status correction. Auditor access is read-only.

The earlier OS settlement draft/preview/post workflow remains in the data/API history for pre-cutover records only. Once a selected batch has an OS batch obligation, its legacy settlement writes are rejected with `OS_ACCOUNT_CUTOVER`; the ERP presents legacy settlement history read-only. Cutover reconciliation uses attributable legacy batch payments and permits only a Superadmin-approved, evidence-backed opening adjustment where required.

**Historical OS settlement:** a Superadmin may open the historical reconciliation review. It retains the three newest batches overall by pickup-date/order and marks every older batch as historically settled for its current OS outstanding amount. The preview is fingerprinted and blocks if a target lacks the required hub/account information; apply rechecks the complete target and retained selections inside a serializable transaction. It creates any needed migrated opening obligation and recorded return credit, then posts an `OS_HISTORICAL_SETTLEMENT` clearing entry for the outstanding amount. This records no Cash/KBZ Pay/Wave Pay movement, leaves parcel statuses and rider debts unchanged, preserves audit reason/date/actor/idempotency evidence, and locks affected batch COD/parcel additions from further changes. Existing OS credit remains available.

### 6.7 Rider compensation and daily settlement

Rider pay model is configured on the rider profile (§6.3) as `PERCENTAGE`, `SALARY`, or `SALARY_PLUS_PERCENTAGE`.

- **`PERCENTAGE`:** Daily commission = configured % of delivery fees for successful (`DELIVERED`) deliveries that day (examples: 40%, 50%). Use existing Rider Commission Expense/Payable vocabulary.
- **`SALARY`:** Monthly fixed salary in integer MMK minor units. At settlement, deduct the daily pro-rata share `floor(monthlySalary / daysInMonth)` for the settlement business date from the total amount collected from the rider; record the deduction in the settlement journal / cashbook together with daily cash inflows/outflows (not a silent net), posted through rider settlement with auditable `RIDER_RECEIVABLE` lines (no new account code).
- **`SALARY_PLUS_PERCENTAGE`:** Monthly fixed salary plus the same daily percentage-commission rules as `PERCENTAGE`; daily salary deduction uses the same pro-rata rule as `SALARY`.
- Rejected/Failed/Returned parcels produce zero rider commission. Partial is non-commissionable until an authorized final outcome is recorded. Salary (when applicable) is not earned per failed/returned way.
- At evening settlement, calculate expected remittance from **rider cash collections** minus applicable rider compensation for the rider/day/settlement scope: `Amount Owed to Hub = Cash COD Collected + Cash Delivery Fees Collected - Rider Commission - salaryDeduction` (where `salaryDeduction` is 0 for `PERCENTAGE`). Paid-to-OS deliveries contribute no rider COD debt. When the delivery fee is not included in OS credit, include that fee in Cash Delivery Fees Collected (fee-only rider receivable) so net remittance is fee − commission; when the fee is included in OS credit, contribute neither COD nor fee to rider debt. Commission on paid-to-OS `DELIVERED` follows the same rules as other successful deliveries. Surface `salaryDeduction` on settlement preview and in auditable settlement journal lines (same non-silent treatment as above).
- Linked-group settlement totals: when a delivered parcel belongs to a linked group, fees and commission are taken once from the group’s adjusted `totalDeliveryFee` only if **every** member of the group is `DELIVERED`. Incomplete linked groups do not fall through to individual member fees/commission in settlement totals (COD for delivered members still counts).
- Record actual remittance separately by wallet: Cash, KBZ Pay, and Wave Pay. Admins, Operations Managers, and Finance users record the rider’s evening settlement manually, splitting the declared amount across the supported wallets (for example Cash 100,000, KBZ Pay 100,000, Wave Pay 200,000). Permit under/over settlement only with reason, approval, and a receivable/payable balance.
- The Finance rider-outstanding view is scoped to its selected business date: its Expected and Received columns show that date’s parcel obligation and posted Cash/KBZ Pay/Wave Pay receipts (with a date total), while Outstanding balance remains explicitly cumulative through that date. It must not present a cumulative paid figure beside date-scoped receipt detail. The rider workspace derives its initial selected date with the Asia/Yangon business-date helper rather than the browser/UTC ISO date; backend hub-timezone configuration is validated through `HUB_TIMEZONE` (default `Asia/Yangon`).
- Require cashier confirmation and attach reference/note where applicable. Reconciliation compares expected, declared, verified, and variance values.
- **Implementation note:** Per-rider `payModel` / `commissionRateBps` / `monthlySalary` are persisted and editable in Settings. `resolveCommissionRateBps` forces commission to 0 for `SALARY` riders at delivery and settlement preview; percentage models use the rider rate when positive, else env default. `calculateDailySalaryDeduction` / `calculateRiderSettlementAmounts` implement the formula above; preview returns `salaryDeduction`. When `salaryDeduction > 0`, the `RIDER_SETTLEMENT` journal posts a visible `RIDER_RECEIVABLE` credit for remittance before salary (`cod + fees - commission`) and a `RIDER_RECEIVABLE` debit for the salary deduction, with the description including the salary amount; otherwise a single `RIDER_RECEIVABLE` credit for `expectedAmount` is used. No dedicated salary account code is introduced.
- The rider app should surface the rider's outstanding balance / settlement status so riders can see what remains to be remitted. The outstanding amount is reduced only when the manual settlement is posted; it is not inferred from `DELIVERED`.

### 6.8 Cashbook and day-close

- Maintain independent wallet ledgers for Cash, KBZ Pay, and Wave Pay, plus opening balance, posted movements, transfers, adjustments, and closing balance.
- A wallet adjustment records a real-world balance correction without editing prior wallet history. The current Finance overview exposes this action to Superadmins: select the wallet, hub, business date, and actual balance in hand, then provide a required reason. The ERP calculates the signed difference from the recorded wallet balance and posts one immutable, balanced `CASHBOOK_ADJUSTMENT` increase or decrease. The API also authorizes Finance for this cashbook command, subject to normal hub scope and day-close checks; the current web control is Superadmin-only.
- Finance wallet and journal balance cards use a database aggregate summary that is independent of the bounded journal-entry detail report. The detail endpoint remains capped at 500 entries and asks users to narrow its filters; the summary returns debit, credit, balance, and balanced/difference totals by account without loading every journal entry into the application.
- **Wallet transaction statement:** Finance provides a read-only, banking-style statement for Cash, KBZ Pay, and Wave Pay. It is scoped to one permitted hub and an inclusive business-date range (defaulting to the current hub business date, with Today and Yesterday shortcuts). It shows each wallet's opening balance, money in, money out, and closing balance for the whole selected period, independently of any list filter. The chronological, newest-first journal list can be filtered by wallet, supported source type, rider, or OS; a rider and OS filter are mutually exclusive, and party filtering retains corresponding reversal records. Each row shows its wallet split and, for every affected wallet, the balance immediately after the entry. That balance is calculated across all wallet movements in the selected period before applying list filters, so narrowing the displayed list does not create a false running balance. Expanded rows also show business date, recorded timestamp, description, reference, recorder where attributable, and ledger source. The list is paginated at 50 rows (API maximum 100); CSV export preserves the active filters and includes balance-after columns for Cash, KBZ Pay, and Wave Pay, limited to 10,000 rows / 366 days. CSV values are protected against spreadsheet-formula execution.
- The statement is read-only for Superadmin, Finance, Operations Manager, and Auditor, with server-enforced hub scope. Rider outstanding remains an amber, separate cumulative receivable summary through the selected end date: it is not wallet cash until a rider settlement posts. The statement also shows current available OS credit and current pending-return count as non-cash context, without presenting either as a wallet movement or a historical total for the selected dates.
- Prevent cross-wallet movement from being represented as a single-sided entry; record both sides.
- Day-close is a controlled procedure: stop or queue new postings for the business date, compute expected balances, reconcile verified settlements, require variance explanations/approval, post close record, and lock the date.
- Reopening a closed day requires Superadmin authorization and creates an audit event; subsequent corrections are reversals, not edits to historical entries.
- The ERP must **show profits**: daily (and period) gross profit as a derived report metric on Finance/Reports and/or Dashboard, with visible components including delivery fee revenue, commission/salary cost, returns, and adjustments (and other components already listed for gross profit). Do not hide the composition behind a single opaque total.

### 6.9 Alerts and reporting

- Persisted ERP alerts currently originate from Partial and Failed outcomes, including `DATE_CHANGE` when the Partial/Failed reason is a reschedule/date-change code. They are addressed to Superadmin and Operations Manager by default and retain their existing acknowledgement scope. Additional alert producers (overdue Pending Return, settlement variance, failed day-close, and suspicious duplicate actions) remain planned until implemented.
- **Operations Review** (`/operations/review`) is a role-gated workspace for Superadmin, Operations Manager, and Finance. Superadmin and Operations Manager see current unacknowledged Partial, Failed, and `DATE_CHANGE` alerts with parcel context and a link to the appropriate operational action, plus separately calculated review queues for overdue Pending Returns and unresolved parcels that have been in hand for at least three elapsed days. All three roles see a wallet-alert section listing negative Cash, KBZ Pay, or Wave Pay balances in their permitted hub scope, with the wallet's balance and shortfall. Wallet alerts are derived from journal lines, do not create persisted alert records, require no acknowledgement, and disappear automatically when that specific wallet reaches zero or above. Finance sees this wallet section only.
- The header notification bell, available to Superadmin, Operations Manager, and Finance, opens a dropdown of current negative-wallet alerts and, for Superadmin and Operations Manager, recent unacknowledged persisted parcel alerts. Opening the dropdown or viewing an alert never acknowledges it. Parcel-alert items retain their explicit **Acknowledge** action, and **View all** opens Operations Review. Acknowledgement remains an explicit persisted-alert action and does not clear a parcel from the separately calculated review queues; wallet alerts are resolved only by restoring that wallet's balance to zero or above.
- Outstanding-rider reporting must include the number of unsettled riders and each rider’s outstanding amount for **rider cash collections** (including fee-only receivables from paid-to-OS deliveries where the fee was not included in OS credit), plus the manual split-wallet payment history used to reach that balance. The selected-business-date Finance view shows only that day’s Expected/Received activity, split across Cash, KBZ Pay, and Wave Pay, while identifying Outstanding as the cumulative balance through the selected date. Dashboard/Overview should also show unsettled OS batches, the total **Outstanding to OS** in MMK, available OS credit, COD collected today, **Total delivered today**, wallet balances, returns due, overdue returns, failed/partial delivery alerts, expense total, and net profit breakdown, with each card deep-linking to the filtered operational or Finance view that explains the total. **COD collected today** is a parcel-event metric: the COD sum of unique parcels that reached `DELIVERED` during the current business day. **Total delivered today** is that COD plus those parcels’ configured delivery fees. Neither metric includes, nor is changed by, wallet adjustments, pickup advances, OS payments, or journal postings. Outstanding to OS is derived from the OS COD payable account balance and links to the OS & riders account workspace. The overview must distinguish paid-by-OS credit and physical-return credit from rider-cash receivables (including fee-only paid-to-OS fee receivables), so finance users can see the next advance reduction and the cash collection still requiring manual entry.
- The dashboard and Dispatch Queue expose a three-day-in-hand queue: every parcel other than `DELIVERED` or `RETURNED` whose original `createdAt` timestamp is at least three elapsed days old. A reschedule does not reset this age. This queue is distinct from the Pending Return timer.
- Reports: daily operations, monthly operations, OS statement, batch inventory, rider performance/commission (and salary where configured), wallet/cashbook, day-close, outstanding receivables, returns, gross profit with component breakdown, and audit activity.
- Reports support timezone-aware date ranges, hub/OS/rider/zone filters, CSV export where useful, and PDF output for manifests and settlement statements.
- **Implementation note:** Finance/Reports now surfaces gross profit with component breakdown for authorized financial roles through the detailed reports UI and report endpoint set, rather than only an opaque aggregate dashboard figure.
- Dispatchers may link two to 20 unlinked parcels in the responsible rider’s hub, including parcels from different batches and with different addresses or fees. `DELIVERED`, `RETURNED`, and `VOIDED` parcels are excluded; other statuses remain linkable. Linking assigns the responsible rider, preserves assignment history, and uses the highest member fee as the base plus 1,000 MMK for each additional parcel. The linked group is visible to riders, and commission is calculated from the group’s adjusted total delivery fees rather than separate full-fee ways. Rider settlement applies group fees/commission only when all members are `DELIVERED`; incomplete groups do not fall through to individual fees. **Dispatch Queue link suggestions:** Superadmin, Operations Manager, and Dispatcher can request a read-only, on-demand review of eligible unlinked parcels. Suggestions group normalized customer name and phone only within the same shop and hub, including matches from different batches or Dispatch Queue pages. They never link parcels automatically and do not use address equality as a matching condition. The review displays each candidate's address, township, status, rider, and configured delivery fee so the authorized user can assess address differences or typos, choose the members, confirm that the addresses were checked, choose a responsible rider, and provide a reason before submitting the existing link command. Results disclose when bounded scans or group/member limits make the review incomplete. Linked parcels that are visible together in the Dispatch Queue are kept adjacent and show a bracket-style group cue with the visible-member count and adjusted group fee; this is not an assertion that every member is visible under the current filters or page.

## 7. Double-Entry Accounting Model

Every posted monetary event creates balanced debit and credit lines in one journal entry. Journal entries include immutable ID, business date, posting date, source type/id, description, currency, actor, and reversal linkage. The ledger must reject unbalanced entries and duplicate source event keys.

Minimum account categories:

| Account | Typical meaning |
|---|---|
| Wallet: Cash | Physical cash controlled by hub |
| Wallet: KBZ Pay | Digital wallet balance |
| Wallet: Wave Pay | Digital wallet balance |
| OS COD Payable | OS batch COD obligation, reduced by posted advances, applied OS credits, and OS payments |
| OS Batch COD Clearing | Counter-account used when an OS batch obligation is created |
| OS Credit | Available against OS account payables; created by paid-to-OS delivery or physical return to OS and carried forward within the same OS/hub |
| Customer COD Receivable | COD expected from customer |
| Delivery Fee Revenue | Delivery fee earned under policy |
| Rider Commission Expense | Commission owed to rider (percentage component) |
| Rider Settlement Receivable | Amount rider owes hub after collection/commission |
| Cashbook Adjustment | Auditable counter-account for a verified wallet increase or decrease |
| Variance/Adjustment | Authorized operational or financial variance |

Percentage commission continues to use `Rider Commission Expense` (and related Rider Commission Payable vocabulary where applicable). Fixed rider salary is not given a newly invented account code in this chart: deduct the daily pro-rata share from the rider remittance at settlement and post it through rider settlement / cashbook day movement with auditable `RIDER_RECEIVABLE` lines alongside daily cash inflows/outflows (credit remittance-before-salary, debit salary deduction when `salaryDeduction > 0`). Introduce a dedicated salary expense/payable account only if a later explicit finance policy requires one.

Illustrative postings must be confirmed against the finance policy before implementation:

- Pickup advance: debit `OS_COD_PAYABLE`; credit the funding wallet.
- Finalized batch obligation: debit `OS_BATCH_COD_CLEARING`; credit `OS_COD_PAYABLE` for the batch original COD.
- Paid-to-OS delivery: create OS credit for COD plus the full configured delivery fee only when that fee is included by the OS; do not create rider COD receivable. When the fee is not included, create a rider receivable for the delivery fee only (COD remains OS credit). When the fee is included, create no rider fee receivable. Recognize delivery-fee revenue and commission according to policy.
- Rider cash collection (technical mode `CASH_RECEIPT_EXCEPTION`): debit selected rider-clearing/settlement account; credit `Customer COD Receivable`; separately recognize fee revenue and commission according to policy. This is the only delivery mode that creates rider COD receivable; paid-to-OS may still create a fee-only rider receivable when the fee is excluded from OS credit.
- Rider remittance: debit wallet(s); credit `Rider Settlement Receivable` (`RIDER_RECEIVABLE`) for rider cash collections and for fee-only receivables from paid-to-OS deliveries where the fee was not included in OS credit. When a daily salary deduction applies, post a visible `RIDER_RECEIVABLE` credit for remittance before salary and a `RIDER_RECEIVABLE` debit for `salaryDeduction` in the same settlement journal (description includes the salary amount); no new account code.
- OS account payment: debit `OS_COD_PAYABLE`; credit the selected Cash, KBZ Pay, and/or Wave Pay wallets. Applied OS credit uses a balanced memo entry and retains per-credit allocations.
- Wallet adjustment: when the actual wallet balance is higher, debit the selected wallet and credit `CASHBOOK_ADJUSTMENT`; when lower, debit `CASHBOOK_ADJUSTMENT` and credit the selected wallet. The posting carries the actor, business date, hub, and required reason and remains append-only.
- Physical return to OS: confirmation creates OS credit for the parcel's batch and does not create a wallet line. Paid-to-OS delivery credits and physical-return credits automatically reduce the next batch advance before any wallet payment; surplus remains available within the same OS/hub.
- Partial Return (`OS_PARTIAL_RETURN_ADJUSTMENT` / `PARTIAL_RETURN_COLLECTION`): record the bounded collection/shortfall accounting for `min(Original COD − Actual COD Collected, advance)` with versioned source IDs after reversal. This remains separate from the OS account's batch return credit and does not reinstate the retired settlement-draft workflow.
- Linked delivery: use the group-adjusted fee (base fee for the first parcel plus 1,000 MMK per additional parcel) for delivery-fee revenue and rider commission. The link dialog requires a responsible rider and preselects that rider when every selected parcel already has the same rider; authorized users may replace the selection. Linking atomically assigns/reassigns all selected parcels to that rider and records assignment history. The journal source must identify the linked group and remain idempotent. Rider settlement must not substitute incomplete linked groups with individual member fees. **Implementation boundary:** linked members support COD-only paid-to-OS credit; their shared group delivery fee remains on the rider-receivable path and may not be included in that OS credit.

The system must expose the exact journal lines behind every business total.

## 8. Data Model

Core entities:

- `Organization`, `Hub`, `User`, `Role`, `Permission`, `UserRole`, `Session`. A Phase 2 Online Shop User has exactly one `OnlineShop` authorization link.
- `OnlineShop`, `Zone`, `Rider`, `RiderZone`.
- `Rider` compensation fields (persisted): pay model (`PERCENTAGE` | `SALARY` | `SALARY_PLUS_PERCENTAGE`), `commissionRateBps` when the model includes percentage, and `monthlySalary` in integer MMK minor units when the model includes salary.

Return information supports an explicitly OS-visible return note/flag separate from internal-only operational notes.
- `Parcel` also stores Partial Return Actual COD Collected and calculated shortfall fields, assignment metadata, and optional linked-group membership.
- `LinkedParcelGroup` stores hub, group membership, base fee, per-additional-parcel fee, adjusted total fee, and lifecycle/audit metadata. Linked members retain their individual parcel and batch identity; matching address is stored/displayed data, not a linking prerequisite.
- `DeliveryWay` with parcel, rider, assigned time, outcome, commission rate/base/amount, and completion time. Duplicate open ways for the same parcel are closed with outcome `SUPERSEDED` while one primary way remains open (on `OUT_FOR_DELIVERY`) or is completed with the real delivery outcome; outcome recording may create a completed way when none is open so ERP can finish delivery without a prior rider-started way.
- `StatusHistory`, `ReasonCode`, `Alert`, `AlertRecipient`.
- `Account`, `Wallet`, `JournalEntry`, `JournalLine`, `OsBatchObligation`, `OsAccountPayment`, `OsPaymentAllocation`, `OsReturnCredit`, `OsCreditAllocation`, `OsHistoricalSettlement`, legacy `Settlement`/`SettlementLine`, `CashbookDay`, `WalletTransfer`.
- `Batch` stores automatic-accounting/idempotency metadata for new pickup-and-advance records and optional one-to-one historical OS settlement evidence. `Parcel` stores an optional planned delivery date for rescheduling, delivery collection mode, and the auditable paid-by-OS credit components; its original created timestamp remains the age source for operations queues.
- `AuditLog`, `ImportJob`, `Manifest`, `ReportRun`.

Use UUIDs or another non-guessable public ID, internal relational keys as appropriate, created/updated timestamps, optimistic concurrency/version fields for mutable operational records, and soft deletion only for master data where legally appropriate. Add unique constraints for tracking number, OS+pickup-date batch identity, journal source event, settlement scope, and wallet/day-close identity. Do not add unique or composite-unique constraints on `Order ID`; it remains a searchable, non-unique OS reference. Preserve optional `osOrderDate` as a searchable attribute when present. Index status/date/hub/OS/order ID/osOrderDate/rider/search fields, including `(trackingSequence, trackingNumber, id)` for deterministic numeric tracking order.

Use pagination, filter validation, bounded page sizes, and explicit timezone/date semantics. Provide OpenAPI documentation when implementation begins.

A user must explicitly apply or ignore every displayed candidate. A unique phone candidate with compatible blank/equivalent fields is safe; multiple locations, a different customer name/address/township, and an exact name-and-address fallback for a previously used second phone require review. The fallback never auto-fills. A bulk save submits at most 500 valid rows at once and preserves later valid rows in the recovered draft, with an on-screen count explaining the remainder. It returns an editable preview with source page, row confidence, and warnings; customer name, address, optional phone, COD, and optional non-unique manifest row reference are mapped into the existing bulk parcel grid only after explicit user confirmation. Township matching is conservative against master data, unmatched/ambiguous townships require review, and delivery fees remain server-derived. Image-only/scanned documents return `OCR_REQUIRED` through an adapter boundary until an approved local OCR implementation exists.

## 11. Key Workflows

### Pickup and advance

1. Superadmin, Finance, or Operations Manager creates an automatic-accounting draft batch for one OS and exact pickup date, entering any actual pickup advance as a Cash/KBZ Pay/Wave Pay split. Dispatcher may create a zero-advance batch.
2. One idempotent save creates the draft and—when an advance was entered—the balanced `BATCH_PICKUP_ADVANCE` wallet movement. It does not reserve available OS credit or create an OS obligation. A browser refresh can retry the same saved request without duplicating the batch or wallet movement.
3. Operations adds/imports parcels and reviews the derived COD, advance, available credit, expected credit application, outstanding amount, and any advance-over-COD carry-forward credit.
4. Authorized operations explicitly finalizes the batch. Finalization atomically creates the COD obligation, applies only the credit needed for the finalized COD, creates any over-advance credit, and locks additions plus COD/delivery-fee/township edits. The legacy Finance post-pickup-advance action applies only to older non-automatic batches.

### Assignment and delivery

1. Dispatcher filters eligible parcels by zone and assigns a rider.
2. System generates a versioned PDF manifest and assignment snapshot.
3. Rider opens assigned work and starts a way.
4. Rider records Delivered, Partial Return, Failed, or Rejected (or Superadmin / Operations Manager / Dispatcher sets any allowed status from the ERP **Dispatch Queue**, including corrections broader than rider-allowed transitions). Standard Delivered follows the rider-cash workflow; **Delivered — paid to OS** is the explicit ERP action that records OS credit for COD (and the fee only when included), never creates rider COD debt, creates a fee-only rider receivable when the fee is excluded, recognizes commission as for other `DELIVERED` parcels, and does not place the parcel on Return to OS / `PENDING_RETURN`. Ops can report both physical-return candidates and Paid-to-OS deliveries from the focused Return to OS workspace in one labelled OS Handover Report; download is non-mutating, while Received remains physical-return-only. Failed must receive an operations decision to retry tomorrow, reschedule to a chosen date, or send to OS. Cancellation is recorded as Rejected and enters Return to OS. Partial, Failed, and Rejected capture the configured reason and required note; Partial additionally requires Actual COD Collected. Dispatch Queue's direct `PENDING_RETURN` action records its required free-text return reason in one dialog. ERP `OUT_FOR_DELIVERY` / outcome recording keeps one primary `DeliveryWay` (prefer current rider, else oldest open), closes other open ways with outcome `SUPERSEDED`, and creates a completed way when none is open. Reschedule reason codes raise `DATE_CHANGE` alerts.
5. ERP updates inventory, OS credit and/or rider receivable (COD+fee for rider cash; fee-only when paid-to-OS fee excluded), commission eligibility, and return queue.

### Pending return and OS recovery

1. `REJECTED` (including cancellation) enters the Return to OS workflow. A Failed parcel first awaits its explicit retry-tomorrow, reschedule-date, or send-to-OS decision; only the send-to-OS decision enters `PENDING_RETURN` with its due date = entry date + four hub-timezone calendar days. Partial may remain `PARTIAL` until finance/operations resolution; the finance recovery queue also includes `PARTIAL` / `FAILED` / `REJECTED` before or without that intermediate status. A date change is a separate reschedule action: it stores a planned delivery date/reason, leaves the parcel in its original batch, and does not reset the original age.
2. Operations monitors and resolves overdue returns via **Dispatch Queue** parcel status (`/operations/dispatch`), the dedicated **Return to OS** workspace (`/operations/returns`), and the calculated overdue-return review queue in **Operations Review** (`/operations/review`). The direct Pending Return action requires a free-text reason recorded in status history. The focused Return to OS workspace can download a branded landscape OS Handover Report with labelled physical-return and Paid-to-OS sections, without changing parcels or finance. Physical handoff is confirmed separately; only that confirmation changes eligible physical parcels to `RETURNED` and creates OS credit. Paid-to-OS `DELIVERED` parcels remain outside the physical-return queue and are report-only in this workspace. Timer extensions remain audited as already specified.
3. At due time, Operations Review presents the pending-return age and direct action while the parcel remains pending. This calculated review entry is not a new persisted-alert producer.
4. **Finance OS recovery:** authorized Finance users (and Superadmin / Operations Manager) confirm one or up to 50 physical returns via **Received** (`POST /finance/os-returns/receive` or `/receive-bulk`, with idempotency key). The bulk command validates the complete scoped selection and records a fingerprinted audit record; it atomically sets each eligible parcel to `RETURNED` and records its batch return credit. It does not credit a wallet. Auditor may view the queue but cannot receive returns.
5. Finance OS & riders presents OS account balances, next-batch advance reduction, record-payment and account-history actions, and the read-only legacy settlement history. Paid-by-OS credits, physical-return credits, and then Cash/KBZ Pay/Wave Pay payments reduce selected batch payables through the simplified OS account (§6.6).
6. Explicit paid-to-OS `DELIVERED` has no rider COD obligation. When the delivery fee is not included in OS credit, the rider owes a fee-only receivable (settlement remits fee − commission); when the fee is included, there is no rider fee receivable either. Standard rider cash collection creates rider outstanding for COD and fee, which is cleared when its evening settlement is manually recorded and verified.

### Bulk dispatch and linked delivery
1. Dispatcher opens **Dispatch Queue**, filters unassigned parcels by batch (batch dropdown), rider, assignment status, zone/township, customer/order/tracking (case-insensitive), and date range (**batch pickupDate** on the parcel list).
2. Dispatcher selects eligible parcels, chooses a rider, and submits one atomic bulk assignment.
3. System validates hub scope, rider eligibility, parcel state, and duplicate/concurrent assignment conditions, then generates a PDF manifest (multi-rider selection supported in the download modal; manifest/Reports date filters use status activity date; PDF embeds Myanmar font).
4. Superadmin, Operations Manager, or Dispatcher may first request Dispatch Queue's read-only possible-link review. It identifies eligible unlinked parcels with the same normalized customer name and phone in one shop and hub, across batches/pages; it never links automatically. Address equality is not required, so the reviewer checks displayed addresses, township, current rider, status, and configured fee, selects the intended members, confirms the address review, selects the responsible rider, and enters a reason.
5. The authorized user links two to 20 eligible selected parcels to one responsible rider. Address and fee matching are not required, but `DELIVERED`, `RETURNED`, and `VOIDED` parcels are excluded.
6. System stores linked-group metadata and applies the highest member fee plus 1,000 MMK for each additional parcel to delivery-fee revenue and customer COD receivable calculations.
7. Dispatch Queue keeps members of a group that are visible on the current page together and marks them with a bracket-style group cue, visible-member count, and adjusted group fee. It states when filters or pagination may hide other members. Rider sees linked parcels grouped together; commission is calculated from the adjusted linked-group delivery fees.
8. Rider settlement includes linked-group fees/commission only when every group member is `DELIVERED`; incomplete groups do not fall through to individual member fees in settlement totals.
9. A linked parcel may use **Paid to OS** for COD only. The group delivery-fee inclusion option is unavailable; shared fee and commission remain on the rider path and post once after all members are delivered.
10. Riders can filter parcels by township and sort them by township in the mobile app; list/detail UI favors OS Order ID when present.
11. Tap-to-call from the rider app opens the native phone dialer or provides an accessible fallback when direct dialing is unsupported.

### Rider evening settlement

1. System calculates compensation under the rider’s pay model (daily successful-delivery commission and/or daily pro-rata salary deduction `floor(monthlySalary / daysInMonth)` per §6.7), returns `salaryDeduction` on preview, and computes expected amount owed from rider cash collections as `cash COD + cash fees - commission - salaryDeduction` (including fee-only amounts from paid-to-OS deliveries where the fee was not included in OS credit; paid-to-OS never adds COD to this total).
2. Rider declares remittances by Cash, KBZ Pay, or Wave Pay; manual settlement can split a single rider handover across multiple wallets (for example Cash 100,000, KBZ Pay 100,000, Wave Pay 200,000). Salary (when applicable) is deducted from the collected total and shown as auditable `RIDER_RECEIVABLE` settlement journal lines (credit remittance-before-salary, debit salary deduction).
3. Cashier verifies references/counts and records actual amounts.
4. Variances require reason and authorization; settlement is locked after posting.
5. The rider-facing outstanding balance remains visible until this manual settlement is posted and verified.

### Cashbook day-close

1. Cashier reviews each wallet’s opening, movements, transfers, expected closing, and physical/digital verified balance.
2. System flags missing settlements, unposted events, and variances.
3. Cashier submits close; authorized manager approves exceptions.
4. System locks the business date and emits a close summary. Reopen requires Superadmin and creates a compensating audit trail.

## 13. Non-Functional Requirements

- **Correctness:** balanced double-entry journals, idempotent money commands, transactional status/ledger updates, no floating-point money math.
- **Security:** JWT claim validation, hashed passwords, secure secret handling, CORS allowlist, rate limiting, input validation, authorization at API boundary, auditability, and safe error responses.
- **Reliability:** graceful shutdown, database transaction boundaries, retry-safe commands, health/readiness endpoints, structured logging, and alert delivery retry/dead-letter handling. Atomic frontend releases retain recently built hashed assets from the prior release so already-open browser tabs can finish loading them; the entry document is not cached, and missing asset paths return `404` rather than the SPA document. A failed ERP lazy-route import renders a localized recovery screen with a page-reload action. The repository includes a disposable local PostgreSQL financial-flow runner that applies the committed provider-specific migrations and exercises payment idempotency/correction, concurrent payment retries, concurrent tracking allocation/finalization, aggregate ledger summaries, automatic advances, simple workflow, and bounded detail reads. The current repository contains 21 PostgreSQL and 25 SQLite migration directories; the isolated PostgreSQL run passed 6 suites / 25 tests. Production deployment verification remains a release check.
- **Performance:** indexed operational queries, pagination, bounded exports, background jobs for large imports/PDFs/reports, and no unbounded dashboard queries.
- **Availability:** define target uptime and backup/RPO/RTO before production; PostgreSQL backups must be encrypted and restore-tested.
- **Accessibility/localization:** keyboard-accessible web UI, mobile screen-reader labels, English/Myanmar coverage, locale-aware dates/numbers, and consistent hub timezone.
- **Observability:** request IDs, audit IDs, structured logs, metrics for failed transitions/settlements/day-close, and error monitoring with sensitive data redaction.
- **Privacy:** minimize customer data, restrict access by role/hub, encrypt transport and managed storage, define retention/deletion policy, and avoid customer data in logs.

## 14. Architecture

Use three independent applications with separate dependency manifests and configuration; do not use a monorepo:

```text
frontend/    # React + Vite + TypeScript
backend/     # Express + TypeScript + Prisma
mobile/      # React Native + Expo + Expo Router
```

The API is the authoritative boundary for business rules and ledger posting. Web and rider clients use typed API contracts, React Query for server state, React Hook Form for forms, and one auth abstraction each. Domain modules should separate parcel operations, accounting, settlements, reporting, alerts, identity, and master data. Use an outbox/event mechanism or transactional alert creation so Partial/Failed events cannot commit without their alert record. Use WebSocket/SSE or short polling for ERP alerts based on deployment constraints; the database event remains authoritative.

3. **Parcel operations:** batch import, parcel model, lifecycle/state machine, ERP All Batches + Dispatch Queue split (dense Dispatch Queue with inline assign/status, multi-edit, multi-rider manifest), Operations Review and notification-dropdown attention flow, all-status actions for Superadmin/Operations Manager/Dispatcher, assignment, rider app tabs, manifests, persisted alerts, and return timer/queue resolution.
4. **Ledger core:** accounts/wallets, journal posting, pickup advances, delivery collections, commission and salary-from-remittance calculation (cashbook-visible), OS receivables/deductions, and immutable reversals / compensating adjustments.
5. **Settlements:** rider settlement by wallet, simplified OS accounts with payment/credit history and non-destructive payment correction, read-only legacy settlement history after cutover, reconciliation, cashbook, day-close/reopen controls, variance approvals, and finance reports.
6. **Reporting and hardening:** daily/monthly/profit (with component breakdown)/OS/rider/return reports, exports, performance indexes, security review, backup/restore drill, observability, localization QA, accessibility QA, and end-to-end acceptance tests.
7. **Phase 2 roadmap (planned; not implemented):** an authenticated, read-only Online Shop portal. An administrator provisions an OS login linked to exactly one shop. The user searches only that shop's parcels by exact tracking number or non-unique OS `Order ID`, then views OS Order ID, tracking number, customer/address, COD, delivery fee, current status, status history, and return reason/notes explicitly marked OS-visible. Server-side shop scoping is mandatory; internal notes and all finance, settlement, wallet, ERP-write, and cross-shop access are excluded. This roadmap uses the current tracking-number identity and does not include parcel stickers, barcode/QR generation, or template management.

   Phase 2 begins only after the outstanding Phase 1 release-readiness work in §17 has been completed or explicitly accepted: production PostgreSQL deployment and restore verification, real-time alert transport, observability and backup/restore drills, signed APK build/install and device QA, and broader production-like end-to-end coverage. Operational UX, mobile reliability, and further business-process upgrades may be planned after that release gate, but no additional Phase 2 business rules are approved by this specification yet.

## 16. Acceptance Criteria

- Every monetary business event is represented by balanced, queryable journal lines and cannot be posted twice.
- A rejected/failed/returned parcel earns zero rider commission and is visible in the correct return/settlement calculations. Salary-bearing pay models still follow the configured salary rules without inventing commission on those outcomes.
- Failed parcels require an explicit retry-tomorrow, reschedule-date, or Return to OS decision; cancellations are recorded as `REJECTED` and enter Return to OS with the configured reason/note. A direct Pending Return status requires one free-text reason and records it in status history. The focused Return to OS workspace downloads one non-mutating, landscape OS Handover Report with separate labelled physical-return and Paid-to-OS sections; its return rows retain wrapped customer, address, and reason/note data, and its fee/total columns include delivery fees only when the persisted paid-to-OS fee-included decision applies. Paid-to-OS `DELIVERED` parcels stay off the physical Return to OS / `PENDING_RETURN` queue and are report-only; they cannot be confirmed as returned. Operations can resolve Pending Returns via Operations return queue / parcel status (`PENDING_RETURN → RETURNED`). Finance can confirm physical return-to-OS via **Received** on the OS & riders pending-return panel (`FAILED` / `REJECTED` / `PENDING_RETURN` / `PARTIAL` → `RETURNED`), creating a batch return credit without a wallet credit. The OS account applies that credit and split-wallet OS payments to batch COD payables; payment corrections are non-destructive and legacy settlement history is retained read-only in the collapsed archived section after cutover.
- Recording a failed delivery first persists the configured reason/note and alert; its separate retry/reschedule/Return-to-OS decision may be made later without losing the failed record. An unacknowledged Failed alert links to the pending decision in Dispatch Queue while the parcel remains `FAILED`. Staff parcel details render the ordinary and exceptional status history as a human-readable journey timeline, and failed-decision reschedules retain their selected date at the beginning of their history note.
- A new automatic-accounting batch can save its actual advance wallet split and later parcel COD in one continuous workflow: Superadmin, Finance, or Operations Manager can record the advance exactly once at draft creation; finalization atomically creates the single OS obligation, applies only needed same-OS/hub credit, creates any advance-over-COD carry-forward credit, and locks parcel additions plus COD/delivery-fee/township edits. Retried or concurrent finalization cannot duplicate money movement, credit allocation, or carry-forward credit. Legacy batches retain their explicit posting workflow.
- Historical reconciliation retains the newest three batches overall and marks older batches settled with an audited OS clearing adjustment that does not change any wallet, parcel status, or rider debt. It is Superadmin-only, preview-validated, idempotent, and locks those historical batch COD/parcel additions.
- A Superadmin can reconcile an actual Cash, KBZ Pay, or Wave Pay balance from Finance without rewriting history: the system posts exactly the calculated signed `CASHBOOK_ADJUSTMENT`, with hub, business date, actor, and reason. The dashboard shows the current OS COD payable total as **Outstanding to OS** and links to the OS account workspace.
- An explicit paid-by-OS `DELIVERED` parcel creates OS credit for COD plus the full configured delivery fee only when the OS includes that fee, and creates no rider COD debt. When the fee is not included, create a rider receivable for the delivery fee only and recognize commission as for other `DELIVERED` parcels (net remittance fee − commission); when the fee is included, create no rider fee receivable. A linked parcel may be paid to OS for COD only: fee inclusion is rejected and the shared linked delivery fee/commission remains rider-collected and posts once after every member is delivered. Paid-to-OS parcels must not appear on physical Return to OS / `PENDING_RETURN` queues, but are reportable alongside selected physical returns in the single non-mutating OS Handover Report. Paid-by-OS and confirmed physical-return credits are available at automatic-batch finalization for the same OS/hub, with surplus carried forward. Standard rider cash collection is the delivery mode that creates rider COD receivable requiring manual settlement.
- Superadmin, Operations Manager, and Dispatcher can set any allowed parcel status from the ERP Dispatch Queue with attributable status history; riders remain limited to permitted delivery outcomes.
- ERP shows gross profit with visible components on Finance/Reports and/or Dashboard (Phase 1 requirement; the component report and breakdown UI are implemented).
- Partial Return requires a validated Actual COD Collected amount, posts at most one unreversed OS shortfall offset / collection pair (`OS_PARTIAL_RETURN_ADJUSTMENT` / `PARTIAL_RETURN_COLLECTION`, versioned `sourceId` after reversal), and preserves the original and adjusted values.
- Status override leaving `DELIVERED`/`PARTIAL` while unreversed money journals remain is rejected with `409 MONEY_POSTED` (parcel-scoped including versioned `parcelId:…` and `LINKED_RIDER_RECEIVABLE_COD`; group-scoped `LINKED_*` including versioned `groupId:…`). The exception is an authorized, noted correction of a delivered linked rider-cash parcel to COD-only Paid to OS: it reverses only that parcel's linked COD receivable and records one OS credit without changing the shared linked fee/commission; retries remain non-duplicating. Other delivered collection-mode changes return `409 DELIVERY_COLLECTION_CORRECTION_REQUIRED`. After reversal, delivery collection and related money events re-post with versioned sourceIds; duplicate open `DeliveryWay` rows are closed with outcome `SUPERSEDED` while one primary way carries the real outcome.
- Partial and Failed actions require reason codes and produce ERP alerts for Superadmins and Operations Managers; reschedule/date-change reason codes (`DATE_CHANGE`, `DELIVERY_DATE_CHANGE`, `RESCHEDULE`) produce alert type `DATE_CHANGE`.
- Operations Review is available to Superadmin, Operations Manager, and Finance. It must show current derived negative-wallet alerts for Cash, KBZ Pay, and Wave Pay in the caller's permitted hub scope, including balance and shortfall; each clears automatically when its own balance is zero or above and has no acknowledgement action. Superadmin and Operations Manager additionally see recent unacknowledged Partial, Failed, and `DATE_CHANGE` persisted alerts in context, plus separately calculated overdue Pending Return and unresolved 3+ days-in-hand queues. The header dropdown shows the same negative-wallet alerts for all three roles and persisted parcel alerts for Superadmin and Operations Manager; it preserves parcel alerts until explicit acknowledgement and links View all to Operations Review. Opening or viewing never acknowledges a parcel alert.
- Bulk dispatch validates the complete selection atomically, records assignment history, and produces a manifest PDF (Myanmar font embedded; Reports/manifest date range = status activity date; Dispatch Queue parcel-list dates = batch pickupDate). Dispatch sorting validates the ten supported fields/directions, persists across server-paginated pages, orders generated tracking numbers numerically by nullable `trackingSequence` with a tracking-string fallback, and retains a deterministic ID tie-breaker. The computed Total column remains unsortable. Dispatch Queue excludes `VOIDED`, `DELIVERED`, and `RETURNED` rows by default at the server before pagination; its completed-parcels checkbox only restores `DELIVERED` and `RETURNED`, and works with the active filters. The role-gated Dispatch Queue Void entry affordance appears only for likely eligible `CREATED`, unassigned, unlinked rows and still relies on the existing preview, confirmation, authorization, and server eligibility guards.
- Linked parcels use the base-plus-1,000-MMK fee rule and calculate rider commission from the adjusted linked-group fee. Individual linked members may be COD-only Paid to OS; they cannot include that shared fee in OS credit.
- Parcel import/create flows preserve a unique `trackingNumber` identifier and permit duplicate OS `Order ID` values within the same batch without uniqueness errors. Dispatch Queue and rider app UIs present OS Order ID prominently when present; the spec does not require a branded `LTY-[YYMMDD]-[Sequence]` policy in Phase 1.
- Phase 2 provides an OS portal scoped to one linked shop per login. Exact tracking-number search and non-unique OS Order ID search return only that shop's parcels; parcel detail exposes operational fields and only explicitly OS-visible return reason/notes.
- For the Phase 2 OS portal, an OS user cannot read another shop's search result or parcel detail by changing an identifier or request parameter, cannot access finance or ERP write endpoints, receives every parcel for a duplicated matching OS Order ID within their own shop, and never receives an internal return note in a portal response.
- Pending Return defaults to four days, supports audited extensions, and cannot silently expire or disappear.
- A reschedule stores its intended next delivery date/reason without moving the parcel out of its original batch or resetting its age. Dispatch Queue provides focused To assign, With riders (`OUT_FOR_DELIVERY` only after physical handover), Rescheduled, Return to OS, and unresolved 3+ days-in-hand queues; `ASSIGNED` remains a planning/overnight state. The latter queue is calculated from original parcel creation time.
- Rider settlement formula (including daily pro-rata salary deduction, incomplete linked-group fee exclusion, and fee-only remittance for paid-to-OS deliveries where the fee is not included in OS credit) and wallet remittances reconcile to a locked daily cashbook close.
- Rider app supports township filtering/sorting and native-dialer tap-to-call for customer phone numbers with an accessible fallback path, with a quick route-friendly list layout.
- Web and mobile protected routes wait for verification, handle expiry safely, and never trust client-side JWT decoding.
- English/Myanmar translations cover all visible starter UI and persisted toggles work across restarts.
- Unit and integration tests cover ledger invariants, auth, validation, workflows, permissions, errors, and critical UI behavior.

## 17. Current Implementation Status

- **Paid-to-OS workflow:** the shipped parcel collection mode includes the explicit Dispatch Queue paid-to-OS action, auditable optional full-fee inclusion, `OS_PAID_TO_OS_CREDIT` journal/source records (COD-only when fee excluded; COD+fee when included), and commission on `DELIVERED` as for other successful deliveries. Linked members support COD-only Paid to OS; their shared group fee cannot be included in OS credit and remains on the rider path, posting once with group commission after the final member is delivered. An authorized ERP user can correct an already delivered linked rider-cash member to COD-only Paid to OS with an attributed note: the service reverses only that member's COD receivable and creates its one OS credit, without duplicating or reversing the shared linked fee/commission. Repeating the correction is idempotent; other delivered collection-mode changes are rejected. When the delivery fee is not included in OS credit, non-linked shipped delivery posting creates an `OS_PAID_TO_OS_FEE_RECEIVABLE` fee-only rider receivable (not COD) so settlement remits fee − commission; when the fee is included, no fee receivable is created. Finance terminology now presents **OS credit** rather than the retired “OS Advance Receivable” labels. Physical-return credits share the same available-credit mechanism. The focused Return to OS workspace joins selected physical-return candidates and date/shop/rider-filtered Paid-to-OS deliveries into one non-mutating `POST /operations/parcels/os-handover/pdf` report with labelled sections. Physical Received confirmation remains separate and cannot apply to paid-to-OS rows. Do not place paid-to-OS `DELIVERED` parcels on physical Return to OS / `PENDING_RETURN` queues.

- **Failed-delivery workflow and parcel journey:** Dispatch Queue uses one adaptive two-step modal to save the failed reason/note and then record the separate retry, reschedule, or Return-to-OS decision. Closing after the first step leaves the `FAILED` status and alert in place. A current unacknowledged Failed alert opens that parcel directly at the decision step. The read-only staff parcel-details modal renders all status history as a human-readable journey timeline; failed-decision reschedules persist the selected date as a `YYYY-MM-DD` note prefix for that timeline.

- **Web release and route recovery:** each atomic release stages the current frontend build together with non-conflicting hashed assets from the immediately previous release, retaining those assets for 30 days. Nginx serves asset requests only when the requested file exists, returns `404` for a missing asset, and prevents caching of `index.html`. If an ERP lazy route cannot load, the user receives localized refresh guidance and a reload action instead of a raw router exception.

- `backend/`: Express + Prisma API with JWT auth, English/Myanmar errors, validation, and targeted Jest/Supertest coverage. Implemented behavior includes automatic new-batch actual-advance wallet posting with idempotency, draft parcel entry, and locked/idempotent finalization that creates one obligation, applies only needed same-OS/hub credit, and carries advance-over-COD credit forward; it also includes the `PAID_BY_OS` / `CASH_RECEIPT_EXCEPTION` parcel collection mode with `OS_PAID_TO_OS_CREDIT` journals, linked COD-only Paid to OS, and fee-excluded `OS_PAID_TO_OS_FEE_RECEIVABLE` fee-only rider receivable posting. Other implemented behavior includes a hub-scoped, read-only wallet transaction statement with aggregate period balances, filtered and paginated journal lines, per-entry balance-after values computed across every period movement, CSV export, transaction-source attribution, and formula-safe CSV cells; Superadmin historical settlement of every batch except the newest three; server-paginated All Batches with current OS balances; atomic dispatch actions; reschedule and physical-return-to-OS bulk flows; a three-day-in-hand queue based on parcel creation time; OS account payments/credits with non-destructive correction; return-credit and COD-journal actor attribution; append-only `CASHBOOK_ADJUSTMENT` posting for a verified Cash/KBZ Pay/Wave Pay increase or decrease; read-only legacy settlement history after cutover; detailed reports; bounded ledger detail plus aggregate account balances; reconciliation, cashbook, reopen, and salary paths. The repository currently contains 22 PostgreSQL migration directories and 26 SQLite migration directories, including the paid-to-OS credit migration. Previous disposable local PostgreSQL verification passed 6 suites / 25 tests, including automatic advances, simple workflow, simultaneous payment retry, and tracking-allocation/finalization coverage. Remaining work is external/manual: production PostgreSQL deploy/restore verification, real-time alert transport, observability, backups, and broader integration coverage.

- `frontend/`: Vite/React/TypeScript ERP shell with protected routes, verified-token auth bootstrap, persisted JWT auth, English/Myanmar translations, theme persistence, finance and report surfaces, atomic dispatch, parcel field audit UI, All Batches / Dispatch Queue / Return to OS / Operations Review navigation, and the public `/app` rider download page with a direct APK link. Finance overview shows the current signed Cash, KBZ Pay, and Wave Pay balances both individually and as their Total wallet balance; the wallet section is first, Cash uses a banknote card, and KBZ Pay / Wave Pay use bundled brand logos.
