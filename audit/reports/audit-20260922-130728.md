## Executive summary

The refactor materially improves financial integrity. Draft batch creation no longer reserves OS credit or creates an obligation; finalization is atomic, uses a per-batch mutation lock plus a same-OS/hub allocation lock, and creates one obligation/allocation/carry-forward result. Linked Paid-to-OS correctly excludes the shared fee, and the correction path reverses only the member COD receivable while preserving group fee and commission records. Cashbook posting helpers translate both uniqueness and serialization races after re-reading the day state.

One reliability defect remains in the shared parcel serializable-transaction helper. After its third PostgreSQL `P2034`, it rethrows the raw Prisma error. Paid-to-OS delivery/correction uses this helper, so peak contention can return a 500-style internal error instead of a retryable 409 domain response. Transactions remain atomic, so this is not evidence of ledger corruption, but it violates the specified stable concurrency outcome and can provoke ambiguous client retries.

## Findings

### FIN-001 — Exhausted parcel serialization retries leak a raw database error

**Risk:** Medium
**Location:** `backend/src/services/parcel.service.ts:260-268`, callers at `:1117-1124` and the bulk status path below `:1167`.

**Evidence:** `serializableTransaction` retries PostgreSQL `P2034` twice, but on the third occurrence line 265 executes `throw error`. The intended `ApiError(409, "TRANSACTION_CONFLICT", ...)` at line 268 is unreachable for the exhausted-retry case. `updateStatus` only translates `P2002`, so it does not repair this result. Both initial Paid-to-OS delivery and the already-delivered linked correction execute inside this helper.

**Failure scenario:** Concurrent parcel status/accounting work or a cashbook close repeatedly causes serialization failure. All transaction effects roll back, but the final attempt escapes as a Prisma error. The API can expose an internal-server response rather than a stable `409 RETRYABLE_CONFLICT`/`DAY_CLOSED`, leaving an operator unsure whether the financial action committed and encouraging unsafe manual retries.

**Impact:** Availability and operational reliability degradation on money-bearing delivery actions; violation of the documented stable conflict contract. No partial journal, OS credit, or parcel mutation should survive because each attempt is transactional.

**Recommended mitigation:** On the final `P2034`, re-read the relevant cashbook day(s) outside the aborted transaction, return `409 DAY_CLOSED` when closed, otherwise return `409 RETRYABLE_CONFLICT`. Add a PostgreSQL-only regression test that forces retries to exhaustion for both single and bulk status updates and asserts no financial side effects plus the stable error code.

## Performance, reliability, and scalability observations

- Finalization serializes credit allocation at `(shopId, hubId)` granularity. This is conservative and financially safe, but high-volume shops at one hub will finalize sequentially. Monitor lock wait time and `P2034` frequency after release.
- `accountRows` performs bounded bulk queries and in-memory aggregation across all obligations for a shop/hub. It avoids an obvious per-row database N+1, but response/finalization cost grows with historical batch count. Introduce pagination or summarized balance tables only if production telemetry shows this becoming material.
- The over-advance credit uses the existing `OsReturnCredit` table with a synthetic unique `parcelId`. That column has no parcel foreign key, so the record is valid; the explicit `kind = BATCH_OVER_ADVANCE` exclusion keeps it out of physical-return totals.

## Positive controls verified

- Batch advance wallet splits must exactly equal the saved actual advance, use safe non-negative integers, and require an idempotency key for positive money movement.
- Advance posting, batch creation, and cashbook-day validation share one transaction; closed-day rejection rolls the batch and journal back.
- Draft batches create neither OS obligation nor advance-credit allocation.
- Finalization is `Serializable`, takes a batch mutation lock and a same-OS/hub credit lock, freezes parcel additions, and is replay-aware.
- Carry-forward over-advance credit is uniquely keyed and excluded from returned-COD reporting while remaining allocatable as OS credit.
- Initial linked Paid-to-OS is COD-only; the shared linked fee/commission posts once when the group completes.
- Already-delivered linked correction requires an override note, reverses the unreversed member COD journal, creates a matching negative rider-receivable projection and one COD-only OS credit, and preserves group fee/commission records.
- Active user role and hub scope are reloaded server-side for batch finalization and parcel status actions.
- Generic cashbook journal posting now translates both `P2002` and `P2034` after an out-of-transaction closed-day re-read.
