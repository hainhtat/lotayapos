# Reliability and financial workflow audit

Timestamp: 2026-09-16 19:03:48 Asia/Yangon. Context: working-tree changes based on `8168c2d`; concurrent implementation ongoing. Findings describe the inspected snapshot, not a release approval.

## Scope and exclusions

Reviewed PROJECT_SPEC.md and AGENTS.md, ledger summary changes, OS payment modal/rules and backend payment persistence/replay, parcel draft/PDF changes, deployment prerequisites, rollback, domain checks, restore drill and deployment test scripts. No production access, external requests, database writes, migrations, installs, or backend tests were performed. PostgreSQL integration validation is owned by another agent.

## Executive summary

Three Medium findings need resolution or explicit follow-up. No Critical or High issue was confirmed within this bounded review. Database aggregation removes the historical ledger entry cap from wallet totals, and exact request reuse improves in-modal payment retries. A correction-prefill mismatch and replacement replay validation gap remain in the inspected snapshot. Deployment rollback needs to restore prior absence as well as prior file content.

## Findings

### R1 — Medium: correction wallet fields do not match persisted history

Location: `frontend/src/components/os-accounts-panel.tsx`, `openCorrection`; `backend/src/services/os-account.service.ts`, `createPayment`.

Evidence: history wallet rows are created from `Object.entries(input.wallets)` with names `cash`, `kbzPay`, `wavePay`. The modal reads `CASH`, `KBZ_PAY`, `WAVE_PAY`, producing zero values for real API responses.

Impact: correction does not prefill the original payment; users must reconstruct financial values and could replace a payment with an unintended amount.

Mitigation: use the actual API wallet names, with an explicit compatibility mapping if historical uppercase rows exist. Test correction using API-shaped history with all three splits.

### R2 — Medium: replacement replay bypasses request-content validation

Location: `backend/src/services/os-account.service.ts`, `replaceOsPayment` priorReplacement branch.

Evidence: the branch returns an existing replacement selected by original payment ID and replacement idempotency key before checking its request hash or original void date/reason/key. The ordinary create-payment replay does check requestHash.

Impact: a changed correction request with reused keys receives success for an older operation, although its submitted amount/reason/date was not applied. This weakens the financial API's retry contract.

Mitigation: validate replacement hash and outer correction identity before replaying. Test exact replay and changed amount, reason, date and outer key cases against PostgreSQL.

### R3 — Medium: first-install rollback leaves newly created configuration behind

Location: `deploy.sh`, config backup and rollback function.

Evidence: rollback copies back files only if prior backups exist. If an initial install creates a bad nginx configuration, `nginx -t` fails but its newly enabled configuration remains on disk.

Impact: subsequent nginx reloads, including maintenance for unrelated sites, can fail until the invalid Lotaya configuration is removed. Existing prior-config installations are better protected.

Mitigation: record prior file and enabled-link existence, restore that state exactly, and only remove the precise newly created Lotaya targets when previously absent. Add failure-injection tests covering absence, existing files and failure after release switch.

## Performance, reliability and scalability observations

- Ledger summary uses database account grouping with existing user/hub/date checks and includes compensating entries. This avoids fetching historical journal rows solely to calculate balances.
- Domain guard verifies both local nginx TLS hostnames and rejects non-JSON readiness responses. It does not establish public DNS/ISP reachability, as its comment correctly states.
- Restore drill creates a new database and checks unfinished migrations and journal debit/credit equality. A successful script inspection is not evidence that a real backup was restored; compare resulting totals to a backup-time snapshot.
- Payment request retention is in memory. Reloading/unmounting loses uncertain requests; protection is limited to retries within the open mounted modal. Persisting unresolved attempts would extend protection across refresh.
- Deployment tests inspected mainly assert source strings. They cannot prove rollback recovery or backup restoration behavior.

## Positive controls

- Payment submit guard prevents concurrent clicks; uncertain responses retain the serialized request and lock amount editing.
- Summary results check safe integer bounds.
- OS account writes use server-side hub authorization, transactions and closed-cashbook checks.
- Draft restoration normalizes values, preserves existing rows on PDF apply and reports storage failure.
- Deployment serialization protects against concurrent symlink switches; TLS hostname checking uses OpenSSL hostname validation.
