## Security findings

### MED-SEC-01 — Public registration remains enabled and creates rider-role accounts

**Location:** `backend/src/routes/v1/auth.routes.ts`, `backend/src/services/auth.service.ts`  
**Evidence:** `POST /auth/register` remains unauthenticated; `register()` directly creates a user, relying on the schema default role `RIDER`. The specification requires authorized admin/invite registration unless explicitly enabled.  
**Impact:** Anyone who can reach the API can create accounts. Although rider data access requires a rider profile, this permits account/database abuse and creates identities outside the controlled onboarding process.  
**Mitigation:** Disable public registration by default in production; require an admin/invite token and audit every account creation.

### MED-SEC-02 — Authentication has no abuse controls

**Location:** `backend/src/app.ts`, `backend/src/routes/v1/auth.routes.ts`  
**Evidence:** There is no rate limiter, lockout/backoff, or login abuse telemetry in the middleware chain.  
**Impact:** The login endpoint is exposed to password guessing and resource exhaustion from bcrypt work.  
**Mitigation:** Add per-IP and per-identity throttling, bounded backoff, security events, and proxy-aware deployment configuration.

### LOW-SEC-03 — Cookie token boundary is not production hardened

**Location:** `backend/src/controllers/auth.controller.ts`, `backend/src/middleware/auth.ts`  
**Evidence:** Authentication accepts an `accessToken` cookie, but the cookie emitted by login is not marked `Secure`; write endpoints do not use CSRF tokens. The frontend also retains bearer tokens in `localStorage`.  
**Impact:** Depending on deployment and client choice, tokens can be exposed through non-TLS cookie transport, XSS, or cookie-based cross-site requests.  
**Mitigation:** Choose one hardened token boundary. For cookies use `HttpOnly; Secure; SameSite` plus CSRF protection and an explicit CORS policy; avoid localStorage for long-lived credentials.

## Financial integrity and operational correctness

### HIGH-FIN-01 — Linked-delivery fee and commission accounting is not invoked

**Location:** `backend/src/services/parcel.service.ts:6,91-140`, `backend/src/services/ledger.service.ts:102`, `backend/src/services/finance.service.ts`  
**Evidence:** `calculateLinkedDeliveryAmounts` and `assertBalancedLines` are imported into the parcel service but never used. On `DELIVERED`, the service always creates a per-parcel `DeliveryWay` using the parcel's full `deliveryFee`; it creates no linked collection or linked commission journal. Settlement arithmetic later substitutes the group fee only when every member is delivered, creating a separate calculation that is not backed by the ledger.  
**Failure scenario:** Two linked parcels with a 3,000 MMK base fee should recognize 4,000 MMK total. The status workflow records two ways at 3,000 MMK bases while no adjusted group journal exists; settlement recomputes 4,000 independently. Ledger, way-level commission, and settlement evidence disagree.  
**Impact:** Revenue and commission can be overstated, understated, or unauditable; reversal/idempotency guarantees do not cover the intended linked event.  
**Mitigation:** Post one idempotent, balanced group collection/fee/commission event when the group reaches its terminal delivered condition; allocate the snapshotted group commission to the single validated rider and derive settlement from those postings.

### HIGH-OPS-02 — Partial Return is unusable from both shipped clients

**Location:** `backend/src/validators/parcels.ts:20`, `frontend/src/pages/operations-page.tsx:19`, `mobile/app/parcel.tsx:27`  
**Evidence:** The server requires `collectionWallet` whenever `status` is `PARTIAL`. Neither the web operation nor the rider mobile request includes that field or offers wallet selection.  
**Impact:** Every Partial Return submitted from either client fails validation, so actual COD and the bounded OS offset are not recorded through the intended workflow.  
**Mitigation:** Require wallet selection in both UIs, include it in the DTO, and add web/mobile/API contract tests for Cash, KBZ Pay, Wave Pay, and zero collection.

### HIGH-OPS-03 — Rider mobile cannot progress an assigned parcel to a valid delivery outcome

**Location:** `mobile/app/(tabs)/index.tsx`, `mobile/app/parcel.tsx`, `backend/src/services/parcel.service.ts:8`, `backend/src/routes/v1/parcel.routes.ts`  
**Evidence:** Assigned parcels are normally in `ASSIGNED`; the mobile detail offers `DELIVERED`, `PARTIAL`, `FAILED`, and `REJECTED` immediately. The backend permits those outcomes only from `OUT_FOR_DELIVERY`, while there is no mobile action or API route to start a way / transition to `OUT_FOR_DELIVERY`.  
**Impact:** The core rider delivery workflow returns `INVALID_STATUS_TRANSITION` for normally assigned work.  
**Mitigation:** Implement the documented start-way endpoint/action, expose it in mobile, and cover the complete assigned → out-for-delivery → outcome flow.

### MED-FIN-04 — New financial source types remain invisible to scoped ledger readers

**Location:** `backend/src/services/ledger.service.ts:183-238`  
**Evidence:** Scope resolution recognizes only pickup, delivery collection, shortfall, return deduction, rider settlement, and reversals. It does not recognize `PARTIAL_RETURN_COLLECTION`, `OS_PARTIAL_RETURN_ADJUSTMENT`, or cashbook sources.  
**Impact:** Non-superadmin finance/auditor reports omit valid journal entries and cannot consistently investigate or reverse them, undermining hub-level reconciliation.  
**Mitigation:** Persist hub/resource scope on every journal entry and filter it in SQL; enumerate and test every source type until the schema is migrated.

## Reliability, deployability, performance, and scalability

### CRIT-DB-01 — Clean SQLite migration replay fails on a duplicate column

**Location:** `backend/prisma/migrations/20260811000000_linked_parcels/migration.sql`, `backend/prisma/migrations/20260811010000_zone_assignment_integrity/migration.sql`  
**Evidence:** The linked-parcels migration adds `Parcel.zoneId`; the immediately following migration adds `Parcel.zoneId` again. Replaying all SQL files in an in-memory SQLite database fails with `duplicate column name: zoneId`.  
**Impact:** A new environment cannot deploy the checked-in migration chain, and disaster recovery/bootstrap is blocked. Existing databases may report applied history while differing from the intended schema.  
**Mitigation:** Replace the unapplied migration safely or add a provider-supported corrective migration strategy, then prove an empty-database deploy and schema diff in CI.

### CRIT-DB-02 — PostgreSQL deploy command points at a SQLite migration history

**Location:** `backend/package.json`, `backend/prisma/migrations/migration_lock.toml`, `backend/prisma/migrations/**/*.sql`  
**Evidence:** `db:deploy:postgresql` uses `schema.postgresql.prisma` but the only migration directory is locked to `provider = "sqlite"` and contains SQLite-oriented SQL. No separate PostgreSQL baseline exists.  
**Impact:** Production PostgreSQL deployment is unsupported and will fail provider-history validation or execute incompatible DDL.  
**Mitigation:** Maintain and CI-test a PostgreSQL-native migration chain against an empty PostgreSQL database; do not share provider-specific SQL histories.

### LOW-PERF-01 — Parcel and ledger reporting remain fixed/unbounded in opposite directions

**Location:** `backend/src/services/parcel.service.ts:89`, `backend/src/services/ledger.service.ts:232-238`  
**Evidence:** Parcel listing silently caps at 100 without a cursor/total, while ledger reporting loads every matching entry and performs per-entry scope queries.  
**Impact:** Dispatch can omit eligible work, while ledger latency/query volume grows linearly and can exhaust memory/database capacity.  
**Mitigation:** Add explicit cursor pagination and totals to parcel APIs; persist journal hub scope, filter in SQL, and paginate ledger entries.
