# Lotaya ERP and Rider App Audit

**Audit date:** 2026-08-10 23:14:57 Asia/Yangon  
**Scope:** `backend/`, `frontend/`, `mobile/`, Prisma configuration, tests, package configuration, and `PROJECT_SPEC.md`  
**Method:** Static review of authentication, authorization, ledger mutations, validation, concurrency, resource usage, deployment configuration, and available validation commands. No production source code was modified.

## Executive Summary

The repository has a validated foundation, but it is not production-ready for a high-trust COD ledger. The highest risks are unsafe production defaults, non-idempotent money commands, a PostgreSQL migration path that still contains SQLite SQL, globally scoped cashbook state in a multi-hub system, and unbounded ledger reads. Existing focused tests cover selected business rules but do not establish database-backed authorization, reconciliation, concurrency, or deployment safety.

## Prioritized Findings

### AUD-001 — Critical — Production can start with a forgeable JWT secret

**Evidence:** `backend/src/config/env.ts:3` supplies `development-only-secret-change-me` when `JWT_SECRET` is absent. The same line silently defaults the database provider to SQLite and accepts an unvalidated provider string.  
**Impact:** A misconfigured production instance can allow token forgery and unintended local-database operation. This is an account-takeover and data-integrity risk.  
**Mitigation:** Fail closed when `NODE_ENV=production` unless a strong secret, explicit `DATABASE_PROVIDER`, and valid `DATABASE_URL` are present. Validate secret length/entropy and reject unknown providers at startup. Add startup configuration tests.

### AUD-002 — Critical — PostgreSQL deployment is not operationally safe

**Evidence:** `backend/prisma/schema.postgresql.prisma` changes only the datasource provider, while `backend/prisma/migrations/20260810120000_cashbook_controls/migration.sql` contains SQLite-specific `DATETIME`, `BOOLEAN`, and SQLite DDL. `db:deploy:postgresql` points Prisma at the same migration directory.  
**Impact:** A fresh PostgreSQL deployment can fail or diverge from the tested schema; production rollout and recovery are not reliable.  
**Mitigation:** Generate and apply a PostgreSQL-native migration history against a disposable PostgreSQL instance; keep provider-specific migration workflows explicit; add CI that runs `db:deploy:postgresql`, Prisma validation, and a smoke test against PostgreSQL before release.

### AUD-003 — Critical — Several financial commands are not retry-safe

**Evidence:** `backend/src/services/finance.service.ts:64-101` generates a random UUID for opening balances, wallet transfers, and adjustments. Repeating a request after a timeout creates another journal entry. The API has no idempotency-key contract.  
**Impact:** Mobile/network retries or operator retries can duplicate cash movements, violating the strict ledger requirement.  
**Mitigation:** Require a client-supplied idempotency key or stable business-event key, enforce a unique constraint, and return the original result for replay. Apply this to every money/status command, not only parcel collection and settlement paths.

### AUD-004 — Critical — Cashbook state is global, not hub-scoped

**Evidence:** `CashbookDay.businessDate` is globally unique in `backend/prisma/schema.prisma:139-153`; close and variance calculations in `backend/src/services/finance.service.ts:133-156` aggregate all settlements for a date without a hub dimension.  
**Impact:** In a multi-hub deployment, one hub can close or approve variance for another hub’s money, and reconciliation results can mix independent wallets. This breaks authorization and financial isolation.  
**Mitigation:** Add hub/wallet ownership to cashbook, settlement, journal, and report scope; enforce hub filters in every read/write; define whether close is per hub or organization-wide and test cross-hub denial cases.

### AUD-005 — High — Close/post concurrency can produce inconsistent day state

**Evidence:** `closeCashbook` checks `closedAt` and later updates the row inside a transaction, while posting paths separately call `assertCashbookOpen`. There is no compare-and-set/version predicate or explicit serializable transaction policy.  
**Impact:** Concurrent close, reopen, settlement, or posting requests can race, producing duplicate audit events or a close summary that omits a concurrent posting.  
**Mitigation:** Use a persisted version/state transition with conditional updates, appropriate PostgreSQL isolation/locking, and a single transactional guard for all postings. Add concurrent integration tests for close-versus-post, duplicate settlement, and reopen-versus-post.

### AUD-006 — High — Ledger reporting is unbounded and uses an N+1 scope query

**Evidence:** `backend/src/services/ledger.service.ts:198-217` loads all matching journal entries without pagination or a maximum date span, then calls `entryInScope` once per entry. `backend/src/services/finance.service.ts:190` also exposes an unfiltered account aggregation helper.  
**Impact:** Ledger growth can cause high memory use, long response times, database connection pressure, and request-level denial of service.  
**Mitigation:** Add bounded pagination and validated date-range limits, index `(businessDate, sourceType)` and scope keys, and replace per-entry scope checks with relational predicates or precomputed hub ownership. Stream or background large exports.

### AUD-007 — High — Authentication cookie and CSRF protections are incomplete

**Evidence:** `backend/src/controllers/auth.controller.ts:2` sets an `HttpOnly` cookie without `Secure`; mutating routes accept cookie authentication and there is no CSRF token/origin enforcement.  
**Impact:** In production over an incorrectly terminated or mixed HTTP path, tokens may be exposed; cookie-authenticated state-changing requests lack defense-in-depth against CSRF.  
**Mitigation:** Set `Secure`, use an explicit production cookie policy, preferably use a `__Host-` cookie, enforce trusted `Origin`/`Referer` or CSRF tokens for cookie-authenticated writes, and document bearer-only versus cookie clients.

### AUD-008 — High — Public registration violates the stated access model

**Evidence:** `backend/src/routes/v1/auth.routes.ts:2` exposes unauthenticated `POST /auth/register`; the schema defaults new users to `RIDER`. `PROJECT_SPEC.md` requires authorized admin/invite registration in production.  
**Impact:** Anyone can create accounts and consume resources; future role-management mistakes could turn this into privilege escalation.  
**Mitigation:** Disable public registration by default in production, or require an invite/admin authorization flow. Add rate limiting, email/phone verification hooks, audit events, and tests for registration policy.

### AUD-009 — High — Request validation is shallow for batch and parcel payloads

**Evidence:** `backend/src/routes/v1/operations.routes.ts:1` validates `parcels` only as an array; nested fields, string lengths, monetary bounds, tracking uniqueness, and address/contact limits are not validated at the API boundary. Parcel `reasonCode` and `note` are free text.  
**Impact:** Malformed or oversized payloads can reach transactional writes, cause data-quality failures, and increase storage/processing load. Free-text reason codes weaken reporting and controls.  
**Mitigation:** Add nested validators or a typed schema validator, strict unknown-field handling, bounded strings/arrays, nonnegative COD/fee checks, controlled reason-code records, and atomic import error reporting.

### AUD-010 — High — Account disablement and token revocation are delayed

**Evidence:** Access tokens last 15 minutes in `backend/src/utils/jwt.ts:3`; `requireAuth` verifies the token but does not query current user state. Logout only clears the client cookie/token in `backend/src/controllers/auth.controller.ts:6`.  
**Impact:** A stolen token remains usable until expiry, and logout does not revoke an already-issued bearer token.  
**Mitigation:** Add a session/token version or revocation record checked at the API boundary, or shorten access-token lifetime and add rotating refresh tokens with server-side revocation. Verify active status consistently for every sensitive command.

### AUD-011 — Medium — Mobile delivery updates are online-only and have weak lifecycle feedback

**Evidence:** `mobile/src/lib/api.ts:3` has no request timeout, retry queue, mutation idempotency key, or offline state. `mobile/app/parcel.tsx:1-2` posts directly and returns on success; the app has no protected-route UI tests or device-flow tests.  
**Impact:** Poor connectivity can cause duplicate taps, lost status attempts, ambiguous outcomes, and stale assignment views.  
**Mitigation:** Add an explicit mutation state machine, timeout/retry policy with idempotency keys, persisted offline queue where business rules permit, refresh/invalidation after status changes, and device-level tests for expiry and failed submissions.

### AUD-012 — Medium — Duplicate Expo Router trees create routing drift

**Evidence:** Both `mobile/app/(tabs)/` and the literal directory `mobile/app/'(tabs)'/` exist.  
**Impact:** The unused tree can confuse maintainers and future route generation, and changes may be applied to the wrong route set.  
**Mitigation:** Remove the duplicate literal directory and add a CI route-tree check or Expo export smoke test.

### AUD-013 — Medium — Required production controls are absent or unverified

**Evidence:** No ESLint configuration was found for the applications; `pino-http` is declared but not wired in `backend/src/app.ts`; there is no rate limiter, metrics/error monitoring, backup/restore configuration, real-time alert transport, or PostgreSQL deployment verification. `npm audit` could not reach the registry in this environment.  
**Impact:** Security regressions, operational incidents, sensitive-log leakage, and recovery failures may go undetected.  
**Mitigation:** Add CI lint/security/dependency checks, structured redacted logging, rate limits, metrics/alerts, encrypted backup and restore drills, deployment health checks, and an SSE/WebSocket or bounded polling alert strategy.

### AUD-014 — Medium — Dependency ranges are not reproducible enough for release control

**Evidence:** The three `package.json` files use many `latest` dependency ranges, even though lockfiles are present.  
**Impact:** Clean installs can change behavior or pull breaking/security-sensitive transitive versions when lockfiles are regenerated.  
**Mitigation:** Pin direct dependencies to reviewed versions, use lockfile-only CI installs, update on a controlled cadence, and record dependency/security review results.

## Validation Status

- Previously reported focused validation: backend 33 tests, frontend 6 tests, and mobile 4 tests passed; backend Prisma generation/validation, typecheck, and build passed before the latest PostgreSQL configuration change.
- The latest PostgreSQL change was explicitly reported as requiring full validation.
- A fresh combined validation command was started during this audit but interrupted before completion; this audit does not certify a new full-suite result.
- `npm audit` was attempted for all three apps but could not reach `registry.npmjs.org` because network DNS was unavailable.

## Release Recommendation

**Do not deploy to production.** Resolve AUD-001 through AUD-006 before handling real COD money. Then complete authorization/invite controls, validation, mobile retry behavior, PostgreSQL deployment testing, observability, backups, and database-backed/concurrency/E2E tests. Re-run the independent Test Reviewer and Verifier gates after remediation; use the Auditor again for the release candidate.
