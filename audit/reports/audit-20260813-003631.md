## Executive summary

Overall posture for this slice is **high financial / operational integrity risk**, driven less by missing authz than by a **broken status-correction contract** and **incomplete salary settlement**.

Client and server deny-by-default for Dispatch Queue edits align with the spec (Superadmin / Operations Manager / Dispatcher; hub-scoped). Parcel list pagination is bounded and surfaced in UI. Manifest generation enforces a 500-parcel hard cap. `resolveCommissionRateBps` correctly returns `0` for `SALARY` at delivery, linked collection, and settlement call sites. Township (and thus fee) edits are rejected after `BATCH_PICKUP_ADVANCE`.

Remaining urgent issues: (1) `MONEY_POSTED` still sees original journals after Finance posts `LEDGER_REVERSAL`, so the documented “reverse then correct” path cannot complete and commission source keys cannot be reused; (2) linked delivery/collection/commission journals use **group** `sourceId` and are invisible to the parcel-scoped gate; (3) salary riders no longer earn phantom commission, but settlement still never deducts `monthlySalary`; (4) client bulk status overrides remain non-atomic.

**Finding counts:** **1 Critical** · **3 High** · **3 Medium** · **2 Low**

## Findings (by severity)

### CRITICAL-OVERRIDE-01 — `MONEY_POSTED` gate does not honor ledger reversals; correction path dead-ends

**Risk:** Critical  
**Location:** `backend/src/services/parcel.service.ts` (`MONEY_POSTED_SOURCE_TYPES`, `overrideLeavesMoneyBearingStatus`, `updateStatus`); `backend/src/services/ledger.service.ts` (`reverseJournalEntry`)  
**Evidence:** Leaving `DELIVERED`/`PARTIAL` via ERP override queries `journalEntry.findFirst({ sourceId: parcelId, sourceType ∈ MONEY_POSTED_SOURCE_TYPES })` and throws `409 MONEY_POSTED` if any row exists. Finance reversals create a **new** `LEDGER_REVERSAL` entry whose `sourceId` is the **original entry id**; the original `RIDER_COMMISSION` / `PARTIAL_RETURN_*` / `DELIVERY_COLLECTION` row is retained for audit. The gate never checks for an existing reversal, so Finance can reverse and Ops still cannot change status. Separately, re-entering `DELIVERED` uses create-if-missing on the same `(sourceType, sourceId)` unique key—so even if the gate were relaxed, commission cannot be re-posted after a netting reversal without a new source-key scheme. Unit tests only cover the boolean helper, not reversal interaction.  
**Impact:** Spec/UI message (“Finance must reverse posted entries before correcting status”) is operationally false. Wrong money-bearing statuses become sticky after any commission/collection/partial posting; day-close, rider remittance, and OS offsets diverge from physical truth with no supported ERP correction sequence.  
**Mitigation:** Treat money as “still posted” only when net of unmatched originals (e.g. no `LEDGER_REVERSAL` for that entry). On successful reverse+override, clear or reverse delivery-way outcomes and partial COD fields in the same serializable transaction. For re-delivery after reversal, use a versioned source id or allow posting when net commission is zero. Add integration tests: deliver → commission → reverse → override to `FAILED`; deliver → reverse → re-deliver → commission again.

### HIGH-LINK-02 — Linked collection/commission journals bypass the parcel `MONEY_POSTED` gate

**Risk:** High  
**Location:** `backend/src/services/ledger.service.ts` (`postDeliveryCollection` uses `LINKED_DELIVERY_COLLECTION` / `LINKED_RIDER_COMMISSION` with `sourceId = group.id`); `backend/src/services/parcel.service.ts` (`MONEY_POSTED_SOURCE_TYPES` + parcel-id lookup)  
**Evidence:** Linked postings never create parcel-scoped `DELIVERY_COLLECTION` / `RIDER_COMMISSION` rows. Per-parcel `RIDER_COMMISSION` is skipped when `parcel.linkGroupId` is set. `MONEY_POSTED_SOURCE_TYPES` also omits `LINKED_*` types. An override leaving `DELIVERED` on a linked parcel therefore often finds **no** parcel-scoped money rows and proceeds, leaving group journals and way allocations intact.  
**Impact:** Ops can rewrite linked parcel status after Finance collected COD/fees and posted linked commission, orphaning wallets/payables relative to operational status and enabling incomplete-group settlement fall-through (see MEDIUM-SETTLE-05).  
**Mitigation:** When `linkGroupId` is set, gate on any unreversed `LINKED_*` journal for that group (and optionally block override until Finance reverses). Clear/reallocate ways atomically. Cover with regression tests.

### HIGH-SALARY-03 — `SALARY` commission is zeroed, but settlement still ignores `monthlySalary`

**Risk:** High  
**Location:** `backend/src/utils/commission.ts` (`resolveCommissionRateBps`); call sites in `parcel.service.ts`, `finance.service.ts` (`settlementWork`), `ledger.service.ts` (`postDeliveryCollection`); contrast `master-data.service.ts` (`normalizeRiderPayFields` persists `monthlySalary`)  
**Evidence:** `SALARY` → `0` bps is correctly applied at delivery posting, linked commission calculation, and settlement total recomputation for linked groups. `settlementWork` selects `payModel` / `commissionRateBps` but **never** reads `monthlySalary`; `calculateRiderSettlementAmounts` / remittance expected amount remain `cod + fees - commission` with no salary deduction or cashbook salary line. Spec §6.7 requires salary deducted from rider remittance with auditable cashbook visibility.  
**Impact:** Salary riders no longer receive phantom percentage commission (prior Critical mitigated), but hubs still expect full COD+fees remittance without salary offset—systematic underpayment of salary riders and incorrect day remittance / cashbook composition whenever `SALARY` or `SALARY_PLUS_PERCENTAGE` is configured.  
**Mitigation:** Apply salary policy in settlement/cashbook (period rules, pro-rate if needed), surface salary lines in preview/post, and add integration coverage for `SALARY` and `SALARY_PLUS_PERCENTAGE` settle days.

### HIGH-BULK-04 — Client-side bulk status overrides are non-atomic and amplify money side-effects

**Risk:** High  
**Location:** `frontend/src/pages/operations-page.tsx` (`applyStatusBulk`, `OPS_CORRECTION_NOTE`); `backend/src/services/parcel.service.ts` (`updateStatus`)  
**Evidence:** Multi-edit loops selected parcels with sequential `POST /parcels/:id/status` and a canned note `"Ops correction"`. There is no server bulk-status API, no all-or-nothing transaction across the selection, and no special confirmation for jumps to `DELIVERED` / money outcomes. Authz correctly limits UI (`canDispatchEdit`) and routes to Superadmin / Ops Manager / Dispatcher. On mid-loop `MONEY_POSTED` or conflict errors, earlier parcels may already have posted journals/ways.  
**Impact:** Partial application leaves mixed operational + ledger state; mistaken bulk `DELIVERED` can create many commission postings before failure; canned notes weaken attribution required by the spec.  
**Mitigation:** Server bulk status with explicit per-id results or atomic policy, require free-text override reasons for non-lifecycle transitions, confirm money-impacting targets, and cap selection size for override-to-delivered.

### MEDIUM-SETTLE-05 — Incomplete linked groups fall through to per-parcel fee/commission in settlement

**Risk:** Medium  
**Location:** `backend/src/services/finance.service.ts` (`calculateRiderSettlementTotals`)  
**Evidence:** Linked totals apply only when **every** member is `DELIVERED`; otherwise the reducer falls through and adds each remaining delivered parcel’s own `deliveryFee` + way `commissionAmount`. Link creation stores group `totalDeliveryFee` but does not rewrite member `deliveryFee` snapshots. After HIGH-LINK-02 overrides (or any mixed outcomes), settlement can charge full individual fees instead of the linked base+increment total (or omit group fee incorrectly depending on membership).  
**Impact:** Remittance and commission diverge from the linked-delivery fee policy whenever a linked group is operationally incomplete.  
**Mitigation:** For any parcel with `linkGroupId`, never settle individual fees; either require full-group delivery, settle only completed groups, or settle a defined incomplete-group policy with tests.

### MEDIUM-BATCH-06 — `GET /operations/batches` remains an unbounded hub dump

**Risk:** Medium  
**Location:** `backend/src/services/operations.service.ts` (`listBatches`); consumers: Dispatch Queue filters, All Batches, Finance batch picker  
**Evidence:** Returns all hub (or all) batches with `parcels: { select: { status: true } }` and no `take`/cursor. Dispatch Queue now paginates parcels (`page` + `pageSize` max 100, UI page size 100 with prev/next and `showingOfTotal`)—prior unbounded parcel-list concern is mitigated—but the batch list still grows with history.  
**Impact:** Latency and memory growth for busy hubs; Finance/Dispatch share the same heavy endpoint.  
**Mitigation:** Paginate or summarize batches (counts via aggregation); date-window defaults for operational UIs.

### MEDIUM-AUDIT-07 — Parcel field edits still lack attributable history

**Risk:** Medium  
**Location:** `backend/src/services/parcel.service.ts` (`updateParcel`)  
**Evidence:** Successful PATCH updates allowlisted fields only (good mass-assignment control) but writes no field-level audit / statusHistory analogue for COD (pre-advance), PII, township, or fee changes. Township/COD after advance are blocked (`ADVANCE_POSTED`)—prior fee-edit-after-advance High is mitigated for parcel PATCH.  
**Impact:** Pre-advance money/PII disputes and insider edits cannot be reconstructed from server history.  
**Mitigation:** Append immutable before/after audit events for money/PII field changes.

### LOW-ALERT-08 — Alerts deep-link is role-blind in the shell

**Risk:** Low  
**Location:** `frontend/src/components/app-shell.tsx` (`NavLink` → `/operations/batches#alerts`); `frontend/src/pages/batches-page.tsx` (hash scroll + `/operations/alerts` query); `backend/src/routes/v1/operations.routes.ts` (alerts require Superadmin / Operations Manager)  
**Evidence:** Bell is shown to every authenticated ERP user. Deep-link scroll works when hash is `#alerts`. Dispatchers/Finance/Auditors hitting the page will fail the alerts query (403) while batches may still load—no privilege escalation because acknowledge/list remain server-gated and hub-scoped (`take: 50`).  
**Impact:** Noisy errors / empty alerts UX for non-recipient roles; not a data exfiltration path.  
**Mitigation:** Hide bell / alerts section unless role ∈ {SUPERADMIN, OPERATIONS_MANAGER}; soft-handle 403.

### LOW-MANIFEST-09 — 500-parcel cap still materializes full PDF in memory

**Risk:** Low  
**Location:** `backend/src/services/operations.service.ts` (`buildManifestForRiders`); `backend/src/utils/manifest-pdf.ts`; validator riderIds max 50  
**Evidence:** Hard `parcels.length > 500` → `BATCH_TOO_LARGE` is enforced after `findMany` (hub-scoped for non-superadmin). PDF is still built fully in-process with customer PII/COD. Cap mitigates unbounded prior finding; residual peak memory ~O(500). No download audit log observed.  
**Impact:** Contained availability/PII export risk for compromised Dispatcher tokens within policy limits.  
**Mitigation:** Optional date filters, streaming, and audit log (actor, riderIds, parcelCount).

## Performance / reliability / scalability observations

- Parcel list: server `pageSize` max 100; Dispatch UI sends `page`/`pageSize=100` and shows totals—good.
- Manifest: rider cap 50 + parcel cap 500; in-memory PDF at the cap remains the main CPU/memory spike for Ops.
- `listBatches` unbounded embed of parcel statuses is the largest remaining list-scale risk in this slice.
- Single-parcel `updateStatus` uses serializable transactions with P2034 retry—strong for one id; forfeited by client bulk loops (HIGH-BULK-04).
- `updateParcel` uses `updateMany` with editable status set—status race TOCTOU from earlier audits remains mitigated.
- Alerts list capped at 50 unacknowledged—good; deep-link is UX-only.

## Positive controls verified

- Dispatch edit UI gated by `canDispatchEdit` (Superadmin / Operations Manager / Dispatcher); status/rider/edit controls disabled otherwise.
- Server: `PATCH /parcels/:id` and operations assign/manifest/link/reassign require the same ops roles; `POST /parcels/:id/status` allows Rider but `canOverrideStatus` denies rider non-lifecycle jumps; hub scope enforced in services.
- `resolveCommissionRateBps({ payModel: "SALARY", ... }) === 0` (even if stale bps present); covered in `business-rules.test.ts`; used from parcel delivery, finance settlement linked path, and linked collection posting.
- Township and COD edits rejected after `BATCH_PICKUP_ADVANCE` (`ADVANCE_POSTED`).
- Manifest rider uniqueness + max 50; parcel volume hard-capped at 500; bulk assign max 500.
- Parcel list pagination validators (`page` / `pageSize` ≤ 100) + UI pagination controls.
- Override note required for non-lifecycle transitions; reason codes validated for PARTIAL/FAILED/REJECTED.
- Alerts acknowledge restricted to Superadmin / Operations Manager with hub filter for non-superadmin.
- Operations nav split + `/operations` → `/operations/dispatch` query-preserving redirect matches spec direction.
