## Executive summary

The three reviewed changes address the previously reported weaknesses in the inspected code. Cookie-backed writes lacking a trusted source now fail; an IP attacking one username does not block that username from another IP; riders cannot read shop endpoints, and non-Superadmin batch history is hub-scoped and bounded. No Critical or High defect was confirmed in these changes. A limited availability risk remains for users sharing a network address.

## Findings

### AUD-01 — Low — Shared-IP login throttling can disrupt a whole office

**Location:** `backend/src/middleware/auth-rate-limit.ts:61-65`, `backend/src/middleware/auth-rate-limit.ts:72-73`.

**Evidence:** Login attempts increment an IP-wide counter before authentication. After 100 attempts in 15 minutes, all subsequent logins from that IP receive 429, even for different users. An attacker on the same NAT or office network could trigger this. The previous global username lock was removed, so users on other IPs remain able to sign in.

**Impact:** Temporary login disruption to staff sharing one public IP. This is bounded to a source network, not an account takeover or a global account lock.

**Mitigation:** Monitor 429 frequency after deployment. If shared-IP disruption occurs, put abuse controls at the edge and tune the per-IP threshold using observed traffic while retaining the source/account limit. Ensure any multi-replica deployment uses a shared or gateway limiter.

## Performance, reliability, and scalability observations

- The in-memory attempt store is bounded to 10,000 keys by default (`auth-rate-limit.ts:7-38`), limiting memory growth, but counters are process-local and reset on restart. The comment at lines 70-71 correctly calls out multi-replica requirements.
- `getShop` limits included batches to 100 (`master-data.service.ts:57`), avoiding the previous unbounded batch-history response. It has no pagination, so older batches cannot be retrieved through this endpoint; confirm callers do not need complete history.
- CSRF guard relies on the deployed `WEB_ORIGIN` allowlist (`csrf-origin.ts:14,20`). A wrong production value will reject legitimate browser writes. Browser smoke testing after deployment remains necessary.

## Positive controls verified

- Write requests carrying session cookies without Origin or Referer fail with 403; cross-site Fetch Metadata and untrusted Origin/Referer also fail (`csrf-origin.ts:11-28`). Explicit native/Bearer calls remain supported.
- Shop reads invoke live actor-scope checks, deny RIDER, and restrict non-Superadmin included batches to the actor's current hub (`master-data.service.ts:15-17,48-59`). The regression test covers rider denial and cross-hub batch exclusion (`backend/tests/api-contract.test.ts:30-52`).
- Rate-limit keys are hashed and include both source IP and identifier; the regression test confirms another IP can still log in (`backend/tests/security-infrastructure.test.ts`).
- Nginx proxies to a loopback API and app trust-proxy is set to one in production (`deploy/nginx/lotaya.mmds.site.conf:26-32`, `backend/src/app.ts`).
