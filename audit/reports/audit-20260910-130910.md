## Executive summary

**Overall risk posture: Critical / do not release the OS-account or financial unlink workflows as currently implemented.** The new and legacy OS payout systems can independently pay the same batch. The migration also recreates the original liability for previously settled batches without migrating settlement state. Separately, unlinking a delivered group leaves member COD receivables live and posts new individual receivables, corrupting rider outstanding balances. Batch finalization can race parcel insertion and permanently snapshot an incomplete obligation.

Finding counts: **Critical 2, High 3, Medium 4, Low 3**.

## Security and financial-integrity findings

### AUD-001 — Critical — Migration reopens already-settled OS liabilities

**Location:** `backend/prisma/migrations/20260906090000_os_account_subledger/migration.sql:15-18,61-64`; PostgreSQL counterpart `backend/prisma/migrations-postgresql/20260906090000_os_account_subledger/migration.sql:10-13,50-53`; `backend/src/services/os-account.service.ts:69-94`.

**Evidence:** Both migrations create an `OsBatchObligation` for every existing hub batch using the full sum of parcel COD and backfill return credits, but create no `OsAccountPayment`/`OsPaymentAllocation` from posted `OsSettlement` records. `accountRows` computes outstanding only as `originalCod - posted advances - returnedCod - OsPaymentAllocation`; legacy settlement payments are absent.

**Failure scenario:** A batch paid before deployment is migrated with its original COD liability and no payment allocation. Finance sees it as outstanding in the new panel and can pay the OS again.

**Impact:** Direct duplicate cash payout and a subledger that disagrees with the existing journal/settlement history.

**Mitigation:** Block deployment. Design a reconciled cutover that converts every active legacy settlement into per-batch opening allocations (including advances, returns, reversals, and amendments), or explicitly excludes fully settled batches. Run pre/post migration reconciliation proving per-shop/hub opening balance equality and abort on any difference.

### AUD-002 — Critical — New and legacy OS write paths can pay the same batch

**Location:** `backend/src/routes/v1/finance.routes.ts:22-24,28-45`; `backend/src/services/os-account.service.ts:124-153`; `backend/src/services/finance.service.ts:629-636,704-723`; `frontend/src/pages/settlement-workspaces.tsx:84,89-107`.

**Evidence:** New payment validation checks only the new obligation/allocation tables. Legacy settlement preview/post checks only active `OsSettlementBatch` links. Neither rejects a batch paid by the other system. Both write routes remain enabled, and the same Finance workspace renders `OsAccountsPanel` followed by the legacy settlement section.

**Exploit/failure scenario:** Finance posts a legacy OS settlement for a batch, then records a new OS-account payment for the same batch (or in the opposite order). Both pass their independent eligibility checks and both credit a wallet.

**Impact:** Duplicate OS payout, conflicting histories, and understated wallet balances. Per-request idempotency does not help because the duplicate events use different models and keys.

**Mitigation:** Choose one authoritative write path before release. Disable legacy mutation routes/UI after a reconciled cutover, or enforce one database-level batch-payment state/constraint consumed atomically by both paths. Add an integration test proving neither direction of cross-system duplicate posting is possible.

### AUD-003 — High — Financial unlink doubles delivered-member COD and changes fee economics

**Location:** `backend/src/services/parcel.service.ts:833-849,885-897`; `backend/src/services/operations.service.ts:478-519`.

**Evidence:** Linked COD receivable journals are keyed by each parcel ID (`LINKED_RIDER_RECEIVABLE_COD`). Unlink searches every listed source type only by the group ID, so those COD journals are never selected or reversed. It then posts a new `RIDER_RECEIVABLE_RECOGNITION` for each delivered parcel containing full COD plus that parcel's original full fee. Collection reposting, however, reallocates only the previously collected group-adjusted fee.

**Failure scenario:** Two delivered parcels with 3,000 MMK fees have a linked fee of 4,000 MMK. Unlink leaves both linked COD receivables live, adds both COD amounts again, and replaces the 4,000 MMK group fee/commission with 6,000 MMK of individual fee/commission even though only 4,000 MMK was collected.

**Impact:** Rider outstanding, revenue, commission, and cash reconciliation become materially wrong; the same COD obligation is counted twice.

**Mitigation:** Resolve live journals using the source-key convention for each type: group-keyed entries by group ID and COD entries by member parcel ID. Reverse matching `RiderReceivableRecognition` effects as well as journals. Preserve the already-agreed/collected economic fee when allocating post-unlink amounts, and add balance assertions covering COD, fee, commission, rider receivable, and wallet totals before/after unlink.

### AUD-004 — High — Parcel insertion can race finalization and escape the obligation snapshot

**Location:** `backend/src/services/operations.service.ts:297-318,331-347`; `backend/src/services/os-account.service.ts:39-47`.

**Evidence:** `bulkCreateParcels` reads `finalizedAt` before starting its insert transaction and never rechecks or conditionally locks/updates the batch inside that transaction. `finalizeBatch` separately marks the batch finalized and sums the parcels visible to its transaction into an immutable obligation.

**Failure scenario:** Bulk import reads `finalizedAt = null`; finalization commits an obligation; the import then inserts more parcels. The finalized batch contains COD that is absent from `originalCod`, and later edits are blocked by finalization.

**Impact:** OS liability is permanently understated and the batch detail no longer reconciles to its account.

**Mitigation:** Serialize add/finalize on the same database guard. Recheck `finalizedAt` in the parcel-insert transaction after acquiring a row/advisory lock, or use a database-enforced state-dependent insert strategy. Add a PostgreSQL concurrency test with a barrier around finalization and insert.

### AUD-005 — High — Organization/tenant isolation is not representable

**Location:** `backend/prisma/schema.prisma:9-33,82-93,160-168,184-201` (same structure in `schema.postgresql.prisma`); `backend/src/services/master-data.service.ts:15-25,36-50`; `backend/src/services/operations.service.ts:281-290`.

**Evidence:** The specified core `Organization` entity does not exist. Users, hubs, shops, batches, and financial records carry no organization key. Shops are global; every authorized operational user receives all active shops, and an Operations Manager can create a batch in their hub using any global shop ID.

**Exploit/failure scenario:** In a multi-organization deployment, a hub manager selects another organization's OS, creating liabilities and exposing that OS name/history through cross-contaminated operational data. No server predicate or database constraint can distinguish tenant ownership.

**Impact:** Cross-tenant metadata disclosure and financial misattribution; hub scoping cannot substitute for organization scoping when organizations own multiple hubs/shops.

**Mitigation:** Do not enable multi-tenant use until `organizationId` ownership and composite scope constraints exist on hubs, users, shops, batches, journals, and OS subledger records. Centralize actor scope as organization + allowed hubs and test cross-organization IDs on every read/write route.

### AUD-006 — Medium — Replace replay accepts a different correction payload

**Location:** `backend/src/services/os-account.service.ts:181-190`.

**Evidence:** `replaceOsPayment` returns `priorReplacement` based only on original ID plus replacement idempotency key. It bypasses `createPayment`'s request-hash comparison and does not verify correction business date/reason, selected batches, wallets, note, reference, or shop.

**Failure scenario:** A retry reuses the replacement key with changed wallets/batches. The API reports success and returns the previous replacement rather than `409 IDEMPOTENCY_CONFLICT`, causing the caller to believe the correction it submitted was applied.

**Impact:** Silent reconciliation mismatch and unsafe recovery behavior after ambiguous client/network retries.

**Mitigation:** Persist/hash the complete replace request and compare it before replay, including void metadata and replacement payload; return conflict on any difference.

### AUD-007 — Low — Saved settlement drafts are hub-shared despite creator fields

**Location:** `backend/src/services/finance.service.ts:920-925,928-955`; `backend/prisma/schema.prisma:591-610`.

**Evidence:** Draft rows record `createdBy`/`updatedBy`, but list is filtered only by hub/shop and update authorizes only by hub. Any Finance or Operations Manager in that hub can read and overwrite another user's draft.

**Impact:** Draft adjustment rationale and provisional amounts are not private; accidental cross-user edits are possible, though optimistic versioning and audit rows limit silent loss.

**Mitigation:** Explicitly decide whether drafts are personal or shared. If personal, enforce creator ownership with an explicit share/transfer mechanism; if shared, document that policy and surface creator/editor identity in the UI.

## Performance, reliability, and scalability observations

### AUD-008 — Medium — OS statement report suppresses legacy totals when any obligation exists

**Location:** `backend/src/services/reports.service.ts:293-306`.

**Evidence:** One `OsBatchObligation` in the queried hub/shop makes `active` legacy settlements an empty array. All legacy component sums become zero, and the report selects the OS-account source wholesale rather than merging/cutover-partitioning records.

**Failure scenario:** During migration/coexistence, a hub with one new obligation loses every legacy settlement from report totals, including gross COD, advances, returns, fees, adjustments, and net. Raw settlement rows are still returned, so detail and totals disagree.

**Impact:** Incorrect financial statements and audit reconciliation.

**Mitigation:** Report from a reconciled canonical event model or partition by batch cutover state; never switch an entire hub/shop based on `count > 0`. Add mixed legacy/new fixtures and total-to-journal reconciliation tests.

### AUD-009 — Medium — OS-account reads are unbounded and contain quadratic aggregation

**Location:** `backend/src/services/os-account.service.ts:50-104,195-203`.

**Evidence:** Account list loads every obligation/batch, payment allocation, return credit, advance journal and credit allocation for a hub without pagination. In memory, every obligation filters all return credits; every shop filters all batch rows; advance entries search the batch ID array. History returns all payments, returns and legacy settlements without a cap.

**Impact:** Query size, memory, CPU, and response payload grow with the complete hub history; a normal authenticated request can become slow or exhaust a worker as data accumulates.

**Mitigation:** Aggregate balances in SQL, page batch detail/history, cap date ranges, and replace dynamic `2N` source-ID OR predicates with a relational batch key or indexed canonical source reference.

### AUD-010 — Medium — Superadmin cannot load the new OS-account panel

**Location:** `backend/src/services/os-account.service.ts:27-36`; `frontend/src/components/os-accounts-panel.tsx:29-31`.

**Evidence:** The backend requires Superadmin to provide `hubId`, but the panel's initial `/finance/os-accounts` request sends no hub and provides no hub selector. Non-superadmin Finance users work because their hub is inferred.

**Impact:** The fully authorized Superadmin workflow fails with `HUB_REQUIRED`, blocking oversight/correction in the new UI.

**Mitigation:** Add an explicit Superadmin hub selector and include it in account/list/history/write queries, or provide an intentional bounded organization-wide summary endpoint.

### AUD-011 — Low — Overdue-unsent query lacks a matching batch index

**Location:** `backend/src/services/operations.service.ts:140-170`; `backend/prisma/schema.prisma:184-201,334-339`.

**Evidence:** The query filters parcel status joined to `Batch.hubId + pickupDate`, counts the full result, and sorts by related pickup date. Parcel has a status index, but Batch has no `(hubId, pickupDate)` index; its only shown uniqueness is `(shopId, pickupDate)`.

**Impact:** The dashboard and Dispatch Queue each issue this count/list path, which can devolve into large scans/sorts as historical parcels grow.

**Mitigation:** Add and validate a production-query-plan index beginning with `Batch(hubId, pickupDate)` and benchmark the join; consider serving count and first page from one purpose-built summary/query.

### AUD-012 — Low — Frontend role guards route users into pages with denied dependencies

**Location:** `frontend/src/lib/role-access.ts:3-9`; `frontend/src/pages/operations-page.tsx:201-240`; `backend/src/routes/v1/operations.routes.ts:11-12`; `backend/src/services/master-data.service.ts:15-25`; `frontend/src/pages/settlement-workspaces.tsx:47-54`; `backend/src/routes/v1/finance.routes.ts:27-40`.

**Evidence:** Auditor is allowed into Dispatch and Finance, but those pages eagerly call endpoints that exclude Auditor (`operations/batches`, overdue-unsent, full master data, rider outstanding, and settlement drafts). Server-side mutation restrictions remain intact, but the client generates multiple expected 403s and partial panels.

**Impact:** Broken read-only experience, noisy logs/alerts, unnecessary traffic, and misleading empty/error states.

**Mitigation:** Gate queries and panels by the same centralized capability map used for routes, and test each role's page with real endpoint permissions.

## Positive controls verified

- New OS payment/void/replace mutations are server-role-gated to Superadmin/Finance and re-resolve the active user's persisted role/hub.
- Non-superadmin account reads and writes reject an explicit mismatched hub.
- Payment, void, and replacement work execute in database transactions; payment/replace request `Serializable` isolation.
- Wallet inputs are non-negative integers; payment amounts are bounded by the new subledger's computed payable; positive wallet movement checks cashbook day state.
- Payment journals with wallet movement are balanced; void reverses original journal lines in the same transaction.
- New-payment idempotency stores a normalized request hash and rejects mismatched direct payment replays.
- Rider mobile now defaults to all assignments and paginates through every API page (`mobile/src/lib/api.ts:133-148`), removing the former first-page/date-default incompleteness.
- Client mutation affordances and server mutation routes retain deny-by-default role checks for Dispatcher/Finance/Auditor boundaries; server checks, not UI hiding, remain authoritative.

## Unverified areas, limitations, and follow-up

- PostgreSQL migrations were not applied to a clone of production data; locking duration, integer overflow, and exact historical balance drift remain unmeasured.
- No concurrency harness was run for finalization/import or same-key payment/void/replace races.
- No full lint/build/test suite or mobile device runtime test was run in this time-boxed audit.
- The remaining teardown FK should be identified before relying on the linked-parcel suite in CI.
- Before release, create a sanitized production-like migration rehearsal with per-hub/shop/batch reconciliation to ledger balances, then run explicit tests for dual-path payout, mixed reporting, unlink balance preservation, and concurrent finalize/import.
