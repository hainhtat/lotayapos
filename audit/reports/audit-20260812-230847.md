## Executive summary

Overall posture for this slice is **elevated operational/money risk**. Role gates and field allowlists for parcel edit and fee updates are present, and bulk assign retains hub-scoped optimistic concurrency. However, parcel edits lack status-conditioned writes and audit history, COD can change after batch advances without ledger compensation, and `remainingToOs` clamps negatives contrary to `PROJECT_SPEC.md`. Delivery-fee bulk update is authorized for Operations Manager with national blast radius and no fee-change audit trail.

**Finding counts:** 0 Critical · **2 High** · **3 Medium** · **2 Low**

## Findings (by severity)

### HIGH-PARCEL-01 — Parcel edit TOCTOU: status gate is check-then-write without optimistic lock

**Risk:** High  
**Location:** `backend/src/services/parcel.service.ts` (`updateParcel`)  
**Evidence:** Editable status is enforced only on a prior `findFirst` (`editableStatuses` = `CREATED` | `PICKED_UP`). The subsequent `prisma.parcel.update({ where: { id } })` does **not** constrain `status` (contrast `updateStatus` / `bulkAssignParcels`, which use `updateMany` with status/rider predicates). Concurrent `POST /operations/parcels/bulk-assign` can move the parcel to `ASSIGNED` between the read and write.  
**Impact:** COD, address, township, and delivery fee can change on an already-assigned parcel. Dispatch manifests, rider collections, and later commission/fee recognition can disagree with the values present at assignment.  
**Mitigation:** Perform the update with `updateMany` where `id` and `status ∈ {CREATED, PICKED_UP}` (and optionally `riderId: null`); treat `count !== 1` as `409 PARCEL_NOT_EDITABLE` / conflict. Prefer the same serializable/retry pattern used for status transitions. Add a concurrency regression test.

### HIGH-MONEY-02 — COD/fee edits after batch advance plus clamped `remainingToOs` hide receivables

**Risk:** High  
**Location:** `backend/src/services/parcel.service.ts` (`updateParcel`); `backend/src/services/operations.service.ts` (`getBatchDetail` → `remainingToOs = Math.max(0, totalCod - batch.advancePaid)`); advance posting in `postPickupAdvances`  
**Evidence:** Dispatchers/ops may patch `codAmount` and township-derived `deliveryFee` while status remains `CREATED`/`PICKED_UP`, including after `batch.advancePaid` is set and after immutable `BATCH_PICKUP_ADVANCE` journal posting. Batch detail then recomputes `totalCod` from live parcel COD and clamps remaining with `Math.max(0, …)`. Spec §4: advances may exceed COD; **“Negative balances are allowed as receivables, never silently netted away.”** Spec also requires monetary changes to be attributable and corrections via reversals, not silent operational rewrites.  
**Impact:** Operators can reduce COD below posted advance; UI/API show `remainingToOs = 0` instead of an OS receivable/over-advance. Posted wallet/OS advance journals are unchanged, so ERP settlement views diverge from the ledger without an audit/reversal path.  
**Mitigation:** Block COD (and optionally township/fee) edits once a batch advance journal exists, or require Finance-authorized compensating entries. Return signed `remainingToOs = totalCod - advancePaid` (allow negative). Surface over-advance explicitly in batch detail UI. Record actor/timestamped parcel field audit for money fields.

### MEDIUM-FEE-03 — Delivery-fee bulk update: national blast radius, zero fee, no audit

**Risk:** Medium  
**Location:** `backend/src/routes/v1/master-data.routes.ts`; `backend/src/services/master-data.service.ts` (`updateTownshipDeliveryFees`); `frontend/src/pages/settings-page.tsx`  
**Evidence:** Any `SUPERADMIN` or `OPERATIONS_MANAGER` may set one `deliveryFee` (integer ≥ 0) on up to 500 township IDs with no hub/geo constraint, no confirmation token, and no `locationImportAudit`-style record. Existing parcels keep snapshotted fees (not retroactive), but all **new** parcels in those townships inherit the new fee (including `0`). Role check lives in the service (route is auth-only); that is correct but fee changes remain unaudited.  
**Impact:** Compromised or mistaken Ops Manager credentials can zero or inflate fees nationwide, immediately affecting new intake COD/fee economics and rider commission bases. Incident response cannot reconstruct who changed which townships/fees.  
**Mitigation:** Restrict bulk fee writes to Superadmin (or dual-control), require non-zero policy or explicit `allowZero` flag, persist an audit row (actor, before/after, township set, timestamp), and optionally require a confirmation phrase for updates spanning many regions. Add integration tests for authz deny paths (`FINANCE`, `DISPATCHER`, `RIDER`).

### MEDIUM-AUDIT-04 — Parcel PATCH has no attributable history for money/PII changes

**Risk:** Medium  
**Location:** `backend/src/services/parcel.service.ts` (`updateParcel`); contrast `statusHistory` usage in `updateStatus` / assignment flows  
**Evidence:** Successful edits update parcel columns only. No `statusHistory`, field-level audit, or journal note records prior COD/fee/customer values. Spec requires money and overrides to be attributable, timestamped, and auditable.  
**Impact:** Disputes over wrong COD sticker/manifest values, OS settlement mismatches, or insider tampering cannot be reconstructed from server history.  
**Mitigation:** Append an immutable audit event (or status-history note with structured before/after JSON) on every successful PATCH that touches `codAmount`, `deliveryFee`, `townshipId`, or customer identity fields.

### MEDIUM-VALID-05 — Missing upper bounds and incomplete behavioral tests for new money endpoints

**Risk:** Medium  
**Location:** `backend/src/validators/parcels.ts` (`codAmount` min 0, no max); `backend/src/routes/v1/master-data.routes.ts` (`deliveryFee` min 0, no max); `backend/tests/api-contract.test.ts`  
**Evidence:** Contract tests only assert validation **rejection** (negative COD, empty townshipIds / negative fee, missing rider username). There are no success-path, authz, concurrency, or advance-posted-guard tests for parcel edit / fee bulk update / `remainingToOs`. Extremely large integers are accepted by validators.  
**Impact:** Accidental or malicious oversized COD/fee values distort batch totals and manifests; regressions in race/authz guards can ship unnoticed.  
**Mitigation:** Cap COD and delivery fees to a documented operational maximum; add focused tests for happy path, role denials, post-advance edit denial, optimistic status conflict, and signed remaining-to-OS.

### LOW-UI-06 — Wallet `—` for balance `0` conflates empty ledger with true zero

**Risk:** Low  
**Location:** `frontend/src/pages/finance-page.tsx` (`formatBalance`); `frontend/src/i18n/locales/*/common.json` (`noBalance`)  
**Evidence:** `walletBalance` defaults missing accounts to `0`, then renders `t("noBalance")` (`—`) whenever balance === 0.  
**Impact:** Operators may not distinguish a reconciled empty wallet from a missing ledger account row after filter/date changes; low financial integrity impact but weak reconciliation UX.  
**Mitigation:** Show `0 MMK` for an explicit zero balance; reserve `—` for absent account lines only.

### LOW-UX-07 — Dark mode grid text fix is cosmetic only (no security defect)

**Risk:** Low  
**Location:** `frontend/src/pages/batch-detail-page.tsx` (`cell` includes `dark:text-slate-100`)  
**Evidence:** Input contrast in dark theme is improved; no authz or money path involved.  
**Impact:** None for security/money; residual accessibility depends on full contrast QA.  
**Mitigation:** Keep as-is; cover with a brief visual regression note in UI QA.

## Performance / reliability / scalability observations

- `getBatchDetail` loads all parcels for a batch without pagination; acceptable for current batch sizes, but large imports (up to 500) increase payload and edit-list cost.
- Fee settings load all townships when `districtId` is omitted; Myanmar-scale master data is manageable but unbounded growth should eventually paginate/filter server-side.
- Assign-and-download generates a **single-page** PDF (`manifest-pdf.ts`); large selections may clip content off-page (reliability), while assignment itself remains transactional with per-parcel conflict detection.
- Bulk assign bounds (1–500) and unique ID checks are sound; frontend eligibility mirroring reduces avoidable 409s.

## Positive controls verified

- Parcel PATCH route uses `requireAuth` + `requireRoles(SUPERADMIN, OPERATIONS_MANAGER, DISPATCHER)` and repeats role checks in service with hub scope via `buildParcelScope`.
- Service updates only an explicit field set (`orderId`, customer fields, `codAmount`, `townshipId`/`deliveryFee`, `zoneId`); Prisma mass-assignment of `status` / `riderId` / `advanceAmount` via body extras is not performed.
- Linked parcels cannot be edited (`PARCEL_LINKED`); zone must match township + batch hub.
- Rider create requires `username` (`^[A-Za-z0-9._-]{3,50}$`), normalizes case, and rejects email/username collisions.
- Zone create requires `townshipId` and validates township existence + hub scope for non-superadmin.
- Delivery-fee updates require Ops Manager/Superadmin and reject unknown township IDs.
- Bulk assign enforces hub match (actor/rider/parcels), eligibility, and optimistic `updateMany` conflict handling; PDF download uses `apiRaw` with JSON error parsing on failure.
- Backend and frontend `tsc --noEmit` succeed for this tree.
