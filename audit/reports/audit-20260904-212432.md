## Scope and exclusions

Reviewed `PROJECT_SPEC.md`, root `AGENTS.md`, backend API/auth/authorization, Prisma SQLite and PostgreSQL schemas and new migrations, parcel and financial workflows, reporting/CSV, local PDF manifest parsing/generation, frontend session/routing and report surfaces, mobile auth/storage/API lifecycle, package scripts, systemd, nginx, `deploy.sh`, public `/app` page, and Rider APK publication metadata.

No production services, remote databases, network endpoints, migrations, dependency installs, APK execution/signature tools, load tests, or destructive actions were used. Production code and tests were not modified. Existing secrets were not inspected or reproduced.

## Executive summary

**Overall risk posture: High; do not treat the current deployment path as production-ready without addressing the High findings.** The application has meaningful positive controls: server-side role and hub checks, active-user/token-version verification, hashed rotating refresh tokens, serializable transactions on the highest-risk finance mutations, unique source/idempotency constraints, closed-day gates, bounded PDF uploads/pages/concurrency, and local-only PDF parsing.

The primary release blockers are transport/database TLS defaults and a non-atomic deployment workflow that changes the database before proving the new application build can run. Financial posting is generally transactionally protected, but salary deductions are represented differently from the explicit source-of-truth accounting rule. Report endpoints also permit unbounded materialization and CSV formula injection. Release publication calculates a checksum but does not establish that the APK is the intended, trusted, correctly versioned build.

## Security findings

### SEC-01 — High — Fresh deployments expose an HTTP-only public site

**Location:** `deploy/nginx/lotaya.mmds.site.conf:3-6`, `deploy.sh:63-68`, `backend/src/controllers/auth.controller.ts:6-15`

**Evidence:** The checked-in nginx site listens only on port 80 and has no redirect to HTTPS. `deploy.sh` preserves an existing TLS vhost if one happens to exist, but installs this HTTP-only configuration on a fresh host. The API returns access and refresh credentials and also sets production cookies with `Secure`.

**Failure/exploit scenario:** On a fresh or rebuilt host, credentials and operational/financial data can traverse plaintext and be intercepted or modified. Browser `Secure` cookies will not be sent over HTTP, breaking the intended refresh flow even when a bearer token initially works.

**Impact:** Account/session compromise, parcel/financial data disclosure or manipulation, and an unusable browser refresh session on the default deployment.

**Mitigation:** Provision TLS as a mandatory deployment precondition; install an explicit port-80 redirect and a reviewed 443 server with HSTS. Fail deployment if a valid TLS configuration/certificate is absent, and validate the effective nginx config rather than merely searching for `listen 443` in an arbitrary existing file.

### SEC-02 — High — PostgreSQL certificate verification is disabled by default

**Location:** `backend/src/config/postgres-pool.ts:3-6,19-24`

**Evidence:** Every PostgreSQL connection uses TLS, but `rejectUnauthorized` is false unless `DATABASE_SSL_REJECT_UNAUTHORIZED=true` is explicitly configured. The comment documents false as the default for poolers.

**Failure/exploit scenario:** A network-positioned attacker or compromised DNS/routing layer can present an untrusted certificate and intercept database credentials and all operational/financial traffic.

**Impact:** Full database confidentiality and integrity compromise.

**Mitigation:** Make certificate verification the production default and require an explicit, narrowly documented break-glass override. Configure the provider CA correctly and add a startup assertion/test for production.

### SEC-03 — Medium — CSV exports permit spreadsheet formula injection

**Location:** `backend/src/controllers/reports.controller.ts:11-13,30-44`

**Evidence:** CSV quoting only doubles quotes. It does not neutralize cells beginning with `=`, `+`, `-`, `@`, tab, or carriage return. Exports include user/import-controlled fields such as order ID, tracking number, rider name, and shop name.

**Failure/exploit scenario:** A dispatcher imports a formula-shaped order/customer reference; a finance user later opens the export in Excel/LibreOffice and the formula executes (for example, external-link exfiltration or a deceptive action).

**Impact:** Workstation-side data exposure or social engineering across a trust boundary.

**Mitigation:** Prefix dangerous text cells with an apostrophe (or use a proven CSV serializer with formula hardening), retain ordinary numeric cells as numeric, and add malicious-cell regression tests.

### SEC-04 — Medium — Authentication throttling is process-local, bypassable, and retains keys indefinitely

**Location:** `backend/src/middleware/auth-rate-limit.ts:4-30`; `backend/src/app.ts:3`

**Evidence:** Login/refresh counters live in a module-level `Map`, are keyed only by proxy-derived IP, reset on restart, are independent across instances, and expired keys are removed only when the same address returns.

**Failure/exploit scenario:** Distributed attempts, process restarts, or horizontal replicas bypass the advertised limit. High-cardinality source addresses cause continuous map growth. A single NAT can also lock out many legitimate riders.

**Impact:** Increased credential-stuffing exposure, denial of service to shared-IP users, and slow memory growth.

**Mitigation:** Use a bounded shared limiter (Redis/database/gateway) combining normalized account and IP/device signals, periodic eviction, trusted-proxy configuration, and monitoring.

### SEC-05 — Medium — Browser auth responses expose refresh tokens to JavaScript unnecessarily

**Location:** `backend/src/controllers/auth.controller.ts:23-30,39-48`; `frontend/src/app/auth.tsx:46-55`

**Evidence:** Login and refresh always serialize both access and refresh tokens in JSON even though the web client uses the HttpOnly refresh cookie and ignores the JSON refresh token.

**Failure/exploit scenario:** Any successful frontend XSS can read a long-lived refresh token from the login/refresh response, widening compromise beyond the in-memory access token lifetime.

**Impact:** Longer-lived session theft if another frontend defect enables script execution.

**Mitigation:** Split native and browser token delivery explicitly. For browser-origin requests, return no refresh token in JSON; retain the body token only for an authenticated native-client policy or dedicated endpoint.

### SEC-06 — Low — Public APK metadata is not presented as a verifiable trust signal

**Location:** `deploy/publish-rider-app.sh:16-25`; `deploy/app/index.html` release-fetch script

**Evidence:** Publication computes SHA-256 into `version.json`, but the public page displays only version/size and does not show the checksum or signing identity. The publication check trusts a mutable plaintext `.version` sidecar and does not inspect the APK manifest version or verify its Android signing certificate.

**Failure/exploit scenario:** An incorrect or replaced APK can be published as long as the sidecar text matches. Riders have no visible out-of-band value to authenticate the download.

**Impact:** Weak release provenance and detection; not by itself a remote compromise because filesystem write access is already required.

**Mitigation:** Build/sign in CI, verify the APK package/version/signing certificate before publishing, publish an immutable signed release manifest, and expose the checksum/signing fingerprint on the download page.

## Financial integrity findings

### FIN-01 — Medium — Salary deduction posting contradicts the specified ledger representation

**Location:** `PROJECT_SPEC.md` §§4, 6.7, 7; `backend/src/services/finance.service.ts:1932-1937,2014-2025`; `backend/src/services/reports.service.ts:76-80`

**Evidence:** The specification requires the salary deduction to appear in the rider settlement journal as visible `RIDER_RECEIVABLE` credit/debit lines and says not to invent a different account treatment. Implementation creates a separate `RIDER_SALARY_DEDUCTION` journal debiting `RIDER_COMMISSION_PAYABLE` and crediting `RIDER_RECEIVABLE`; the `RIDER_SETTLEMENT` journal only credits the actual remittance. Profit reporting then interprets that commission-payable debit as salary cost.

**Failure scenario:** Auditors following the specified settlement journal cannot reconcile salary from that journal, while the payable account is used as an implicit salary expense. Reports and downstream accounting exports inherit a semantic treatment not approved by the source of truth.

**Impact:** Misclassification and audit/reconciliation ambiguity, even though the entry is balanced and the rider outstanding arithmetic is reduced.

**Mitigation:** Align implementation and tests with the current spec: include the explicit before-salary credit and salary-deduction debit in the settlement journal (or obtain a deliberate finance-policy/spec change through the required spec-maintainer flow). Validate the profit accounting treatment with finance before release.

## Performance, reliability, and scalability findings

### REL-01 — High — Deployment is non-atomic and migrates the database before build validation

**Location:** `deploy.sh:23-57,61-75`

**Evidence:** Deployment pulls directly in the live repository, installs dependencies, runs `prisma migrate deploy`, then compiles and rsyncs with `--delete` into live directories. It restarts the service without a staged release, preflight test, post-restart readiness check, or rollback. Database migration occurs before TypeScript/frontend build success is known.

**Failure scenario:** A compile failure leaves the database migrated while the old binary remains; rsync/restart failure can leave mixed assets or downtime; an application that starts but cannot serve readiness is still reported as successfully deployed.

**Impact:** Avoidable outage, schema/binary incompatibility, and difficult rollback of financial-system releases.

**Mitigation:** Build/test into a versioned release directory first, back up/verify restore posture, classify migrations for backward compatibility, switch an atomic symlink, restart and require `/api/v1/health/ready`, then retain/automate rollback. Do not mutate the live checkout as the release mechanism.

### PERF-01 — Medium — Detailed reports have no date-span, row, pagination, or response-size limits

**Location:** `backend/src/validators/reports.ts:3-27`; `backend/src/services/reports.service.ts:120-155,175-187,206-216,229-264`; `backend/src/controllers/reports.controller.ts:12-13`

**Evidence:** Validators check only date syntax. Each report performs an unbounded `findMany`, often including nested rows/journal lines, then builds the complete JSON or CSV in application memory with array maps and string joins.

**Failure scenario:** An authorized user requests a multi-year range. The API and database allocate/query all matching status history, ways, settlements, or journal lines; CSV creates additional full-memory arrays and one large string.

**Impact:** Long database occupancy, process memory exhaustion, event-loop stalls, 120-second proxy timeouts, and degraded service for delivery/finance operations.

**Mitigation:** Enforce role-appropriate maximum spans and row caps, paginate JSON, stream CSV from a cursor/batches, move large exports to an asynchronous job with explicit limits, and add query/index/load-envelope tests.

### REL-02 — Medium — Shutdown can disconnect Prisma before in-flight HTTP work finishes

**Location:** `backend/src/server.ts:1-2`; `deploy/systemd/lotaya-api.service`

**Evidence:** Signal handling calls `server.close()` without awaiting its callback/promise and immediately awaits `prisma.$disconnect()`. There is no readiness drain state or bounded forced-shutdown logic.

**Failure scenario:** A deploy signal arrives during a settlement, report, or PDF request; database resources are disconnected while accepted requests are still running.

**Impact:** Failed requests during routine deployments and uncertain client retry behavior around high-value operations.

**Mitigation:** Mark readiness false, stop accepting requests, await server close and in-flight completion, then disconnect Prisma with a bounded timeout and explicit exit status. Idempotency remains necessary for client retries.

### PERF-02 — Low — Frontend ships a large single initial JavaScript chunk

**Location:** `frontend/src/app/router.tsx:1-12,33-57`; production build output

**Evidence:** All primary pages are eagerly imported. The verified production build emitted a 737.71 kB minified initial chunk (197.75 kB gzip), triggering Vite's >500 kB warning.

**Impact:** Slower startup and higher memory/data use, particularly on rider/low-end mobile connections, even for the public Rider app page.

**Mitigation:** Lazy-load role/page routes and large report/finance workspaces, then enforce a bundle budget in CI.

## Positive controls verified

- JWT verification pins issuer, audience and HS256; authenticated requests re-read the active user, persisted role and token version.
- User privilege/active/password changes revoke refresh tokens and increment token version; last-superadmin changes have serializable/advisory-lock protection.
- Login performs a dummy bcrypt comparison and returns a common invalid-credentials response, reducing account enumeration.
- Refresh tokens are random, hash-only at rest, rotated transactionally, and reuse revokes the user's refresh-token family.
- Routes are role-gated server-side and reviewed parcel/finance/report flows generally apply hub/rider scope after the role check.
- High-risk parcel and settlement mutations use transactions, optimistic conditions/idempotency keys, unique journal source keys, cashbook-open checks and serializable isolation where needed.
- Ledger construction validates balanced integer lines in the shared ledger helper; reviewed direct-created business entries were balanced by construction.
- PDF import requires authorization and hub scope, limits input to 10 MB/50 pages, rejects non-PDF/scanned input, disables PDF JavaScript evaluation, caps two concurrent parses per process, and removes private temporary files.
- Mobile native tokens use Expo SecureStore when available; production builds require an explicit API base URL.
- Readiness performs a database query at `/api/v1/health/ready`.

## Operational blockers and release observations

- `releases/lotaya-rider.apk` exists locally and hashes to `c5a354b1…0ad`, but it is git-ignored and `releases/lotaya-rider.version` is absent. The current publication script therefore deliberately keeps whatever APK/metadata is already on the server. This is an external release-input blocker: version `0.1.1` cannot be newly published by this checkout until a trusted, version-matched artifact and sidecar are supplied.
- The repository contained concurrent uncommitted work. Commit/build provenance was therefore not reproducible, and the ignored APK cannot be tied to commit `d01f420` from repository evidence.
- Effective production TLS, environment values, PostgreSQL behavior, backups/restores, observability, log shipping, resource limits, live migration compatibility, APK signing identity, and recovery objectives remain unverified.
- There is no CI configuration visible in the reviewed scope proving typecheck/lint/tests/build/migration verification gates a release.
