## Prioritized Findings

### P0 — Current migrations do not create the tables used by current code

The current Prisma models define `Zone` and `PackageAssignment` in `/Users/heinhtetaung/Developer/lotaya-pos/backend/prisma/schema.prisma:49-59` and `:131-147`. However, the four migration SQL files do not create either table. Direct inspection of `/Users/heinhtetaung/Developer/lotaya-pos/backend/dev.db` showed `PackageAssignment: MISSING` and `Zone: MISSING`; only the `Parcel.zoneId` column exists. `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/operations.service.ts:135` now writes `PackageAssignment` during bulk dispatch.

**Impact:** bulk assignment can fail at runtime against the checked-in local database; zone foreign-key/data integrity is also absent. `prisma migrate status` reporting up to date is misleading because the migration history does not represent the current model.

**Mitigation:** add provider-correct migrations for every model/column/index, recreate a clean SQLite database from migrations in CI, run the full dispatch workflow against it, and fail CI on schema drift using a migration diff/check.

### P0 — PostgreSQL deployment still uses an incompatible shared SQLite migration history

`/Users/heinhtetaung/Developer/lotaya-pos/backend/package.json` defines `db:deploy:postgresql` against the shared `prisma/migrations` directory. Those SQL files contain SQLite-oriented `DATETIME`, `BOOLEAN`, `TEXT` primary keys, and SQLite-style table alterations. The initial migration also predates current models such as `Zone`, `PackageAssignment`, partial-return fields, and linked groups. There is still no `migration_lock.toml` under `/Users/heinhtetaung/Developer/lotaya-pos/backend/prisma/migrations`.

**Impact:** a clean production PostgreSQL deployment is not proven and is likely to fail or produce schema drift. Prisma schema validation alone does not validate migration execution.

**Mitigation:** generate/test an independent PostgreSQL baseline and migration chain from an empty PostgreSQL database, run `db:deploy:postgresql` in CI, and add backup/restore and rollback verification.

### P0 — Linked delivery accounting remains vulnerable to double or misallocated money

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:139-154` creates a per-parcel `DeliveryWay`, then posts group collection and group commission journals when the last linked parcel is delivered. The group collection hard-codes `WALLET_CASH` and has no actual collected amount or wallet input. The group commission journal has no rider allocation. Meanwhile `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/finance.service.ts:10-25` adjusts settlement fee totals to the group fee, but does not derive the settlement from the group journal or allocate the group commission to a rider.

The link operation at `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/operations.service.ts:89-97` still permits parcels assigned to different riders, compares raw addresses, and chooses the first returned parcel’s fee as the base. This can create a group with ambiguous commission ownership and a nondeterministic base fee.

**Impact:** wallet balances, delivery-fee revenue, rider commission expense, and rider settlement expectations can disagree.

**Mitigation:** require one rider or persist explicit group allocation, normalize and persist an address key, validate a deterministic/common base fee, snapshot the commission policy, capture actual collection wallet/amount, and make group posting plus settlement allocation one idempotent journal-driven operation.

### P1 — Partial Return collection is now posted, but wallet selection defaults silently to Cash

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:91-135` now posts `PARTIAL_RETURN_COLLECTION` and the OS offset, which is an improvement. But `collectionWallet` is optional in `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/validators/parcels.ts:14-21`, defaults to `CASH` in the service signature, and is not supplied by the web Partial Return form or mobile parcel screen. The partial collection journal can therefore misclassify KBZ Pay or Wave Pay collections as cash.

**Mitigation:** require the wallet for Partial Return, expose it in both clients, and add API/integration tests for all three wallets and zero-collection cases.

### P1 — Ledger scope resolution still omits newer source types

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/ledger.service.ts:183-229` only resolves hub scope for pickup, regular delivery, shortfall, return deduction, rider settlement, and reversals. It does not resolve `PARTIAL_RETURN_COLLECTION`, `OS_PARTIAL_RETURN_ADJUSTMENT`, `LINKED_DELIVERY_COLLECTION`, `LINKED_RIDER_COMMISSION`, or `CASHBOOK_*` entries. Non-Superadmin ledger reports can therefore omit valid entries, and authorized finance users cannot consistently reverse or audit them.

**Mitigation:** store an explicit hub/resource reference on every journal entry and centralize scope resolution for all journal source types.

### P1 — Cashbook close has a check-then-close concurrency window

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/finance.service.ts:158-180` reads the open state, validates settlements and wallet reconciliation, then updates settlements and the cashbook in one transaction without an explicit serializable isolation/locking strategy. Concurrent postings can pass `assertCashbookOpen` before the close update and race with the close decision.

**Mitigation:** use database-supported row locks/serializable transactions, retry serialization failures, and add concurrent close/post integration tests against SQLite and PostgreSQL semantics.

### P1 — Return timing and manual extension requirements remain incomplete

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:8,103` uses a fixed four-day duration from the current timestamp rather than four hub-timezone calendar days. There is no extension endpoint, extension audit trail, or server-side due-date check before `PENDING_RETURN -> RETURNED`.

**Mitigation:** persist hub timezone, calculate calendar due dates, implement authorized extension/override records, and enforce the due-date rule server-side.

### P1 — Assignment history is created only for bulk assignment, without lifecycle controls

The new `PackageAssignment` insert fixes the original missing-history issue, but there is no reassignment/end-assignment path that closes the prior row with `endedAt`, `endedById`, and a reason. The parcel list still scopes by `Parcel.riderId`, not by an active assignment record. The model has no database constraint ensuring one active assignment per parcel.

**Mitigation:** implement reassignment as a transaction that closes the old assignment and creates the new one, enforce active-assignment uniqueness, and test concurrent reassignment.

### P1 — Mobile linked-group response contract still does not match the backend

The backend returns a nested `linkGroup` object from `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:89`. The mobile client expects flat `linkedParcelGroupId`, `linkedParcelCount`, and `linkedParcelIds` fields in `/Users/heinhtetaung/Developer/lotaya-pos/mobile/src/lib/api.ts:4`, and the Home screen reads those fields. No mapper is present.

**Impact:** the rider may not see linked parcels grouped even though the API returns group data.

**Mitigation:** use a versioned DTO mapper or align the API contract, then add a rendered mobile test for linked-group visibility.

### P1 — Dispatch UI remains bounded to 100 records and client-side rider-name filtering

The API uses `take: 100` at `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:89`. The frontend filters rider name locally at `/Users/heinhtetaung/Developer/lotaya-pos/frontend/src/pages/operations-page.tsx:17`, requires a manually entered rider ID, and has no pagination or stable selection reconciliation when filters change.

**Impact:** dispatchers can miss eligible parcels, select stale IDs, or receive server rejection after changing filters.

**Mitigation:** add server-side rider filters and a scoped rider selector, cursor pagination, selection invalidation, and a shared eligibility DTO.

### P1 — Authentication hardening is improved but still incomplete

The production JWT fallback is now rejected and development receives a generated secret in `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/config/env.ts:11-13`, which fixes the previous known-secret issue. However, `DATABASE_URL` still defaults to `file:./dev.db`, `DATABASE_PROVIDER` is not validated and unknown values fall through to SQLite in `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/config/database.ts:6-8`, and authentication has no rate limiting, lockout, or abuse telemetry. The web client stores bearer tokens in `localStorage` at `/Users/heinhtetaung/Developer/lotaya-pos/frontend/src/lib/api.ts:2-14`; the API cookie lacks `Secure` in `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/controllers/auth.controller.ts:2`.

**Mitigation:** fail fast on production database configuration, validate provider/origin values, add rate limits and audit events, and prefer a hardened HttpOnly/Secure token boundary with CSRF protection where cookies are used.

### P2 — Alert delivery, acknowledgment, and pagination are not implemented

Alerts are stored transactionally for Partial/Failed outcomes, but `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/operations.service.ts:67-69` only exposes the latest 50 unacknowledged records. There is no acknowledgment route, cursor, outbox/retry mechanism, or WebSocket/SSE transport.

**Mitigation:** add an outbox/event delivery path, acknowledgment APIs, pagination, retries, and operational monitoring.

### P2 — Ledger reporting has an N+1 query pattern and no pagination

`getLedgerReport` loads all matching journal entries and calls `entryInScope` separately for each entry at `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/ledger.service.ts:232-238`. This can generate one or more database queries per entry and become expensive as the ledger grows.

**Mitigation:** persist hub scope on entries, filter in SQL, paginate report results, and add query-count/performance tests with realistic ledger volumes.

### P2 — Mobile routing and quality gates remain unverified
