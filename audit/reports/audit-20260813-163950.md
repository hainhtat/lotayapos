## Executive summary

Overall risk posture for this change is **High–Critical** on **money integrity**, despite solid **authz**, **no-wallet receive lines**, **hub checks**, and **Serializable** receive transactions.

The primary defect is that Finance receive correctly stages recovery into `OS_SETTLEMENT_OFFSET`, and settlement `returnedAdvance` is then zeroed for parcels with those credits — but **OS settlement posting never clears `OS_SETTLEMENT_OFFSET`**. Spec requires settlement net to handle cash movement after receive; the implemented path **under-recovers / overpays OS** after the intended receive-then-settle workflow. Secondary gaps: any existing `OS_RETURN_DEDUCTION` (including partial or reversed) is treated as terminal success, blocking remainder recovery.

Authz controls reviewed here look correct: Auditor can list, cannot receive; non-superadmin receive is hub-scoped; wallet accounts are not posted on receive.

**Finding counts:** Critical **1**, High **2**, Medium **3**, Low **2**.

## Findings

### F-01 — Critical — Settlement omits cash recovery after Finance receive stages `OS_SETTLEMENT_OFFSET`

**Location:** `finance.service.ts` `osBatchComponents` / `postOsSettlement` journal lines; `os-advance.ts` `buildReturnDeductionLines`; contrast `PROJECT_SPEC.md` §6.6 / §7

**Evidence:**

- Receive posts `Dr OS_SETTLEMENT_OFFSET` / `Cr OS_ADVANCE_RECEIVABLE` for recoverable remainder (`buildReturnDeductionLines`).
- Unit language confirms staging intent: *“reclassifies a returned parcel advance into a future OS settlement offset”* (`business-rules.test.ts`).
- Spec: return recovery does **not** credit wallets; **“settlement net handles cash movement later.”**
- After receive, `osBatchComponents` sets `returnedAdvance` via `recoverableAdvanceAmount(...)` → **0** when credits cover the advance.
- `postOsSettlement` still only applies return cash impact via `returnDeduction` defaulting to that `returnedAdvance`, posting `Cr` account `OS_RETURN_DEDUCTION` — it **never credits/clears `OS_SETTLEMENT_OFFSET`**.
- Focused test explicitly expects drafts `returnedAdvance === 0` after receive (`os-pending-return.test.ts`).

**Impact:** Intended happy path (Received → later OS settlement) **fails to reduce net payable / wallet outflow** for already-offset returned advances. Company can **overpay OS by the staged offset** (e.g. mixed delivered+returned batch). `OS_SETTLEMENT_OFFSET` accumulates with no settlement consumer.

**Mitigation:** In OS settlement posting (preview defaults + live re-check), consume unreversed `OS_SETTLEMENT_OFFSET` debits for statement parcels (clear with `Cr OS_SETTLEMENT_OFFSET` while reducing net payment), **or** keep settlement `returnedAdvance` as the cash component while ensuring parcel journals and settlement lines cannot both reduce OS economically. Add an end-to-end money test: receive → settle → assert net/wallet and OFFSET balance.

### F-02 — High — Existing `OS_RETURN_DEDUCTION` treated as fully complete (blocks remainder; ignores reversals)

**Location:** `finance.service.ts` `receiveOsReturn` (`RETURNED` + `existingDeduction` branch); `os-advance.ts` `postReturnDeductionInTx`

**Evidence:**

- Ledger `POST /ledger/return-deductions` allows `amount` **below** recoverable (`amount ?? recoverable` with only upper bound).
- Unique `(sourceType, sourceId)` allows **one** `OS_RETURN_DEDUCTION` per parcel.
- On `RETURNED` with any existing deduction, receive returns `alreadyReceived: true`, `recoverableAmount: 0`, without comparing to `recoverableAdvance()`.
- `postReturnDeductionInTx` returns the existing row when credited amount matches input; on mismatch → `IDEMPOTENCY_CONFLICT`; it does **not** check `LEDGER_REVERSAL`.
- If the unique row exists but was reversed, `sumUnreversedCreditsToOsAdvanceReceivable` correctly excludes it (`recoverable > 0`), yet receive still short-circuits as already received.

**Impact:**

1. Partial legacy deduction permanently **blocks** remainder recovery via Finance receive.
2. After reversal, receivable can reopen while receive reports success with **no new journal** — silent under-recovery and broken correction workflow.

**Mitigation:** On receive, if an `OS_RETURN_DEDUCTION` exists: require it unreversed and `credited === full current recoverable intent`; if reversed, allow a versioned `sourceId` (or dedicated reverse-and-repost policy); if under-posted, either top-up with a second source key or reject with an explicit `DEDUCTION_INCOMPLETE` instead of success. Align ledger partial posts with the same rule (prefer full recoverable only).

### F-03 — High — Optional / note-only idempotency does not bind retries to a single money intent

**Location:** `finance.routes.ts` (`idempotencyKey` optional); `receiveOsReturn` status-history note embedding

**Evidence:**

- Validator: `idempotencyKey` **optional**.
- Key is stored only in `statusHistory.note` (`idempotencyKey=...`), not a unique idempotency table/constraint.
- When already received, a **different** key still returns success (empty `if (!priorNote)` branch).
- Money uniqueness relies on `OS_RETURN_DEDUCTION` source uniqueness + status CAS, not client idempotency semantics.

**Impact:** Low risk of double **journal** create when Serializable + unique hold; higher risk of **ambiguous client retries**, weak audit correlation, and inconsistent HTTP semantics (always 201 with `alreadyReceived`). Does not replace F-02’s completeness bugs.

**Mitigation:** Require idempotency key on receive (as with OS settlement post); persist `(actor/hub, key) → result` with conflict on payload mismatch; return 200 for replay.

### F-04 — Medium — `LINKED_OS_SHORTFALL` credits not visible to parcel-scoped recoverable math

**Location:** `os-advance.ts` `sumUnreversedCreditsToOsAdvanceReceivable*`; `ledger.service.ts` delivery collection shortfall (`sourceId` = group id for linked)

**Evidence:** Recoverable credits are summed only where `journalEntry.sourceId === parcel.id`. Linked shortfalls use `LINKED_OS_SHORTFALL` with `sourceId = group.id` while still crediting `OS_ADVANCE_RECEIVABLE`.

**Impact:** For linked parcels that later enter the pending-return queue, receive may compute **inflated recoverable** and over-credit `OS_ADVANCE_RECEIVABLE` / over-stage OFFSET (over-deduction vs true remainder).

**Mitigation:** Include unreversed linked-group journals that credit `OS_ADVANCE_RECEIVABLE` for the parcel’s group membership when computing recoverable, or always post shortfall credits under parcel `sourceId`.

### F-05 — Medium — Cashbook open guard skipped when `recoverableAmount === 0`

**Location:** `receiveOsReturn` happy path (status update before conditional `assertCashbookOpen`)

**Evidence:** `assertCashbookOpen` runs only when posting a journal (`recoverableAmount > 0`) or when completing recovery on already-`RETURNED` with remainder. Status-only transitions (full partial offset already booked) proceed on a closed business date.

**Impact:** Operational inconsistency vs other finance mutations; less money risk (no new lines) but allows Finance to finalize `RETURNED` against a closed day without an explicit reopen/override audit.

**Mitigation:** Always assert open cashbook for receive (or require Superadmin override reason when day closed), including zero-journal receives.

---

### F-06 — Medium — Concurrent ledger `postReturnDeduction` lacks Serializable isolation

**Location:** `ledger.service.ts` `postReturnDeduction` (`$transaction` without `isolationLevel`)

**Evidence:** Finance receive uses `{ isolationLevel: "Serializable" }` + `updateMany` status CAS. Legacy return-deduction path does not. Unique `(OS_RETURN_DEDUCTION, parcelId)` mitigates duplicate inserts; races with receive can still surface as raw unique violations or F-02 short-circuit behavior rather than clean `STATUS_CONFLICT` / `IDEMPOTENCY_CONFLICT`.

**Impact:** Reliability / error-envelope inconsistency under concurrency; money double-post unlikely due to unique key.

**Mitigation:** Use Serializable (or at least repeatable read + handling) on `postReturnDeduction`; map unique violations to stable API codes; prefer single write path (Finance receive).

---

### F-07 — Low — N+1 reversal probes when summing recoverable credits

**Location:** `os-advance.ts` `sumUnreversedCreditsToOsAdvanceReceivable` / `ByParcel` → per-entry `journalEntryIsUnreversed`

**Evidence:** Each candidate journal triggers `findUnique` on `LEDGER_REVERSAL` / original id. List queue caps at 500 parcels; settlement batches can multiply entries.

**Impact:** Latency under load for pending-return list and settlement preview/post live re-check; not a direct funds bug.

**Mitigation:** Batch-load reversal sourceIds for the entry id set in one query.

---

### F-08 — Low — Receive completion on Ops-`RETURNED` lacks status-history attribution

**Location:** `receiveOsReturn` branch “Ops marked RETURNED without finance deduction”

**Evidence:** Posts journal when recoverable > 0 but does not append `statusHistory` / finance reason note (unlike the pending-status path).

**Impact:** Weaker audit trail for who completed money recovery after Ops status change; attribution depends on journal metadata (no actor field on `JournalEntry` schema).

**Mitigation:** Append an audit/status note (or dedicated audit log) with actor, amounts, and idempotency key when posting recovery on already-`RETURNED` parcels.

## Performance / reliability / scalability observations

- Pending-return list is bounded (`take: 500`) but has no pagination cursor; hubs with large exception queues will silently truncate — operational understatement of `summary.totalRecoverableAmount`.
- Serializable receive is appropriate for money+status; expect retry needs under SQLite/Postgres contention — clients should retry safely once F-03 is hardened.
- Settlement live re-check correctly recomputes credits inside the posting transaction (good), but inherits F-01’s OFFSET gap.

## Positive controls verified

- **Auditor write denied:** route `requireRoles` omits `AUDITOR` on `POST /os-returns/receive`; `assertFinanceActor` allows only Superadmin/Finance/Operations Manager; `api-contract.test.ts` expects 403 for Auditor receive and 200 for list.
- **Hub scope on receive:** non-superadmin must match `parcel.batch.hubId`; mismatch → `403 FORBIDDEN`.
- **List hub resolution:** non-superadmin goes through `resolveFinanceHubForRead` (hub required); Superadmin may omit `hubId` for org-wide list per spec.
- **No wallet leakage on receive:** deduction lines are only `OS_SETTLEMENT_OFFSET` / `OS_ADVANCE_RECEIVABLE`; tests assert no `WALLET_*` accounts.
- **PARTIAL remainder math (parcel-local):** `recoverableAdvance = max(0, advance − unreversed parcel-scoped credits)`; partial adjustment uses same OFFSET/ADVANCE shape; full prior offset → receive with `journalEntry: null`.
- **Status race on pending path:** `updateMany` conditioned on prior status + Serializable transaction.
- **Duplicate deduction create:** unique `(sourceType, sourceId)` on `JournalEntry`.
- **Cashbook guard when posting money:** `assertCashbookOpen` before `postReturnDeductionInTx` when amount > 0.
