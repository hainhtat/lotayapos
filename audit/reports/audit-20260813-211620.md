## Executive summary

**Overall risk posture: Medium-High** for authenticated resource exhaustion and Reports over-fetch; **no Critical privilege-escalation** found in the Superadmin org-wide change.

Hub-scoped roles still cannot select another hub: `input.hubId` is applied only for Superadmin; other roles use `user.hubId` and rider/parcel rows are rejected when `rider.hubId` / `batch.hubId` differs. Superadmin with no `hubId` (user-admin forbids Superadmin hub assignment) is organization-wide, matching `PROJECT_SPEC.md` §6.3. Finance and Auditor may preview and download. Caps remain 50 riders / 500 parcels.

The 500-parcel cap is enforced **after** an unbounded `findMany`, so a legitimate Reports click on “all dates” (or Superadmin org-wide with a wide status set) can load far more than 500 rows of customer PII/COD into memory before returning `400 BATCH_TOO_LARGE`. Reports also loads the full ledger (every journal entry + lines) on mount with no date filter. Tests that pass do not exercise these load paths.

Parcel modal CSS is not a security issue; add/edit overlays still omit the `max-h`/`overflow-y-auto` applied to the manifest dialog.

## Findings

### A-01 — High — Parcel cap applied after unbounded `findMany`

**Location:** `backend/src/services/operations.service.ts` (`buildManifestForRiders`, parcel `findMany` then `if (parcels.length > 500)`).  
**Also:** `frontend/src/pages/reports-page.tsx` (preview on mount; user can set date preset `all`); `frontend/src/lib/manifest-filters.ts` (`buildManifestBody` omits dates when preset is `all`).

**Evidence:** Rider list for empty `riderIds` uses `take: 51`. The subsequent parcel query has **no** `take`. Matching rows (all requested statuses, optional pickup-date filter, up to 50 riders) are loaded with customer name/phone/address and COD, then rejected if `length > 500`. Operations routes have no rate limiter (login-only). Reports default is `datePreset: "today"` and `status: "all"`; choosing **All dates** sends `{ statuses: [...all 10 statuses] }` with no `dateFrom`/`dateTo`.

**Impact:** Any authenticated Superadmin, Operations Manager, Dispatcher, Finance, or Auditor can force a large sequential read and in-process materialization of PII and money fields, then a 400. Repeated requests (including TanStack Query refetch-on-focus on Reports) can stall the Node process. Superadmin org-wide (the bugfix) widens the match set across hubs.

**Mitigation:** Apply `take: 501` (or `findMany` + `take` then reject), or `count` first. Reject wide unfiltered Superadmin queries unless `hubId` or a date range is present. Rate-limit preview/PDF. Prefer a summary aggregate for Reports totals instead of hydrating every parcel.

### A-02 — High — Reports loads unbounded ledger history on mount

**Location:** `frontend/src/pages/reports-page.tsx` (`useQuery` `/finance/ledger` with empty `from`/`to`/`account`); `backend/src/services/ledger.service.ts` `getLedgerReport` (`findMany` journal entries `include: { lines: true }` with no take; Superadmin `where: {}` when dates omitted). Response includes `entries: filteredEntries` even though the UI only renders `ledgerAccounts(...)`.

**Evidence:** Initial `filters` are `{ from: "", to: "", account: "" }`, so the first request is `GET /finance/ledger` with no query string. Hub-scoped Finance/OM/Auditor are hub-filtered; Superadmin is organization-wide and unbounded in time. The page also fires `/operations/parcels/manifest/preview` on the same mount.

**Impact:** Every Reports visit can dump the entire posted ledger (descriptions, amounts, actor-linked entries) to the browser. Grows without bound; not a client-side recalculation bug, but a confidentiality and memory/payload failure as journals accumulate. Complements A-01 on the same screen.

**Mitigation:** Default a business-date range (today / this month). Do not return `entries` unless requested. Paginate or aggregate server-side. Do not auto-run ledger until the user clicks **Run report** (the form already exists).

### A-03 — Medium — Superadmin Reports cannot pick a hub; 50-rider cap fails the default “all riders” view

**Location:** `buildManifestForRiders` empty-`riderIds` branch (`take: 51` then `BATCH_TOO_LARGE`); Reports UI has rider select but **no `hubId` control**. Superadmin user records cannot have a hub (`user-admin.service.ts` `INVALID_USER_SCOPE`).

**Evidence:** Spec §6.3 documents org-wide Superadmin + max 50 riders. Reports `buildManifestBody` with empty `riderIds` sends no `hubId`. Any organization with 51+ riders gets `400 BATCH_TOO_LARGE` on every Superadmin Reports load (and Dispatch “all riders” download), even when today’s parcel count is small.

**Impact:** The HUB_REQUIRED fix unblocks empty-rider Superadmin preview in tests/small fixtures, then the documented cap makes the same Reports panel unusable in a multi-hub production org. Not a cross-hub leak.

**Mitigation:** Add an optional Superadmin hub filter on Reports/Dispatch. If more than 50 hub/org riders exist, require an explicit rider or hub selection instead of auto-querying. Consider raising or paging the rider cap for JSON preview (keep PDF tighter).

### A-04 — Medium — Hub-less Auditor vs manifest hub gate; Auditor cannot load rider master data

**Location:** `normalizeScope` allows Auditor with `hubId: null`; `buildManifestForRiders` returns 403 for non-Superadmin without `hubId`; `listMasterData` roles omit `AUDITOR`.

**Evidence:** Frontend user-admin `needsHub` excludes Superadmin and Auditor. Contract tests attach Auditor to `contract-hub`, so hub-less Auditor is untested. Reports still calls `GET /master-data` for the rider dropdown (403 for Auditor); preview with empty `riderIds` works only if the Auditor has a hub.

**Impact:** An org-wide Auditor (allowed by user-admin) cannot use delivery-status preview/PDF. Hub-scoped Auditor can preview (intended) but the rider filter stays empty. No extra privilege; availability/authz inconsistency with spec “explicitly granted scope.”

**Mitigation:** Either require a hub on Auditor create, or treat hub-less Auditor like Superadmin for **read** manifests (still no mutations). Allow Auditor to list hub-scoped riders without the full master-data payload.

### A-05 — Low — Preview JSON over-exposes PII relative to on-screen table; no download audit

**Location:** `previewManifest` returns full `sections` (phone, address, COD); `DeliveryStatusPanel` shows name/township/COD/fee only; `generateDispatchManifestPdf` prints phone/address; no `statusHistory` / audit row on download.

**Evidence:** Spec allows Finance/Auditor preview for settlement review. Prior audits already noted missing download audit. PDF is still built fully in-process (`operations.controller.ts` `downloadManifest`).

**Impact:** A captured preview response or XSS on Reports leaks phones/addresses even when the table does not show them. Downloads of COD sheets are not attributable. Residual, not a new bypass.

**Mitigation:** Split a totals-only preview from a PII-bearing PDF payload; audit `actorId` + filter hash on PDF.

### A-06 — Low — Parcel add/edit modal CSS (no security impact)

**Location:** `frontend/src/pages/batch-detail-page.tsx` (`formOpen` / `editing` overlays); `frontend/src/pages/operations-page.tsx` edit-parcel dialog.

**Evidence:** Manifest dialog gained `max-h-[90vh] overflow-y-auto`. Add/edit parcel forms remain `fixed inset-0 … place-items-center` without max-height or overlay scroll. COD still validated with `/^\d+$/` before submit; no client-side settlement math.

**Impact:** Tall viewports/keyboards can clip Save/Cancel. No authz, injection, or money-integrity issue.

**Mitigation:** Reuse the manifest overlay pattern (`max-h-[90vh] overflow-y-auto`) on add/edit parcel dialogs.

| No N+1 on manifest | Two Prisma queries (riders, then parcels); sections grouped in memory. |
| Missing index | Parcel query is `riderId IN (…) AND status IN (…)` plus optional `batch.hubId` / `pickupDate`. Schema has `@@index([batchId, status, riderId])` and `@@index([status])`, not `riderId`. Org-wide/all-dates scans will not use a rider-leading index. |
| Sync PDF | `generateDispatchManifestPdf` runs on the request thread; cap 500 still implies large peak CPU/memory and Helvetica-only glyphs (Myanmar names truncated/mojibake). |
| Reports refetch | Default TanStack `refetchOnWindowFocus` re-hits preview + ledger (A-01/A-02). Dispatch preview is `enabled: manifestOpen` (better). |
| Inactive riders | Empty `riderIds` listing does not filter `user.active`. |
| Default statuses | Omitted `statuses` still dispatch-ready `ASSIGNED` / `OUT_FOR_DELIVERY` / `PICKED_UP`. Reports explicitly sends all statuses. Unassigned `CREATED` parcels never appear (filter is `riderId IN`). |
| Integer money | Totals are integer sums from Prisma `Int` fields. PDF `Math.round` is display-only. Clients format with `toLocaleString`; settlement/ledger math stays on the server. Dashboard `cashCollected` is displayed, not recomputed. |

## Positive controls verified

- **Role gates:** Routes allow Superadmin, Operations Manager, Dispatcher, Finance, Auditor. Contract test expects Rider `403 FORBIDDEN`. Service re-checks DB role vs actor (`manifestReadRoles`) and `requireAuth` uses persisted `user.role`, not the JWT role claim.
- **Hub isolation:** Non-Superadmin `hubId = user.hubId`; body `hubId` ignored. Riders missing or in another hub → `404 RIDER_NOT_FOUND` with `outOfScopeRiderIds`. Parcels constrained with `batch.hubId` when `hubId` is set. Superadmin may pass `hubId` to narrow; omitting it is org-wide (intended). Superadmin cannot be assigned a hub.
- **Caps (logical):** `riderIds` validator `max: 50`; duplicate rider IDs → `INVALID_RIDER_IDS`; empty list + `take: 51` → `BATCH_TOO_LARGE`; statuses enum + `max: 12`; dates ISO-8601; `dateFrom < dateTo`.
- **Finance/Auditor preview:** Same `buildManifestForRiders` as PDF; JSON omits filename-only fields. Spec §6.3 / §6.9.
- **Client is not the authz boundary:** Reports has no role-based hiding of the delivery panel; Dispatcher ledger `GET` is denied server-side (`requireRoles` excludes Dispatcher). Rider users are routed to `/rider-app`.
- **Dispatch Queue** does not preview until the manifest dialog is open.

## Recommended follow-up

1. Bound parcel `findMany` with `take: 501` before A-01 can hit production volume (urgent).
2. Stop auto-fetching unbounded `/finance/ledger` on Reports mount; default a date range and drop `entries` from the aggregate response.
3. Add Superadmin hub filter (or require rider selection) so the 50-rider cap does not 400 the Reports panel.
4. Add an integration test: hub-A Dispatcher + hub-B `riderIds` / spoofed `hubId` → 404/ignored; Superadmin empty body → 200.
5. Align Auditor hub policy with user-admin and master-data read access.
