## Requested remediation verification

### 1. Cashbook reopen shared lock and Serializable transaction — Confirmed

`backend/src/services/finance/cashbook-close.ts:245-287` now calls `lockCashbookDay(tx, date, hubId)` before reading/updating the day and executes the transaction at Serializable isolation. `cashbook-policy.ts:5-24` provides the same hub/day advisory-lock primitive used by writers and close operations.

This closes the prior gap where reopen could race close or another cashbook command without joining the shared lock protocol.

### 2. Database aggregation for cumulative rider paid amounts — Confirmed

`backend/src/services/finance/rider-settlements.ts:260-291` now uses `settlement.groupBy({ by: ["riderId"], _max: { actualAmount: true } })` rather than loading every historical settlement and nested line.

Using `_max(actualAmount)` is consistent with this model because each Settlement stores the cumulative paid reconciliation snapshot, while immutable per-receipt evidence remains in SettlementLine. This removes the largest historical-memory component of FIN-R04. The endpoint still loads every active rider and current-day detail, so organization-scale pagination remains a Low scalability improvement.

### 3. OS amendment P2002/P2034 recovery — Confirmed

`backend/src/services/finance/os-settlements.ts:474-561` wraps the Serializable amendment transaction. On `P2002` or `P2034`, it re-reads the unique edit audit; when a committed audit exists it re-enters the normal replay verifier, and otherwise returns `RETRYABLE_CONFLICT`.

The recursive replay is bounded in the successful-race case because the next call observes the persisted audit before entering another transaction. This resolves FIN-R01's indeterminate 500 path. Global error middleware also maps uncaught `P2034` to a stable 409 as a final safety net.

### 4. Durable actor identity for direct cashbook journals — Confirmed with format caveat

`backend/src/services/finance/cashbook-postings.ts:59-75` appends `[actor:<user-id>]` to the persisted journal description and includes that exact description in idempotent replay equivalence.

This makes the initiating actor durable and causes a different actor reusing the same key to receive an idempotency conflict, resolving the immediate attribution gap. A normalized `actorId` column or linked audit row would remain preferable for indexed reporting and referential integrity, but the current implementation meets the attribution requirement without a schema migration.

### 5. Expense limit parsing — Rejected

**Location:** `backend/src/validators/finance/expenses.ts:9`; `backend/src/controllers/finance.controller.ts:42`.

The validator uses `.toInt()`, which sanitizes a valid query value from string to number. The controller then passes a limit only when `typeof req.query.limit === "string"`. A direct express-validator check confirmed that `"25"` becomes the number `25`; therefore the controller supplies `undefined` and `listExpenses` defaults to 100.

**Impact:** response size remains safely capped, but clients cannot request a valid page size such as 25 or 200. This is a Low API correctness defect.

**Mitigation:** accept the sanitized number (`typeof req.query.limit === "number"`) or robustly normalize both string and number. Add an HTTP test asserting `?limit=1` returns at most one row.

## Remaining findings

### FIN-S01 — Medium — PostgreSQL-only cashbook locking remains unexecuted by the PostgreSQL suite

**Location:** `backend/src/services/finance/cashbook-policy.ts:5-24`; `backend/scripts/test-postgresql.mjs`.

The production branch invokes `pg_advisory_xact_lock(hashtext(...))`, but the PostgreSQL runner still does not include `cashbook-posting-workflow.test.ts` or a close/reopen-versus-post concurrency test. SQLite checks cannot verify this SQL path.

**Risk:** provider-specific SQL or transaction behavior could fail only in production, potentially rejecting all cashbook writes or failing to provide the intended serialization.

**Required deployment gate:** run an isolated PostgreSQL test covering ordinary posting plus overlapping close/post and reopen/post operations. Add this workflow permanently to `test:postgresql`.
