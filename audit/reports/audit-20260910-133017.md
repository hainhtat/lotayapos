## Open findings

### PR-AUD-001 — High — Batch finalization can race a parcel import

**Location:** `backend/src/services/operations.service.ts:312-320`, `backend/src/services/operations.service.ts:334-350`

**Evidence:** `bulkCreateParcels` rechecks `finalizedAt` inside a default-isolation transaction, but does not lock or conditionally mutate the Batch row before inserting parcels. `finalizeBatch` runs Serializable and conditionally updates the batch, then calculates its obligation. The tracking allocation lock protects tracking-number allocation only; it does not establish a common batch lock/order between these flows.

**Failure scenario and impact:** On PostgreSQL, an import transaction can read `finalizedAt = NULL`; concurrently, finalization can update the Batch and calculate `originalCod`; the import can then commit parcels after the obligation snapshot. This leaves a finalized batch whose immutable OS obligation excludes accepted parcels, understating OS payable. A Serializable finalizer does not guarantee conflict detection against an otherwise non-serializable reader/writer that did not lock the same Batch row.

**Recommendation:** Make both operations acquire the same row-level Batch lock before checking state, or make parcel creation conditional on a version/finalization guard enforced by the database. Run both at compatible isolation and add a real PostgreSQL two-connection race test asserting exactly one side succeeds and obligation COD equals committed parcel COD.

### PR-AUD-002 — High — Required Organization isolation remains absent

**Location:** `PROJECT_SPEC.md:29`, `PROJECT_SPEC.md:236`; `backend/prisma/schema.prisma:9-33`, `backend/prisma/schema.prisma:82-93`, `backend/prisma/schema.prisma:160-202` (PostgreSQL schema has the same model shape)

**Evidence:** The specification names Organization as a core entity, but User, Hub, OnlineShop, Batch, and financial records have no `organizationId` or Organization relation. Authorization constrains many actors by hub, while Superadmin has global access; globally unique shop/user identifiers likewise span the whole database.

**Exploit/failure scenario and impact:** If more than one customer organization shares a deployment, a global Superadmin or any missed hub filter can enumerate or mutate another organization's operational and financial data. Hub checks cannot prove tenant membership when hubs themselves have no tenant owner.

**Recommendation:** Add Organization ownership to every tenant root and financial/operational aggregate, include organization identity in authenticated server-side scope, enforce organization plus hub predicates centrally, and migrate/backfill under a deploy-time invariant. Until then, document and enforce one organization per deployment.

## Closed prior findings

### Prior AUD-001 — Critical — Migrated legacy settlements reopen liabilities: closed with operational prerequisite

`backend/src/services/os-account.service.ts:84-123` now incorporates attributable legacy settlement batch evidence and fails closed with `OS_CUTOVER_RECONCILIATION_REQUIRED` when settlement-level net and attributable totals differ. `backend/src/services/os-account.service.ts:137-160` permits only Superadmin to apply the exact computed difference, records approval metadata, checks the cashbook, uses an idempotent journal key, and runs Serializable. The new provider-parity migrations add adjustment fields. This prevents payment against an unreconciled account, although deployment must include a reconciliation run and approved adjustments before OS accounts become usable.

### Prior AUD-002 — Critical — Legacy settlement and simplified payment can pay the same batch: closed for normal operation

`backend/src/services/finance.service.ts:704-725` rejects creation of a legacy settlement for any batch with an OS obligation; draft create/edit and legacy reversal paths also fail closed (`:885-896`, `:930-949`, `:1439-1451`). `frontend/src/pages/settlement-workspaces.tsx:45-98` hides legacy writes. The backend guard, not the UI flag, is the effective control. Keep routes only for historical reads until removal.

### Prior AUD-003 — High — Unlink leaves parcel-keyed linked COD live and reposts duplicates: closed

`backend/src/services/operations.service.ts:481-510` discovers both group-keyed and parcel-keyed linked journals, reverses each live journal, negates linked receivable projections, unlinks, and creates individual recognition. Lines `516-532` preserve already-posted linked collections by reversing and reallocating them to individual parcels. The marker journal provides retry idempotency. `backend/tests/linked-parcels.test.ts:106-138` covers authorization, reversal, projection totals, and replay.

## Positive controls verified

- SQLite and PostgreSQL reconciliation migrations have matching adjustment columns.
- Financial unlink requires Finance/Superadmin once live journals exist and checks the cashbook before reversal.
- OS account payment idempotency binds keys to a request hash.
- Finalization uses a conditional update and creates the obligation in the same Serializable transaction; this protects duplicate finalizers, though not the mixed-isolation import race above.
