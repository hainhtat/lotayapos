## Executive summary

**Overall risk posture: Medium–High** for first production cut with refresh auth; **Medium** after TLS, migration, and pooler configuration are verified.

The codebase shows mature patterns for a cash-on-delivery ERP: server-side deny-by-default authz, hub scoping, `Serializable` money transactions, idempotency keys on settlement/receive paths, `MONEY_POSTED` gates on status corrections, and a well-tested refresh-token rotation design (hash-at-rest, family revoke on reuse, `tokenVersion` invalidation). The new 15-minute access JWT + silent refresh closes a real ERP reliability gap.

**Blockers before production ship:**

1. Apply Postgres migration `20260814060000_refresh_tokens` on Supabase (direct `:5432` URL).
2. Confirm HTTPS on `lotaya.mmds.site` (Certbot); repo nginx template is still HTTP-only until TLS exists.
3. Configure Supabase pooler URL with `pgbouncer=true` for runtime; keep direct URL for `migrate deploy`.
4. Set `WEB_ORIGIN=https://lotaya.mmds.site` in shared env.

**Ship recommendation:** **Conditional no-ship** until items 1–4 are verified in production. After that: **conditional ship** for ERP + mobile sideload, with monitoring on DB latency and refresh errors. Supabase region migration (Mumbai → Singapore) is an optional performance investment, not a security fix.

#### AUD-20260814-H02 — Cross-region DB latency (Singapore VPS ↔ Mumbai Supabase)

| Field | Detail |
| --- | --- |
| **Location** | Infra: API on VPS in Singapore; Supabase Postgres in `ap-south-1` (Mumbai) |
| **Evidence** | Typical inter-region RTT ~25–45 ms per hop; each API request may issue multiple sequential Prisma queries; money posts use multi-statement `Serializable` transactions |
| **Impact** | Elevated p95/p99 on dispatch lists, dashboard, rider outstanding, OS settlement preview/post; compounded under concurrent finance users; static frontend assets unaffected |
| **Mitigation** | (1) Optimize hot paths (see performance section). (2) Enable connection pooler with sane pool size. (3) Optional: new Supabase project in `ap-southeast-1` + dump/restore cutover (region cannot be changed in place). (4) Consider read replicas only if query patterns justify it |

#### AUD-20260814-H03 — Supabase transaction pooler vs Serializable money posts

| Field | Detail |
| --- | --- |
| **Location** | `DATABASE_URL` configuration; `finance.service.ts`, `parcel.service.ts`, `user-admin.service.ts` use `isolationLevel: Serializable` |
| **Evidence** | Prior audit D-05; Prisma `pg` adapter with no `pgbouncer=true` handling in `postgres-pool.ts`; deploy uses same env file for runtime and migrate |
| **Impact** | Transaction pooler (`:6543`) can break Serializable semantics, cause subtle posting failures, or migration errors |
| **Mitigation** | Runtime `DATABASE_URL` on pooler with `?pgbouncer=true`; separate direct `:5432` URL for migrations only; document in `lotaya.env` |

#### AUD-20260814-H04 — Refresh rotation is not atomic (TOCTOU race)

| Field | Detail |
| --- | --- |
| **Location** | `backend/src/utils/refresh-token.ts` `rotateRefreshToken` |
| **Evidence** | Flow: `findUnique` → `issueRefreshToken` (create) → `update` revoke old — no `$transaction` or row lock; two concurrent refreshes with the same token can both succeed before revocation |
| **Impact** | Stolen refresh token may yield two valid sessions briefly; legitimate multi-tab refresh can revoke sibling sessions when one tab reuses a stale token (family revoke tested, but race window exists) |
| **Mitigation** | Wrap rotation in `$transaction` with `SELECT … FOR UPDATE` on the token row, or use conditional update (`WHERE revokedAt IS NULL`) and treat 0 rows updated as reuse |

#### AUD-20260814-H05 — Cookie-authenticated writes lack CSRF defense-in-depth

| Field | Detail |
| --- | --- |
| **Location** | `backend/src/middleware/auth.ts` (accepts `accessToken` cookie); all mutating `/api/v1/*` routes; no CSRF middleware |
| **Evidence** | Cookies use `SameSite=Lax` (not `Strict`); CORS allowlist with `credentials: true`; no `Origin`/`Referer` enforcement on writes |
| **Impact** | Cross-site request scenarios that bypass SameSite (legacy browsers, future policy gaps, subdomain issues) could trigger cookie-authenticated state changes if an attacker induces a victim browser session |
| **Mitigation** | Enforce `Origin`/`Referer` against `WEB_ORIGIN` on mutating routes, or CSRF double-submit token for cookie clients; document bearer-only clients (mobile) vs cookie clients (ERP) |

#### AUD-20260814-H06 — PostgreSQL TLS verification disabled

| Field | Detail |
| --- | --- |
| **Location** | `backend/src/config/postgres-pool.ts` — `ssl: { rejectUnauthorized: false }` |
| **Evidence** | All production DB connections accept any server certificate |
| **Impact** | Network-path MITM between VPS and Supabase could intercept or tamper with queries (including auth and ledger reads) if an attacker can position on the path |
| **Mitigation** | Use Supabase CA / `sslmode=verify-full` with proper CA bundle; avoid blanket `rejectUnauthorized: false` in production |

#### AUD-20260814-H07 — Refresh token also returned in JSON response body

| Field | Detail |
| --- | --- |
| **Location** | `backend/src/controllers/auth.controller.ts` `sessionBody`; mobile `session-store.ts` |
| **Evidence** | Login/refresh responses include `refreshToken` in JSON; mobile persists in SecureStore; ERP avoids localStorage refresh (tested) |
| **Impact** | Mobile backup extraction, compromised device, or future XSS on mobile web build exposes long-lived refresh; ERP surface reduced but dual delivery increases API contract complexity |
| **Mitigation** | Mobile-only refresh in body for native clients; consider splitting mobile vs web auth responses; keep ERP on cookie-only refresh |

## Performance / reliability / scalability

### Cross-region latency model

```
[Browser/Rider] → [nginx SG VPS] → [Node API localhost] → [Supabase PG Mumbai]
                      ~1ms              ~25–45ms RTT per query round trip
```

Every Prisma call crossing the pooler pays inter-region latency. Endpoints with sequential queries (dashboard, rider outstanding, settlement preview inside transactions) multiply RTT. **Co-locating Supabase in `ap-southeast-1` (Singapore)** typically saves ~30–80 ms per query vs Mumbai from a Singapore VPS — meaningful for interactive ERP, less so for batch reports run off-hours.

### Query / index observations

| Pattern | Risk | Notes |
| --- | --- | --- |
| Parcel list | Controlled | Paginated, max `pageSize` 100 |
| Batch list | High | Unbounded (M-02) |
| Tracking sequence | High | Full scan (M-03) |
| Rider outstanding | High | N+1 (M-04) |
| Manifest build | Controlled | 500 parcel / 50 rider caps |
| OS settlement post | Good | Serializable + idempotency + live re-check |
| RefreshToken | Good | Index on `tokenHash`, `(userId, expiresAt)` |

### Reliability

- **Idempotency:** OS settlement and finance receive paths use idempotency keys with conflict detection — verified in tests.
- **Money integrity:** `MONEY_POSTED` blocks status overrides when unreversed journals exist; reversals required first.
- **Session refresh:** Family revoke on reuse tested (`auth-refresh.test.ts`); rotation race remains (H-04).
- **Mobile:** SecureStore for tokens on native; localStorage fallback on web dev builds.
- **Offline:** No mutation queue; riders need connectivity for outcomes.

### Infra improvement options (ordered)

1. **Query optimization + indexes** — lowest cost; fix unbounded reads first.
2. **Supabase pooler tuning** — `pgbouncer=true`, appropriate `max` pool size on VPS.
3. **Supabase region migration** — new project in Singapore; planned downtime + dump/restore.
4. **CDN for static ERP** — marginal gain; API latency dominates.
5. **Read replica in SG** — only if read-heavy reporting justifies ops cost.

## Positive controls verified

- JWT access **15m**; refresh **12h session / 7d remember**; hashed at rest (SHA-256)
- Reuse of revoked refresh → **revoke all** user refresh tokens (tested)
- `tokenVersion` increment on password reset / privilege change → invalidates access JWT + revokes refresh family
- Cookies: **HttpOnly**, **SameSite=Lax**, **Secure** in production, path-scoped refresh cookie
- Auth middleware re-reads **role + active + tokenVersion** from DB on every request
- Hub/rider scope enforced in parcel, finance, operations services
- Login rate limit (10 / 15 min / IP) with `trust proxy` in production
- CORS origin allowlist with credentials
- APK update URL validation (`mobile/src/lib/app-release.ts`) — HTTPS + host allowlist
- API binds **127.0.0.1** in production via systemd; nginx reverse proxy
- Error handler avoids stack traces in JSON responses
- Test suites: **167 + 68 + 72** passing locally
- Dual-schema deploy path: `deploy.sh` uses PostgreSQL schema + `migrate deploy` only
