# Production Audit Report

Timestamp: 2026-09-12 23:07:50 +0630 (Asia/Yangon)  
Repository: `lotaya-pos`, commit `1fd9f98` (working tree contains unrelated frontend modification)

## Scope and exclusions

Reviewed `PROJECT_SPEC.md`, backend authentication/configuration, finance settlement draft/post flows, parcel linking/unlinking, ledger-facing services, routes/validators, and package scripts. Read-only inspection only; no database migrations, external services, or production systems were accessed.

## Executive summary

Overall risk posture: **Medium**, with a **High financial/operational integrity defect** in linked-parcel creation. The API can create a linked delivery group from parcels at different addresses and from exception states, while charging a single group fee and applying linked settlement rules. This can misallocate delivery fees, commissions, collections, and OS/rider balances. Production CORS also has an insecure localhost fallback if deployment omits `WEB_ORIGIN`.

## Findings

### AUD-001 — High — Linked parcels are not constrained to the same address or eligible lifecycle state

**Location:** `backend/src/services/operations.service.ts:448-471`, `linkParcels`.

**Evidence:** `normalizeDeliveryAddress()` is defined but never called. The query checks only `linkGroupId`, `DELIVERED`, and `RETURNED`; `FAILED`, `PARTIAL`, `REJECTED`, and `PENDING_RETURN` are accepted. The group address is copied from the first parcel and one adjusted fee is calculated for the entire set.

**Impact/scenario:** An authorized dispatcher can link unrelated destinations or exception parcels. Later linked collection/commission/settlement code treats the group as one delivery and suppresses individual fees for incomplete groups, potentially undercharging customers, miscrediting rider receivables/commission, and distorting OS settlement and return deductions. This is a direct violation of the exact-same-address and lifecycle rules in the spec.

**Mitigation:** Normalize and compare every selected address (and, if required by policy, township/zone) inside the transaction; reject mismatches. Restrict linking to the explicitly eligible pre-delivery statuses, and re-check status/version under a serializable transaction or row/advisory locks. Add regression tests for different casing/whitespace, different addresses, and exception statuses.

### AUD-002 — Medium — Production CORS allows localhost when `WEB_ORIGIN` is omitted

**Location:** `backend/src/config/env.ts:29-39` (`parseWebOrigins`).

**Evidence:** The default is `http://localhost:5173` for both development and production. No production-time requirement rejects an unset `WEB_ORIGIN`.

**Impact/scenario:** A production deployment with incomplete environment configuration accepts credentialed browser requests from a local-origin web app (subject to the rest of the CORS/auth setup), weakening origin isolation and increasing exposure to local malicious pages/tools.

**Mitigation:** Require an explicit non-local `WEB_ORIGIN` in production; fail startup for localhost/127.0.0.1 production origins unless explicitly approved. Keep development defaults only for non-production.

## Performance, reliability, and scalability observations

- OS draft create/update and settlement posting use serializable transactions and optimistic draft versions, which is appropriate for concurrent finance edits.
- Settlement posting rechecks batch eligibility, posted links, live components, coverage, and component bounds inside the transaction; this is a positive concurrency control.
- Linked-parcel mutation uses per-row `updatedAt` checks, but the missing address/status predicates remain an integrity issue and should be fixed in the same atomic operation.
- Saved draft listing is capped at 200; manifest/selection caps are enforced in routes/spec. No load test was run.

## Positive controls verified

- JWT verification checks issuer/audience through the token utility and reloads active user/token version server-side.
- Finance settlement endpoints require role checks, hub scoping, idempotency keys, and serializable posting transactions.
- Draft edits use expected-version compare-and-swap plus append-only edit audit records.
- Posted journals are reversed/compensated rather than silently overwritten in the reviewed flows.
- Backend TypeScript typecheck completed successfully.

## Unverified areas and follow-up checks

- No production PostgreSQL, proxy, cookie, secret-store, backup/restore, or observability configuration was exercised.
- Focused integration tests for linked parcel eligibility/address equality, OS settlement replay under concurrent requests, and CORS startup policy should be added/run.
- Review deployment manifests and runtime environment to confirm `WEB_ORIGIN`, JWT secrets, TLS, secure cookie flags, and database connection limits are explicitly set.
