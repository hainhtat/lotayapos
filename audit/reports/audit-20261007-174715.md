# Dispatch void and sorting focused audit

Timestamp: 2026-10-07 17:47:15 Asia/Yangon. Repository: `lotaya-pos`, HEAD `a5b89c2`, working tree modified.

## Scope and exclusions

Reviewed the new Dispatch void affordance and parcel sorting from React table to validated API, including `PROJECT_SPEC.md`, parcel service authorization and accounting guards, cache invalidation, Prisma indexes, and focused tests. This was a read-only code review; no database, production service, migrations, load checks, or full test suite were exercised. Concurrent working-tree changes may continue after this snapshot.

## Executive summary

No confirmed authorization bypass, cross-hub disclosure, or financial safeguard bypass was found in the new UI or sort parameters. Overall risk of this change is low. Two low-severity UX/reliability gaps remain.

## Findings

### DVS-01 — Low — stale operational summaries after void

Location: `frontend/src/components/void-parcel-dialog.tsx` lines 32–42; `frontend/src/features/dispatch/use-dispatch-data.ts` lines 26–42.

Evidence: successful void invalidates `parcels`, `batches`, `dashboard`, `os-accounts`, and `ledger`, but not `operations-batches` or `overdue-unsent`. Those keys feed the Dispatch batch dropdown and overdue count, and `operations-batches` also feeds All Batches. If these views remain mounted, they can show a pre-void count or amount until another refresh. Invalidate those keys on successful void.

### DVS-02 — Low — preview can invite an ineligible void

Location: `frontend/src/features/dispatch/dispatch-table.tsx` line 159; `backend/src/services/parcel.service.ts` lines 619–640.

Evidence: the UI offers void to an unassigned CREATED parcel without knowing whether it has historical assignment, delivery way, credit, or money activity. The preview returns balances without checking these eligibility conditions. The server rejects the eventual POST with 409, so money and history remain safe, but the user may enter a reason and confirm an action that cannot succeed. Consider returning eligibility and a specific blocking reason from preview, and disabling confirmation when blocked.

## Performance, reliability, and scalability observations

Server sorting is paginated with a stable `id` tie-breaker and an allowlisted set of `orderBy` fields. Relation sorts (shop/rider) may be more expensive at scale; query-plan review is appropriate only if parcel volume or latency warrants it. No new unbounded query was found in this path.

## Positive controls verified

- `POST /parcels/:id/void` and preview routes require authentication and Superadmin/Operations Manager role. The service reloads active actor scope and constrains parcel lookup to the actor's hub.
- The void service checks status, historical activity, settlement and account balances, cashbook state, and duplicate requests inside a serializable transaction; a balanced journal and status history are persisted together.
- The dialog displays current and projected OS balances, zeroing audit, and a required reason before submission; it reuses a UUID idempotency key during retry.
- Sort keys and directions are allowlisted by the API validator. Sort order is applied to the hub-scoped `where` query and cannot broaden it. Invalid keys receive validation errors.
- Focused API and frontend tests cover invalid sort parameters, paginated sorting, role-gated void UI, and preview display.

## Limitations and follow-up

No full test suite, database query plan, concurrent void stress test, or deployed environment was inspected. Run focused checks and manual UI review after any cache or preview change. This report is limited to the Dispatch void/sort change and is not a whole-repository security assessment.
