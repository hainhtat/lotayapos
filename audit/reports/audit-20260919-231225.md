## Current findings

### FIN-R01 — Medium — Posted OS amendment lacks deterministic concurrent-retry recovery

**Location:** `backend/src/services/finance/os-settlements.ts:453-553`.

**Evidence:** amendment performs a replay lookup before entering a Serializable transaction, but unlike `postOsSettlement`, `create/updateOsSettlementDraft`, and `createRiderSettlement`, it does not catch `P2002` or `P2034` and re-read the audit result. The optimistic `updateMany` prevents two amendments from both claiming the current version, but a database serialization/unique conflict can escape as an internal error.

**Failure scenario:** two identical amendment requests with the same key overlap. One commits; the other can fail with an unmapped Prisma error instead of returning the committed replacement or a stable 409.

**Impact:** duplicate money is prevented by the transaction and constraints, but the client receives an indeterminate response and an operator may retry with a new key.

**Mitigation:** wrap amendment in the same race-recovery pattern used by OS posting: on `P2002`/`P2034`, re-read `OsSettlementEditAudit`, verify the complete normalized amendment request, return the replacement if committed, otherwise return `RETRYABLE_CONFLICT`. Add a true concurrent PostgreSQL test.

### FIN-R02 — Medium — PostgreSQL-only cashbook lock is not covered by the PostgreSQL test runner

**Location:** `backend/src/services/finance/cashbook-policy.ts:10-19`; `backend/scripts/test-postgresql.mjs`.

**Evidence:** production executes `pg_advisory_xact_lock(hashtext(...))`, while SQLite skips that branch. The existing PostgreSQL runner does not include `cashbook-posting-workflow.test.ts` and contains no close-versus-post concurrency case.

**Failure scenario:** SQL/provider behavior, lock-key construction, or connection/transaction interaction differs in production. Local tests stay green because the branch is never executed.

**Impact:** a deployment could turn every financial posting into a 500, or fail to serialize close against posting as designed.

**Mitigation:** add the cashbook workflow to `test:postgresql` and test overlapping close-versus-expense, close-versus-adjustment, and close-versus-rider-settlement requests. Require this isolated PostgreSQL suite to pass before deployment.

### FIN-R03 — Medium — Direct cashbook postings are not attributable to an actor in durable finance data

**Location:** `backend/src/services/finance/cashbook-postings.ts:44-102`; `backend/prisma/schema.prisma:457-470`.

**Evidence:** the service authenticates the actor but stores only source type/key, hub, date, description, and lines. `JournalEntry` has no actor field and opening balance, transfer, and adjustment do not create a separate audit record. The idempotent replay comparison also cannot verify actor identity.

**Failure scenario:** two authorized Finance users perform or replay a correction. The ledger shows what changed and why, but cannot establish who initiated it without relying on transient application logs.

**Impact:** this violates the specification's requirement that monetary movements be attributable and weakens incident investigation/non-repudiation.

**Mitigation:** persist `actorId` on journal entries or create an immutable cashbook-command audit record linked to the journal; include actor identity in idempotent request equivalence; backfill or explicitly document legacy entries.

### FIN-R04 — Low — Set-based rider outstanding still loads unbounded historical receipt detail

**Location:** `backend/src/services/finance/rider-settlements.ts:240-333`.

**Evidence:** the N+1 pattern is removed, but the endpoint loads all active riders and all settlement rows with nested lines through the selected date, then sums them in application memory.

**Impact:** query count is stable, but payload-to-server memory and database transfer grow with the complete settlement history. Large organizations may see slow requests or pool pressure.

**Mitigation:** aggregate settlement lines by rider in the database, paginate riders, and add a high-volume query/latency regression test.

### FIN-R05 — Low — Settlement-chain history remains one query per version

**Location:** `backend/src/services/finance/os-settlements.ts:423-450`.

**Evidence:** correctness guards now cap and terminate traversal, but up to 200 sequential `findUnique` calls remain possible.

**Impact:** heavily amended statements can have avoidable latency; the request no longer risks an infinite loop.

**Mitigation:** fetch a bounded chain using recursive SQL in PostgreSQL or maintain/query a root-chain identifier.
