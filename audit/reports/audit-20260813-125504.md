## Executive summary

Overall risk posture for this slice is **Medium–High**. Preview/post correctly enforce `OS_SETTLEMENT_UNDER_COLLECTED` via `isOsSettlementCodCovered`, and post always re-enters that path through `previewOsSettlement` (no intentional client eligibility bypass). Prior returns are shop-keyed (not cross-shop). Residual money risk remains because **coverage is evaluated outside the serializable post transaction**, so concurrent settlements for the same shop can under-enforce prior returns. Draft eligibility deliberately ignores `priorSettledReturns`, so the UI can mark batches selectable when preview will reject them. Superadmin history without `hubId` is an intentional org-wide read, not a hub-user leak; Auditor “View” on the route is broken by `assertFinanceActor`. Deep-link hash handling can trap users on the settlements tab.

Finding counts: **Critical 0, High 1, Medium 4, Low 2**.

## Findings

### AUD-OS-01 — High — Under-collection gate is not re-checked inside the post transaction

**Location:** `backend/src/services/finance.service.ts` (`previewOsSettlement` ~568–612; `postOsSettlement` ~635–673)

**Evidence:** `postOsSettlement` calls `previewOsSettlement` (which aggregates prior `returnDeduction` and throws `OS_SETTLEMENT_UNDER_COLLECTED`) **before** opening the `Serializable` transaction. Inside the transaction it re-validates only batch completion and absence of `POSTED` settlement links—not prior shop returns or COD coverage. Concurrent posts for **different** batches of the **same** shop therefore do not serialize on the coverage read.

**Failure scenario:** Shop has two unsettled complete batches A and B. Individually each passes coverage given current prior returns. Two Finance sessions preview and post A and B nearly simultaneously. Both previews see the same prior total; both post succeed. After both journals exist, shop-level recovered advances/returns can exceed collected COD relative to the intended hardening rule, and wallet outflow / payable clearing can be overstated.

**Impact:** Money-integrity race: the new under-collection control can be bypassed without overlapping batch IDs, defeating the purpose of including `priorSettledReturns`.

**Mitigation:** Move prior-returns aggregation and `isOsSettlementCodCovered` into the same serializable transaction as settlement create (or take a shop-level advisory lock / version row). Add a concurrent integration test that posts two non-overlapping batch sets for one shop where the second must fail once the first’s returns are posted.

### AUD-OS-02 — Medium — Draft eligibility omits `priorSettledReturns` while preview/post enforce it

**Location:** `backend/src/services/finance.service.ts` (`listOsSettlementDrafts` ~486–517); UI `frontend/src/pages/settlement-workspaces.tsx` checkbox `disabled` uses `eligible`

**Evidence:** Drafts compute and return `priorSettledReturns` per shop, but call `isOsSettlementCodCovered` with only `{ collectedCod, advancePaid, returnedAdvance }` (comment: “Batch-local coverage first”). Preview/post pass `priorSettledReturns: priorReturns` and throw `409 OS_SETTLEMENT_UNDER_COLLECTED`.

**Failure scenario:** A shop already has large posted return deductions. A new complete batch has `collectedCod > advancePaid + returnedAdvance` batch-locally, so the draft row is `eligible: true` and selectable. Review then fails at preview.

**Impact:** Operators can prepare invalid statements; trust in the draft “eligible” badge erodes. Not a server-side money bypass (preview blocks), but a reliability/ops defect in the hardening surface.

**Mitigation:** Use the same coverage inputs for draft `eligible` / `underCollected` as preview (shop prior returns). Optionally show prior returns in the draft table and disable selection when shop-level coverage fails.

---

### AUD-OS-03 — Medium — Returned-advance status sets diverge between drafts and preview/post

**Location:** Draft reducer ~475–481 vs `osBatchComponents` ~541–545 in `finance.service.ts`

**Evidence:**

| Path | Statuses included in `returnedAdvance` |
| --- | --- |
| Drafts | `RETURNED`, `PENDING_RETURN` |
| Preview/post (`osBatchComponents`) | `RETURNED`, `CANCELLED` |

Complete-batch eligibility treats `PENDING_RETURN` as unresolved, so draft `PENDING_RETURN` counting mainly affects incomplete rows. For **complete** batches with `CANCELLED` parcels, drafts **omit** cancelled advances from `returnedAdvance` while preview **includes** them—changing coverage and statement defaults after selection.

**Failure scenario:** Batch is complete with cancelled advanced parcels. Draft may show covered/eligible; preview adds cancelled advances, fails under-collection or posts a larger return deduction than the draft implied.

**Impact:** Statement components and coverage disagree across the same workflow; operators cannot reconcile draft numbers to the immutable post payload.

**Mitigation:** Single shared component helper for draft, preview, and post. Align cancelled vs returned treatment with `PROJECT_SPEC.md` (RETURNED deductions vs cancelled pickup advances) and add a unit/integration fixture covering CANCELLED-only advances.

### AUD-OS-04 — Medium — Finance deep-link hash can force the settlements tab permanently

**Location:** `frontend/src/pages/finance-page.tsx` (`resolveFinanceTab`, `selectTab`, hash `useEffect`)

**Evidence:** `#os-settlements` / `#rider-outstanding` map to the settlements tab. `selectTab("overview")` clears `tab` search param but does **not** clear `location.hash`. The effect re-runs `resolveFinanceTab(searchParams, location.hash)` and, while the hash remains, forces `settlements` again.

**Failure scenario:** Dashboard deep link `/finance#os-settlements` opens settlements correctly. User clicks Overview; URL search updates but hash stays; tab snaps back to OS & riders.

**Impact:** Broken navigation after deep link; overview (pickup advances, ledger) becomes hard to reach without manually editing the URL. Test coverage only asserts open-from-hash, not return-to-overview.

**Mitigation:** On tab change, clear or rewrite the hash (`history.replaceState` / navigate without hash for overview; set `#os-settlements` / `#rider-outstanding` when entering those anchors). Add a regression test for Overview after hash entry.

### AUD-OS-05 — Medium — Auditor View on OS settlement list/detail is denied by service authz

**Location:** Routes allow `AUDITOR` on `GET /os-settlements` and `GET /os-settlements/:id`; `assertFinanceActor` only permits `SUPERADMIN` | `FINANCE` | `OPERATIONS_MANAGER` (`finance.service.ts` ~127–142, `listOsSettlements` / `getOsSettlement`)

**Evidence:** Spec matrix grants Auditor **View** for OS settlement / post capabilities. Route middleware includes `AUDITOR`; service `assertFinanceActor` rejects that role with `403 FORBIDDEN`.

**Failure scenario:** Read-only auditor opens Finance history (or calls the API) and receives forbidden despite route-level allowance.

**Impact:** Spec gap / broken control plane for audit review of settlement history; encourages sharing Finance credentials.

**Mitigation:** Extend read paths with an assert that allows Auditor (hub-scoped or granted scope per spec) while keeping post/preview/reversal closed. Align route and service role sets; add contract tests for Auditor GET success and POST deny.

### AUD-OS-06 — Low — Superadmin `listOsSettlements` without hub is org-wide by design (not a hub-user leak)

**Location:** `listOsSettlements` ~676–690; client history query omits `hubId` (`settlement-workspaces.tsx`; finance-page test expects no `hubId=`)

**Evidence:** For `role === "SUPERADMIN"` and no `input.hubId`, `hubId` stays undefined and the query returns up to 200 settlements across all hubs (optionally filtered by `shopId`). Non-superadmin callers always go through `resolveFinanceHub` and are hub-bound. Mutating preview/post still require Superadmin hub selection via `resolveFinanceHub`.

**Failure scenario:** Superadmin lands on settlements tab with empty shop filter and sees cross-hub history. Hub Finance users cannot reproduce this without privilege escalation.

**Impact:** Broader than most finance mutations’ `HUB_REQUIRED` pattern; acceptable for Superadmin “Full” if intentional, but easy to misread as a scope bug. Residual risk is accidental over-disclosure in shared Superadmin sessions / screenshots, not horizontal hub breach.

**Mitigation:** Document org-wide Superadmin history; optionally require hub for Superadmin list parity with preview/post, or label the UI “All hubs”. Keep hub enforcement for FINANCE / OPERATIONS_MANAGER (already present).

---

### AUD-OS-07 — Low — Prior settled returns are shop-scoped; no cross-shop attribution observed

**Location:** Draft aggregation ~438–454; preview aggregate ~578–585

**Evidence:** Prior `returnDeduction` sums are filtered by `shopId` (`in: shopIds` / `shopId: input.shopId`) and status `POSTED`. Draft maps totals with `priorReturnsByShop.get(batch.shopId)`. `OnlineShop` has no hub FK; shop-level (cross-hub for the same shop) aggregation matches comments and i18n (“previously settled returns for the shop”). Preview excludes settlements that already link any selected `batchIds` (redundant for unsettled batches, safe).

**Failure scenario (non-finding for wrong shop):** Settling shop A does not pull shop B’s returns.

**Residual nuance:** The same shop-wide prior total is echoed on every draft row for that shop (display double-count if an operator mentally sums the column). Draft eligibility still ignores the field (see AUD-OS-02). Not a ledger double-post by itself.

**Mitigation:** Treat prior returns as a shop statement header (once), not a per-batch additive column; keep shopId filters in tests.

## Performance / reliability / scalability observations

- History and drafts both `take: 200` with no cursor; large hubs can hide older unsettled batches / settlements without warning.
- Draft path loads full parcel graphs for up to 200 batches then aggregates priors in a second query—acceptable for current scale; watch N+1 if includes grow.
- Post uses `Serializable` and re-checks batch settlement links (good against same-batch double settle); coverage race in AUD-OS-01 remains the sharper reliability gap.
- Client disables cross-hub multi-select using draft `hubId`; server enforces shop+hub match on preview—good defense in depth.
- Editable deductions are capped to preview maxima; lowering `returnDeduction` cannot bypass the coverage gate (gate uses batch totals, not edited lines)—positive.

## Positive controls verified

- `isOsSettlementCodCovered` uses strict inequality (`collectedCod > recovered`); unit tests cover prior returns and equality failure (`business-rules.test.ts`).
- Preview/post throw stable `OS_SETTLEMENT_UNDER_COLLECTED` before journaling.
- `postOsSettlement` always invokes `previewOsSettlement` (no alternate post path that skips coverage).
- Idempotency replay compares shop, date, wallet, batch set, and component/adjustment fields (conflict on mismatch).
- Posted batch links + in-transaction duplicate-link check; cashbook open asserted inside the post transaction.
- Hub Finance actors cannot list outside hub; Superadmin mutating flows still require hub.
- Frontend disables under-collected drafts when API marks `ineligibleReason: "underCollected"`; deep link `#os-settlements` opens settlements tab.
- Reversal restricted to Superadmin/Finance with hub scope and reversing journal lines.
