# Lotaya POS / Delivery ERP Audit

**Audit timestamp:** 2026-08-11 00:24:56 +0630  
**Scope:** Independent review of the backend API, accounting model, web ERP, rider mobile app, tests, and deployment configuration.  
**Restriction:** No production source code or tests were modified.

## Executive Summary

**Release recommendation: DO NOT DEPLOY.** The project has a useful validated foundation, but several issues can produce incorrect money movement or make required workflows unusable in production. The most serious risks are PostgreSQL migration/deployment incompatibility, inconsistent linked-parcel accounting, incomplete Partial Return cash collection posting, and insecure production defaults.

## Prioritized Findings

### P0 — PostgreSQL deployment path is unsafe and unverified

The production schema is PostgreSQL-specific, but `/Users/heinhtetaung/Developer/lotaya-pos/backend/package.json` points `db:deploy:postgresql` at the shared `prisma/migrations` directory. The checked-in SQL migrations use SQLite syntax such as `DATETIME`, `BOOLEAN`, `TEXT` primary keys, and SQLite `ALTER TABLE` statements. The first migration also does not create the current `Zone`, `PackageAssignment`, `ParcelLinkGroup`, partial-return, or later cashbook-control structures. `migration_lock.toml` is absent. A clean PostgreSQL deployment is therefore likely to fail or produce a schema that does not match `/Users/heinhtetaung/Developer/lotaya-pos/backend/prisma/schema.postgresql.prisma`.

**Recommended mitigation:** create and test a PostgreSQL migration history from an empty database, keep provider-specific migration artifacts separate or generate a provider-correct baseline, run deployment in CI against PostgreSQL, and verify rollback/backup/restore procedures before release.

### P0 — Linked-parcel ledger and settlement amounts can disagree

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:126-141` creates an individual `DeliveryWay` and individual commission amount for every delivered parcel, then creates an additional linked-group commission journal. `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/finance.service.ts:120-128` calculates rider settlement fees and commission from each parcel's original `deliveryFee` and individual `DeliveryWay`. This does not use the adjusted base-plus-1,000-MMK linked-group fee and can double-count commission relative to the linked journal.

The regular collection API at `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/ledger.service.ts:136-154` also calculates per-parcel fees and has no linked-group branch. A caller can therefore post individual collection entries after the linked status transition has already posted a group collection entry.

**Recommended mitigation:** make linked-group collection and commission posting a single idempotent domain operation; derive settlement expectations from posted group journals or a persisted group settlement allocation; prevent per-parcel collection/commission posting for linked members; and add database-backed tests for mixed riders, duplicate requests, partial outcomes, and settlement totals.

### P0 — Partial Return records the shortfall but not the actual money collected

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:98-121` stores `actualCodCollected` and posts only the advanced shortfall offset. The delivery-collection service only accepts `DELIVERED` parcels at `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/ledger.service.ts:136-140`, so the actual COD collected for a `PARTIAL` parcel is not posted to a wallet or customer COD receivable. The result can understate cash and leave the double-entry ledger incomplete.

**Recommended mitigation:** post the actual partial collection in the same or an explicitly idempotent follow-up transaction, including wallet selection and COD/fee allocation; then post the bounded OS offset exactly once. Make settlement calculations consume these journal postings rather than only parcel fields.

### P0 — Production authentication can silently use a known JWT secret

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/config/env.ts:2-3` falls back to `development-only-secret-change-me` when `JWT_SECRET` is absent, regardless of `NODE_ENV`. The same configuration also defaults to a local SQLite database. A misconfigured production deployment could issue forgeable tokens or write to the wrong database.

**Recommended mitigation:** fail fast in production unless `JWT_SECRET`, `DATABASE_URL`, `DATABASE_PROVIDER`, and allowed origins are explicitly supplied; enforce a minimum secret length and reject development defaults; validate provider values instead of silently treating unknown values as SQLite.

### P1 — Web Partial Return action sends the wrong API field

`/Users/heinhtetaung/Developer/lotaya-pos/frontend/src/pages/operations-page.tsx:19` sends `{ toStatus: "PARTIAL" }`, while `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/controllers/parcel.controller.ts:4-12` and `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/validators/parcels.ts:14-20` require `status`. The UI's Partial Return workflow therefore fails validation instead of updating a parcel. The UI also exposes the action for `ASSIGNED`, although the backend transition table permits outcome updates only from `OUT_FOR_DELIVERY`.

**Recommended mitigation:** use one typed API contract for status updates, add a frontend regression test that submits the dialog and asserts the exact payload, and align UI eligibility with server transitions.

### P1 — Linked groups do not enforce a single rider or deterministic fee base

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/operations.service.ts:89-97` allows parcels already assigned to different riders to be linked, compares raw address strings, and selects the first database result's `deliveryFee` as the base. The query has no deterministic order. This can create a group whose delivery commission has no clear rider owner and whose fee depends on query order. The schema's `ParcelLinkGroup` also lacks hub, normalized-address, commission snapshot, or settlement-allocation fields.

**Recommended mitigation:** normalize and persist an address key, require one hub and one rider (or explicitly model multi-rider allocation), validate a configured/common base fee, snapshot the commission policy, and persist deterministic fee/commission allocations.

### P1 — Bulk assignment does not persist the assignment-history model

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/operations.service.ts:131-135` updates `Parcel` and creates `StatusHistory`, but does not create `PackageAssignment` rows even though the schema defines that model. The API therefore cannot reliably answer who assigned a parcel, when an assignment ended, or reconstruct assignment history.

**Recommended mitigation:** create an assignment-history row in the same transaction and add reassignment/end-assignment rules, unique active-assignment constraints, and database integration tests.

### P1 — Return timing does not implement the specified hub-calendar rule

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:103` computes `Date.now() + 4 * 24 hours`, not four hub-timezone calendar days. There is no manual extension endpoint, no authorization for extensions, and no server-side check preventing an early `PENDING_RETURN -> RETURNED` transition. The required return queue control is therefore advisory rather than enforced.

**Recommended mitigation:** store hub timezone and a due-date audit trail, calculate calendar boundaries in that timezone, add an authorized extension workflow, and reject return completion before the effective due time unless an approved override exists.

### P1 — Hub-scoped ledger reporting omits newer journal source types

`/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/ledger.service.ts:172-218` only resolves scope for a limited set of source types. Partial-return adjustments, linked delivery/commission entries, cashbook opening balances, transfers, and adjustments are not resolved by `entryInScope`, so non-Superadmin hub users can receive incomplete ledger reports or be denied valid reversal scope.

**Recommended mitigation:** persist `hubId` or an accountable resource reference on every journal entry and use one central scope resolver for all source types. Add cross-hub report and reversal integration tests.

### P1 — No brute-force controls or hardened browser token boundary

There is no authentication rate limiting, account lockout, or abuse telemetry. The web app stores JWTs in `localStorage` at `/Users/heinhtetaung/Developer/lotaya-pos/frontend/src/lib/api.ts:1-14`, while the API also emits a cookie without `Secure` at `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/controllers/auth.controller.ts:2`. A frontend XSS or compromised browser context can read the bearer token, and production cookie transport is not hardened.

**Recommended mitigation:** prefer an HttpOnly, Secure, appropriately scoped cookie or a short-lived access token with refresh-token rotation; add CSRF protection if cookies are used; add rate limits, login audit events, and security headers such as Helmet.

### P1 — Alerts are transactional records only, not real-time delivery

The backend creates alerts for Partial and Failed outcomes, but the only exposed read path is polling `GET /operations/alerts` with a fixed `take: 50` in `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/operations.service.ts:67-69`. There is no acknowledgement endpoint, WebSocket/SSE transport, outbox, retry, or delivery cursor. Operations may miss alerts and cannot reliably process more than the latest 50.

**Recommended mitigation:** add an outbox/event record in the same transaction, a retryable delivery mechanism, acknowledgement APIs, pagination/cursors, and monitoring for undelivered events.

### P1 — Scope and selection behavior makes the dispatch UI unreliable at scale

The API caps parcel results at 100 in `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:89`; the frontend filters rider name locally at `/Users/heinhtetaung/Developer/lotaya-pos/frontend/src/pages/operations-page.tsx:17` and uses a manually typed rider ID. There is no server-side rider-name filter, pagination, stable selection model, or rider lookup. Selection can become stale when filters change, and the UI enables parcels that the server later rejects because it only treats `CREATED` and `PICKED_UP` as assignable.

**Recommended mitigation:** add cursor pagination, server-side filters, a scoped rider endpoint/select, stable selection invalidation, and one shared eligibility contract.

### P1 — Mobile linked-parcel grouping is not aligned with the API response shape

The mobile type and screens expect `linkedParcelGroupId`/`linkedParcelCount` at `/Users/heinhtetaung/Developer/lotaya-pos/mobile/src/lib/api.ts:4` and `/Users/heinhtetaung/Developer/lotaya-pos/mobile/app/(tabs)/index.tsx:11`, while the backend parcel list includes a nested `linkGroup` object at `/Users/heinhtetaung/Developer/lotaya-pos/backend/src/services/parcel.service.ts:89`. Without a mapper or contract change, linked groups may not be visually grouped for riders.

**Recommended mitigation:** publish a shared versioned response contract or map the nested backend shape in the mobile API client, then add a rendered mobile test for linked group visibility.

### P2 — Duplicate Expo Router route directory creates routing ambiguity

Both `/Users/heinhtetaung/Developer/lotaya-pos/mobile/app/(tabs)/` and `/Users/heinhtetaung/Developer/lotaya-pos/mobile/app/'(tabs)'/` exist. The latter contains literal quote characters in the directory name and duplicates the tab routes. This is a packaging and navigation risk that is not caught by the current pure utility tests.

**Recommended mitigation:** remove the literal-quote duplicate, export or launch the native app in CI, and add a route smoke test.

### P2 — Lint and production observability gates are incomplete

None of the three applications currently has a completed, executable lint gate. The project also lacks verified production backups, restore drills, metrics, structured error monitoring, and end-to-end/device QA. These are required for a cash-handling production system even though typechecks and focused unit tests pass.

**Recommended mitigation:** add checked-in ESLint flat configs, run lint in CI, configure structured logs/metrics/error tracking, encrypt and restore-test PostgreSQL backups, and add E2E/device workflows for authentication, dispatch, delivery, settlement, close, and reopen.

## Positive Controls Observed

- Express validation exists for the principal public payloads.
- Parcel status updates use an optimistic status predicate and transactional status history.
- Journal line construction includes a balanced-entry invariant and several idempotency keys.
- Hub and rider scope checks are present on parcel operations and most finance paths.
- Focused tests cover settlement arithmetic, reason requirements, authorization contracts, partial COD arithmetic, dispatch eligibility, PDF generation, and linked-fee calculation.
