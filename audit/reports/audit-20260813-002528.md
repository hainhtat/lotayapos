- Dispatch multi-rider manifest PDF (`POST /operations/parcels/manifest`)

**Focus:** authz, money integrity (COD after advance, commission from rider bps / pay model, status-override side-effects), mass assignment, unbounded lists, PDF/export risks, hub scope.

**Excluded:** full cashbook redesign, mobile rider app hardening, prior fee-bulk-update findings except residual risk, load testing, production secret review.

## Executive summary

Overall posture for this slice is **high financial integrity risk**. Hub scoping, role gates, COD-after-advance blocking, and optimistic status locks on parcel edit are present. However, salary riders are still charged the env commission fallback, status overrides post money without compensating reversals when corrected again, and delivery-fee edits remain open after advance on `ASSIGNED` parcels. Manifest generation is hub-scoped but unbounded by parcel count.

**Finding counts:** **1 Critical** · **3 High** · **4 Medium** · **1 Low**

## Findings (by severity)

### CRITICAL-PAY-01 — `SALARY` riders still earn env commission; pay model unused at posting/settlement

**Risk:** Critical  
**Location:** `backend/src/services/parcel.service.ts` (`resolveCommissionRateBps`, `updateStatus`); `backend/src/services/finance.service.ts` (`settlementWork` → `calculateRiderSettlementTotals(..., env.riderCommissionRateBps)`); `backend/src/services/ledger.service.ts` (`postDeliveryCollection` linked commission); `backend/tests/business-rules.test.ts` (asserts `resolveCommissionRateBps(0)` falls back to env > 0); `backend/src/services/master-data.service.ts` (`normalizeRiderPayFields` sets `commissionRateBps: 0` for `SALARY`)  
**Evidence:** Commission posting uses only `parcel.rider?.commissionRateBps` and never reads `payModel` or `monthlySalary`. `resolveCommissionRateBps` treats `0`/`null` as “use `env.riderCommissionRateBps`” (default 1000 bps / 10%). Salary riders are normalized to `commissionRateBps: 0`, so every `DELIVERED` outcome posts `RIDER_COMMISSION` at the env rate and creates non-zero `DeliveryWay.commissionAmount`. Settlement expected remittance subtracts that commission (`cod + fees - commission`) and never deducts `monthlySalary`. Linked-group settlement/collection paths recompute commission from **env** bps, ignoring per-rider rates entirely.  
**Impact:** Salary riders are underpaid on salary (no remittance deduction / cashbook salary line) and overpaid via phantom percentage commission; hub remittance and ledger expense/payable are wrong every delivery day. Operators configuring `SALARY` in Settings receive false assurance that commission is off.  
**Mitigation:** Resolve commission as: if `payModel === "SALARY"` → 0; if percentage-bearing → require positive rider bps (no silent env fallback for persisted riders); keep env only as bootstrap default for legacy rows lacking a rider rate with an explicit audit flag. Apply salary deduction in settlement/cashbook per `PROJECT_SPEC.md` §6.7. Fix unit tests that currently encode the env fallback for `0`. Add integration coverage for `SALARY` vs `PERCENTAGE` deliver → settle.

### HIGH-OVERRIDE-02 — Status override posts money but never reverses prior journals on correction

**Risk:** High  
**Location:** `backend/src/services/parcel.service.ts` (`updateStatus`)  
**Evidence:** On transition/override **to** `DELIVERED`, code may create `RIDER_COMMISSION` (idempotent per parcel source key) and complete/create a `DeliveryWay`. On override **to** `PARTIAL`, it may create `PARTIAL_RETURN_COLLECTION` and `OS_PARTIAL_RETURN_ADJUSTMENT` (also create-if-missing). On override **away** from those statuses (e.g. `DELIVERED` → `FAILED`, `PARTIAL` → `OUT_FOR_DELIVERY`, `RETURNED` → `CREATED`), the handler only updates `parcel.status` + `statusHistory`. It does not reverse journals, clear `actualCodCollected` / shortfall fields, or reopen ways. Spec requires money side-effects for the destination status and corrections via reversals / compensating entries, not silent status rewrites that leave ledger orphans. ERP UI and bulk multi-edit can perform these overrides with a canned note (`Ops correction`).  
**Impact:** Ledger shows commission expense/payable or partial collections after the parcel is no longer delivered/partial; rider settlement drops the parcel (status filter) while journals remain—cashbook/day-close and OS offsets diverge from operational truth. Re-entering `DELIVERED`/`PARTIAL` often **skips** re-posting because of existing source keys, so operators cannot “fix forward” without Finance reversals they may not know to run.  
**Mitigation:** On any override that invalidates a prior money event, require Finance-authorized reversal (or auto-call the existing ledger reversal path) inside the same serializable transaction before applying the new status. Block overrides that would orphan journals when the cashbook day is closed. Surface “money attached” warnings in Operations UI. Add regression tests for `DELIVERED→FAILED` and `PARTIAL→OFD` ledger invariants.

### HIGH-FEE-03 — Township / delivery-fee edit allowed on `ASSIGNED` after advance; only COD is gated

**Risk:** High  
**Location:** `backend/src/services/parcel.service.ts` (`updateParcel`); `backend/src/validators/parcels.ts`  
**Evidence:** `editableStatuses` includes `ASSIGNED`. `ADVANCE_POSTED` is checked only when `codAmount` is present in the patch. Changing `townshipId` recomputes and writes `deliveryFee` from the township master even after `BATCH_PICKUP_ADVANCE` exists. No field-level audit trail is written. Manifest PDF and later commission use the live `deliveryFee`.  
**Impact:** Dispatchers/ops can inflate or zero fees on already-assigned parcels after OS advance posting, changing rider commission bases and remittance expectations without Finance review or attributable history. Manifests downloaded before/after the edit disagree for the same assignment set.  
**Mitigation:** Block fee/township (and preferably all money-affecting) edits once advance is posted or once status ≥ `ASSIGNED`, unless Superadmin/Finance posts a compensating adjustment. Persist before/after audit. Cap fee/COD maxima. Extend concurrency tests for `ASSIGNED` + advance-posted fee denial.

### HIGH-BULK-04 — Client-side bulk status override amplifies money side-effects without atomicity

**Risk:** High  
**Location:** `frontend/src/pages/operations-page.tsx` (`applyStatusBulk`); `backend/src/services/parcel.service.ts` (`updateStatus`)  
**Evidence:** Multi-edit loops selected parcels and issues sequential `POST /parcels/:id/status` with `note: "Ops correction"` and optional reason codes. There is no server bulk status API, no single transaction across the selection, and no confirmation that distinguishes lifecycle vs override (including jumps to `DELIVERED` / `FAILED` / `REJECTED` / `RETURNED`). Each successful call independently posts commission or exception side-effects. Authz correctly limits callers to Superadmin / Ops Manager / Dispatcher (hub-scoped), matching the spec’s ERP override roles—but blast radius is large.  
**Impact:** Partial multi-edit failure leaves a mixed status set with some commissions posted and others not; a mistaken bulk “DELIVERED” can create many `RIDER_COMMISSION` journals in seconds. Canned notes weaken attribution required by the spec.  
**Mitigation:** Add a server bulk status endpoint with atomic-or-all-or-nothing policy (or explicit per-id results), require a free-text override reason for non-lifecycle transitions (reject canned-only notes), confirm money-impacting targets in UI, and rate-limit / cap selection size for override-to-delivered.

### MEDIUM-MANIFEST-05 — Manifest export is hub-scoped but unbounded by parcel volume

**Risk:** Medium  
**Location:** `backend/src/services/operations.service.ts` (`buildManifestForRiders`); `backend/src/utils/manifest-pdf.ts`; `backend/src/validators/operations.ts` (`riderIds` max 50)  
**Evidence:** Rider IDs are capped at 50 and hub-filtered for non-superadmin, but `parcel.findMany` has **no `take` limit** for statuses `ASSIGNED` | `OUT_FOR_DELIVERY` | `PICKED_UP`. PDF is built fully in memory (string pages → `Buffer`) including customer name/phone/address and COD totals. Filename uses rider id(s) only (no business-date scoping).  
**Impact:** A busy hub or stuck backlog can produce multi‑MB PDFs, high memory/CPU on the API process, and large PII/COD exports via a single authorized click—availability and data-exfil risk for a compromised Dispatcher token.  
**Mitigation:** Enforce a hard parcel cap (e.g. 500–2000) or require date filters; stream/paginate PDF generation; audit log manifest downloads (actor, riderIds, parcelCount); consider excluding phone/address columns behind a privilege flag if not needed on paper.

### MEDIUM-PAGE-06 — Dispatch queue defaults to first 50 parcels with no pagination UI

**Risk:** Medium  
**Location:** `frontend/src/pages/operations-page.tsx` (parcels query omits `page`/`pageSize`); `backend/src/services/parcel.service.ts` (`listParcels` default `pageSize: 50`, max 100)  
**Evidence:** Backend pagination exists and is bounded, but the Operations dispatch UI never sends page params and displays `visible.length` as “records,” implying completeness. Bulk assign/status/manifest rider prefill operate only on the loaded page. `GET /operations/batches` still returns all hub batches with embedded parcel status arrays unbounded.  
**Impact:** Operators may believe they assigned or status-corrected an entire filter set when only the newest 50 rows were affected—operational under-dispatch and inconsistent manifests. Batch list payload grows without bound as history accumulates (performance).  
**Mitigation:** Add pagination / “load more” / total from `pagination.total`; warn when `total > pageSize`; paginate or summarize batch list.

### MEDIUM-AUDIT-07 — Parcel field edits lack attributable history

**Risk:** Medium  
**Location:** `backend/src/services/parcel.service.ts` (`updateParcel`)  
**Evidence:** Successful PATCH updates columns only. Unlike status/assignment flows, there is no `statusHistory` or field audit for COD (pre-advance), customer PII, township, or fee changes. Spec requires money and operational corrections to be attributable and timestamped.  
**Impact:** Disputes over sticker/manifest COD/fee values or insider PII edits cannot be reconstructed from server history.  
**Mitigation:** Append immutable before/after audit events for every successful money/PII field change.

### MEDIUM-LINK-08 — Linked-group commission paths ignore rider bps / pay model

**Risk:** Medium  
**Location:** `backend/src/services/finance.service.ts` (`calculateRiderSettlementTotals`); `backend/src/services/ledger.service.ts` (`postDeliveryCollection`); contrast `updateStatus` way allocation using `resolveCommissionRateBps`  
**Evidence:** Non-linked ways store commission from rider/env resolution at delivery time. Linked groups recompute settlement and collection commission with `env.riderCommissionRateBps`, which can disagree with per-rider `commissionRateBps` and with `DeliveryWay` allocations written at delivery.  
**Impact:** Linked deliveries settle and post ledger commission at a different rate than single-parcel deliveries for the same rider—systematic remittance/ledger drift.  
**Mitigation:** Use the delivering rider’s resolved pay-model rate (or stored way rates) consistently for linked settlement and `LINKED_RIDER_COMMISSION` posting.

### LOW-ASSIGN-09 — Mass assignment on parcel PATCH is contained

**Risk:** Low (positive control with residual note)  
**Location:** `backend/src/controllers/parcel.controller.ts`; `backend/src/validators/parcels.ts`; `backend/src/services/parcel.service.ts`  
**Evidence:** Controller passes `req.body`, but the service only copies an explicit allowlist (`orderId`, `customerName`, `customerPhone`, `address`, `codAmount`, `townshipId`, `zoneId`). Validators reject empty bodies and constrain types. Status/riderId/advanceAmount cannot be smuggled through PATCH. Residual: unknown keys are ignored rather than rejected (harder to detect client bugs).  
**Impact:** Negligible privilege escalation via PATCH mass assignment.  
**Mitigation:** Optionally reject unknown keys strictly; keep allowlist.

## Performance / reliability / scalability observations

- Manifest PDF: O(parcels) memory; no streaming; multi-rider sections each rewind headers—acceptable for small manifests, risky when unbounded (MEDIUM-MANIFEST-05).
- `listBatches` embeds all parcel statuses for every batch—N parcels loaded for sidebar filters on dispatch page.
- Status updates use serializable transactions with P2034 retry—good for single-parcel races; bulk client loops forfeit that atomicity (HIGH-BULK-04).
- Parcel list `pageSize` capped at 100—good; UI does not use it (MEDIUM-PAGE-06).
- `updateParcel` now uses `updateMany` with `status in editableStatuses`—prior TOCTOU finding from `audit-20260812-230847.md` appears mitigated for status races.

## Positive controls verified

- Hub scope on parcel list/detail/history/update/status (non-superadmin), bulk assign, reassign, and manifest rider selection.
- Route role gates: parcel PATCH/status and operations dispatch endpoints deny-by-default via `requireRoles`.
- COD edit rejected after `BATCH_PICKUP_ADVANCE` (`ADVANCE_POSTED`).
- `remainingToOs` is signed (`totalCod - advancePaid`), not clamped—aligns with spec negative-receivable rule.
- Override roles match spec (Superadmin / Operations Manager / Dispatcher); riders cannot override.
- Override note required server-side for non-lifecycle transitions; reason codes validated for PARTIAL/FAILED/REJECTED.
- Manifest riderIds uniqueness + max 50; bulk assign max 500 parcels; parcel list pageSize max 100.
- Zone edits validate township + batch hub membership.
