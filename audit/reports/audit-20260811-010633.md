## Current findings

### CRIT-DB-01 — PostgreSQL deployment still uses a SQLite migration history

**Location:** `backend/package.json`, `backend/prisma/migrations/migration_lock.toml`, `backend/prisma/migrations/**/*.sql`  
**Evidence:** `db:deploy:postgresql` selects the PostgreSQL schema but still points Prisma at the only migration history, which is locked to `provider = "sqlite"` and contains SQLite-specific DDL. There is no PostgreSQL-native baseline/history. Schema validation passes because it does not execute migrations.  
**Impact:** A clean production PostgreSQL deployment is not supported and will fail provider validation or DDL execution. Recovery into a fresh production database is unproven.  
**Mitigation:** Create a PostgreSQL-native migration chain and verify `migrate deploy` from empty in CI, including schema drift and backup/restore tests.

### HIGH-OPS-01 — Rider app still cannot start a delivery way

**Location:** `mobile/app/(tabs)/index.tsx`, `mobile/app/parcel.tsx`, `backend/src/services/parcel.service.ts:8`, `backend/src/routes/v1/parcel.routes.ts`  
**Evidence:** Assigned work normally has status `ASSIGNED`. Mobile immediately offers `DELIVERED`, `PARTIAL`, `FAILED`, and `REJECTED`, all of which the server permits only from `OUT_FOR_DELIVERY`. There is no mobile start action and no `/parcels/:id/ways` or equivalent route to perform `ASSIGNED -> OUT_FOR_DELIVERY`.  
**Impact:** The primary rider outcome workflow returns `INVALID_STATUS_TRANSITION` for normally assigned parcels.  
**Mitigation:** Implement an idempotent start-way command, expose it in mobile, and integration-test the full assigned → out-for-delivery → outcome journey.

### HIGH-FIN-02 — Commission is not posted to the ledger and linked way records disagree with settlement

**Location:** `backend/src/services/parcel.service.ts:139-142`, `backend/src/services/finance.service.ts:10-25,139-153`, `backend/src/services/ledger.service.ts:145-177`  
**Evidence:** Delivery creates one `DeliveryWay` per parcel using each parcel's full fee. For a completed linked group, settlement ignores those recorded amounts and recomputes group commission from `totalDeliveryFee`. Neither regular nor linked delivery posts `RIDER_COMMISSION_EXPENSE` or a commission payable/clearing line; the canonical collection journal records wallet, advance/COD payable, and fee revenue only.  
**Failure scenario:** Two linked 3,000-MMK parcels produce two way records based on 3,000 each, while settlement uses the adjusted 4,000 group fee; no journal exposes the commission expense behind either total.  
**Impact:** Way-level audit evidence, settlement arithmetic, and the double-entry ledger disagree; exact financial totals cannot be drilled down or reversed as required.  
**Mitigation:** Snapshot and allocate adjusted group commission once, update way/group records consistently, and post a balanced, idempotent commission expense/payable journal used by settlement.

### MED-SEC-01 — Public self-registration remains enabled

**Location:** `backend/src/routes/v1/auth.routes.ts`, `backend/src/services/auth.service.ts`  
**Evidence:** `POST /auth/register` is unauthenticated and directly creates a default-role user. No production feature flag, invitation, or admin authorization is checked.  
**Impact:** External users can create uncontrolled identities and consume database/bcrypt resources, contrary to the specification's authorized onboarding requirement.  
**Mitigation:** Disable public registration in production; require an expiring invite/admin command and audit creation.

### MED-SEC-02 — Login has no rate limiting or abuse telemetry

**Location:** `backend/src/app.ts`, auth routes  
**Evidence:** The middleware chain has no IP/identity limiter, bounded backoff, lockout policy, or login security events.  
**Impact:** Online password guessing and bcrypt-driven resource exhaustion remain possible.  
**Mitigation:** Add proxy-aware per-IP and per-account throttles, bounded backoff, and observable security events.

### MED-FIN-03 — Cashbook journal sources remain omitted from hub-scoped ledger reports

**Location:** `backend/src/services/finance.service.ts:83-134`, `backend/src/services/ledger.service.ts:227-245`  
**Evidence:** Opening balances, transfers, and adjustments receive random source IDs with no hub/resource association. `entryInScope` does not recognize `CASHBOOK_OPENING_BALANCE`, `CASHBOOK_TRANSFER`, or `CASHBOOK_ADJUSTMENT`.  
**Impact:** Non-superadmin finance/auditor users cannot see or reverse these wallet movements in their hub ledger even though they affect cashbook balances.  
**Mitigation:** Store hub scope directly on every journal entry and filter by it in SQL; add scoped report/reversal tests for all cashbook source types.

### MED-REL-04 — Return deadline and extension controls remain incomplete

**Location:** `backend/src/services/parcel.service.ts:104`, parcel routes  
**Evidence:** `PENDING_RETURN` uses a fixed `Date.now() + 4*24h`, not four hub-timezone calendar days. No extension endpoint, extension audit record, or due-date enforcement exists.  
**Impact:** Deadlines drift across timezone/DST rules, and operations cannot perform the specified controlled extension workflow.  
**Mitigation:** Persist hub timezone, calculate calendar deadlines, and implement authorized/audited extensions and due-date enforcement.

### MED-REL-05 — Assignment lifecycle has no reassignment/active-row integrity control

**Location:** `backend/src/services/operations.service.ts`, `backend/prisma/schema.prisma` (`PackageAssignment`)  
**Evidence:** Bulk assignment creates history, but there is no path to close it using `endedAt`/`endedById`, no reassignment reason flow, and no database guarantee of only one active assignment per parcel.  
**Impact:** Reassignment requirements are absent and future/manual concurrency can create conflicting active history.  
**Mitigation:** Add a transactional reassignment command that closes the previous record and enforce one active assignment per parcel with provider-appropriate integrity controls.

### LOW-SEC-01 — Token delivery mixes localStorage and a non-Secure cookie

**Location:** `backend/src/controllers/auth.controller.ts`, `frontend/src/lib/api.ts`, `backend/src/middleware/auth.ts`  
**Evidence:** The API returns the bearer token in JSON and sets it as an HttpOnly cookie without `Secure`; the web client stores the JSON token in `localStorage`. Cookie authentication is accepted on writes without a CSRF token.  
**Impact:** Depending on deployment, credentials have avoidable XSS, transport, and CSRF exposure.  
**Mitigation:** Select one hardened auth boundary; for cookies require HTTPS, `Secure`, strict origin/CSRF controls, and do not also persist the token in localStorage.

### LOW-PERF-02 — Dispatch silently caps while ledger reads remain unbounded/N+1

**Location:** `backend/src/services/parcel.service.ts:89`, `backend/src/services/ledger.service.ts:250-270`  
**Evidence:** Parcel listing returns at most 100 records without cursor/total. Ledger reporting loads all entries, then performs resource lookups per entry to determine hub scope.  
**Impact:** Dispatchers can miss eligible parcels; ledger latency, memory, and query count grow with history.  
**Mitigation:** Add cursor pagination and totals, persist journal hub scope, filter in SQL, and apply bounded report pagination.
