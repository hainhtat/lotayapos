## Executive summary

Overall posture for the reviewed slice is **moderate risk**. Role and hub scoping, non-negative integer wallet validation, a unique rider/date settlement constraint, serializable posting transaction, balanced journal construction, declaration evidence, cashbook close guard, and dark-mode primitives are present. No Critical or High vulnerability was confirmed.

The most important correctness risk is that rider work totals are calculated before the serializable transaction begins. A parcel delivery or correction racing the post can therefore produce a successfully committed settlement based on a stale work set. The OS planner also returns the newest 200 batches rather than the unsettled set, which can silently hide older liabilities, and the rider outstanding endpoint amplifies database queries per rider.

**Finding counts:** Critical 0, High 0, Medium 3, Low 2.

## Findings

### AUD-20260813-01 — Medium — Settlement totals can be stale at commit

**Location:** `backend/src/services/finance.service.ts:373-417`

**Evidence:** `settlementWork()` is called at lines 377-378 before `prisma.$transaction()` begins at line 379. The serializable transaction consequently protects the existing-settlement check, declaration verification, settlement, and journal writes, but not the parcel/status/way rows used to derive COD, fees, commission, and salary-adjusted expected remittance.

**Failure scenario:** A parcel is delivered, reversed, reassigned, or financially corrected after `settlementWork()` reads it but before the settlement commits. The unique rider/date guard still permits the first settlement, so the day can be locked with a journal whose expected receivable reflects the earlier work set.

**Impact:** Incorrect rider receivable, variance, wallet reconciliation expectations, and manual follow-up/reversal work. This is a financial-integrity race rather than a confidentiality issue.

**Mitigation:** Execute settlement-work reads using the transaction client inside the same serializable transaction, and add a concurrency regression test that mutates an eligible parcel between calculation and post. Where supported, lock or version the contributing delivery events and reject/retry on change.

### AUD-20260813-02 — Medium — Prior-batch planner can silently omit unsettled liabilities

**Location:** `backend/src/services/finance.service.ts:151-179`

**Evidence:** The query orders all scoped batches newest-first and applies `take: 200`; it does not filter on a persisted settlement state or unresolved financial balance. Each selected batch eagerly loads every parcel.

**Failure scenario:** A shop or hub with more than 200 recent batches has an older unresolved/partially settled batch. The planner returns a successful response without that batch, giving staff no indication that the result is truncated.

**Impact:** Previous advances, returns, or OS settlement obligations may be missed during reconciliation. The result is especially risky if users treat this read-only planner as a complete outstanding statement.

**Mitigation:** Model explicit OS settlement/draft state, query unsettled obligations rather than recent batches, paginate with totals and a continuation cursor, and show truncation/count metadata. Keep posting in the dedicated auditable OS settlement workflow required by the specification.

### AUD-20260813-03 — Medium — Rider outstanding query scales as a database burst

**Location:** `backend/src/services/finance.service.ts:122-148`

**Evidence:** All active scoped riders are loaded without pagination. For every rider, `settlementWork()` issues rider and parcel queries, then declaration and settlement queries are issued; all rider promises run concurrently.

**Failure scenario:** A large hub or Superadmin request over hundreds or thousands of riders creates several concurrent queries per rider, including nested linked-group parcel data. This can exhaust a PostgreSQL connection pool, increase memory use, and degrade unrelated dispatch/finance requests.

**Impact:** Slow or failed Finance pages and wider API latency during reconciliation periods.

**Mitigation:** Paginate riders, aggregate daily delivery totals server-side in bounded queries, batch declaration/settlement lookups, and cap concurrency. Add query-count/performance coverage representative of a large hub.

### AUD-20260813-04 — Low — Settlement POST is duplicate-safe but not retry-idempotent

**Location:** `backend/src/routes/v1/finance.routes.ts:17`; `backend/src/services/finance.service.ts:379-389`; `backend/prisma/schema.prisma:361-374`

**Evidence:** The database unique constraint prevents two settlements for the same rider/date, but the API accepts no idempotency key. A client retry after an ambiguous timeout returns `409 SETTLEMENT_EXISTS` rather than the result of the original equivalent request.

**Impact:** Duplicate money is prevented, but operators cannot distinguish a successful first post from a conflicting different post without reloading and comparing details. This increases manual reconciliation risk under poor connectivity.

**Mitigation:** Accept a scoped idempotency key, persist request identity/fingerprint, and return the original result for identical retries while rejecting key reuse with different content.

### AUD-20260813-05 — Low — Finance tables are operable but not adaptively responsive

**Location:** `frontend/src/pages/settlement-workspaces.tsx:22-25`

**Evidence:** Both tables use fixed minimum widths (`760px` and `900px`) inside horizontal scroll containers. The mobile shell itself provides a seven-item icon navigation and bottom padding, and modal fields collapse below `sm`, but the primary Finance data remains desktop-table shaped on a 320–390px viewport.

**Impact:** Mobile users must pan horizontally to compare rider or batch financial fields, increasing entry/comparison errors. This is usability risk, not a security defect.

**Mitigation:** Render compact cards or prioritized columns with expandable details below the tablet breakpoint; preserve table view for larger screens. Add English and Myanmar viewport tests, including long Myanmar labels and modal keyboard/focus behavior.

## Performance, reliability, and scalability observations

- The OS planner caps batch count but not parcels per included batch; a pathological 200-batch result may still be large.
- Frontend production build reports a 553.56 kB minified JavaScript chunk (159.66 kB gzip). Route-level code splitting would reduce initial load but this was not classified above as a production defect without measured load targets.
- The manual-payment UI defensively normalizes unexpected query payloads to empty arrays, avoiding the prior render crash.
- The new tables provide horizontal overflow containment, so they should not expand the viewport even though the layout is not truly adaptive.

## Positive controls verified

- Routes require authentication and restrict rider-outstanding, OS drafts, and settlement posting to `SUPERADMIN`, `FINANCE`, and `OPERATIONS_MANAGER`.
- Backend re-fetches the actor and verifies active status, role consistency, and non-Superadmin rider/batch hub scope.
- Wallet amounts are constrained to non-negative integers in both route validation and service logic.
- Manual settlement requires either a current declaration or a manual-entry reason; wallet mismatches require a variance reason.
- Settlement, wallet lines, balanced journal, and declaration verification occur in one serializable transaction.
- `Settlement` has a unique `(riderId, businessDate)` constraint, and cashbook-day close blocks later settlement posting.
- Dark mode declares appropriate document `color-scheme`, root/body colors, table text, control colors, option colors, and placeholder colors. The reviewed Finance panels have explicit dark backgrounds/text.
- Frontend API payloads are rendered through React, not raw HTML injection.
