# Finance Refactor Production Audit

**Timestamp:** 2026-09-19 18:29:02 +0630 (Asia/Yangon)  
**Repository context:** `main` at `d995991`; audit performed against a dirty working tree containing the in-progress Finance decomposition and deletion of `backend/src/services/finance.service.ts`.

## Scope and exclusions

Reviewed `PROJECT_SPEC.md`; Finance routes, controller, validators, authorization, and extracted services under `backend/src/services/finance/`; migrated production callers; relevant Prisma constraints; and Finance tests. Traced rider settlement, OS settlement/draft/amendment/reversal, OS returns, expenses, cashbook posting, cashbook close/reopen, hub scope, idempotency, and ledger balance controls.

No production code, tests, schema, configuration, dependencies, or product documentation were modified. PostgreSQL-specific integration tests were not run because they require an external database. No migrations, seeds, production services, load tests, or external requests were run.

## Executive summary

The refactor materially improves ownership: production callers no longer import the deleted monolith, authorization and cashbook policy have explicit modules, journal-affecting operations remain transactional, and unique constraints protect the most important settlement identifiers. No Critical vulnerability was found and no refactor-specific authorization bypass was identified.

Deployment is **not recommended yet**. One High financial-integrity issue remains: three cashbook monetary commands have no idempotency contract and can duplicate postings on an ordinary client retry. Four Medium reliability/scalability risks should be scheduled, especially deterministic handling of concurrent idempotent retries and the rider-outstanding N+1 query pattern. An uncontended full-suite run is also required: the audit full run had three failures while another test agent was active against shared test state; both affected suites passed in isolation.

Finding counts: **Critical 0, High 1, Medium 4, Low 2**.

## Findings

### FIN-001 — High — Cashbook monetary commands can be posted more than once

**Location:** `backend/src/routes/v1/finance.routes.ts:51-53`; `backend/src/validators/finance/cashbook.ts:7-9`; `backend/src/services/finance/cashbook-postings.ts:45-72`.

**Evidence:** opening balance, wallet transfer, and cashbook adjustment routes do not accept an idempotency key. `postCashbookJournal` generates a fresh random `sourceId` for every request, so the database uniqueness rule on `(sourceType, sourceId)` cannot detect a retry.

**Failure scenario:** the browser, reverse proxy, or operator retries after a response timeout. Both requests commit, doubling an opening balance, transfer, or adjustment while producing apparently valid balanced journals.

**Impact:** wallet balances become materially wrong despite every individual journal being balanced. This conflicts with the specification's idempotent monetary-action requirement and is difficult to distinguish from two intentional actions.

**Mitigation:** require a validated idempotency key on all three endpoints; persist it in a unique command/audit record or use it as a stable source identifier; compare the normalized request on replay and return the original result; add sequential and concurrent replay tests for exact-match and conflict cases.

### FIN-002 — Medium — Concurrent settlement retries can surface as internal errors

**Location:** `backend/src/services/finance/os-settlements.ts:277-394`; `backend/src/services/finance/os-settlement-drafts.ts:38-72,83-122`; `backend/src/services/finance/rider-settlements.ts:383-532`; unique keys at `backend/prisma/schema.prisma:573,623,670`.

**Evidence:** several flows perform a read-before-create idempotency check but do not catch a unique-key race or retry a PostgreSQL serialization failure. Expenses explicitly recover from `P2002` (`expenses.ts:80-84`), but OS settlement, settlement draft, amendment audit, and rider settlement do not implement equivalent recovery.

**Failure scenario:** two identical requests with the same key start concurrently. Both observe no prior row; one commits and the other receives a Prisma uniqueness/serialization error that may map to HTTP 500 instead of replaying the committed result.

**Impact:** the database generally prevents duplicate money, but clients see an indeterminate failure and operators may retry under a new key, raising operational duplicate risk.

**Mitigation:** centralize an idempotent transaction helper that maps unique/serialization races to a fresh replay lookup, verifies request equivalence, and returns the first result. Test true concurrent requests against PostgreSQL.

### FIN-003 — Medium — Day close versus posting relies on database serialization without controlled retry/error mapping

**Location:** `backend/src/services/finance/cashbook-policy.ts:4-15`; `backend/src/services/finance/cashbook-close.ts:43-167`; posting transactions including `cashbook-postings.ts:59-72`, `expenses.ts:66-79`, and `rider-settlements.ts:383-532`.

**Evidence:** writers check `closedAt` and then insert financial rows, while close checks the same state and aggregates rows before upserting the close record. Serializable isolation is used in some high-risk flows, but generic cashbook postings and expenses use the client default transaction isolation, and there is no explicit per-hub/day lock shared by close and every writer.

**Failure scenario:** a close and a posting for the same hub/day overlap. Depending on database/isolation behavior, the posting can miss the close or the close summary can miss the posting; at best, a serialization error is exposed as a 500 because no retry/mapping exists.

**Impact:** close summaries can be stale or a valid operator command can fail ambiguously during day-close traffic.

**Mitigation:** acquire a shared database lock/advisory lock keyed by hub and business date for close and every posting command, or use a single conditional day-state claim that writers must validate. Add PostgreSQL concurrency tests for close-versus-expense, close-versus-settlement, and close-versus-adjustment.

### FIN-004 — Medium — Rider outstanding endpoint scales as queries per rider

**Location:** `backend/src/services/finance/rider-settlements.ts:240-291` plus helper calls at `93-165`.

**Evidence:** after loading all active riders, the service executes four asynchronous operations per rider (`settlementWork`, declaration, receipts, and receivable position) inside `Promise.all`. Each helper performs additional database work.

**Failure scenario:** a hub with hundreds of riders triggers hundreds to thousands of simultaneous queries from one request.

**Impact:** connection-pool exhaustion, high database latency, request timeouts, and collateral slowdown of settlement posting.

**Mitigation:** replace per-rider calls with bounded set-based queries/grouping, merge results in memory, paginate the rider list, and add a query-count/performance regression test.

### FIN-005 — Medium — Expense history is unbounded

**Location:** `backend/src/services/finance/expenses.ts:37-44`; route filters at `backend/src/validators/finance/expenses.ts:9`.

**Evidence:** `listExpenses` has no `take`, cursor/page, or required date bound. `businessDate` is optional.

**Failure scenario:** a user requests the endpoint without a date after years of operation, loading every expense and joined category into application memory and a single response.

**Impact:** increasing latency and memory use, oversized responses, and a simple authenticated resource-exhaustion vector.

**Mitigation:** add cursor pagination and a conservative maximum page size; optionally require a bounded date range for exports while preserving a paginated default view.

### FIN-006 — Low — Settlement history traversal issues one query per version and has incomplete cycle termination

**Location:** `backend/src/services/finance/os-settlements.ts:411-438`.

**Evidence:** predecessor and successor chains are traversed through repeated `findUnique` calls. The successor loop records whether a node was seen but breaks only when the repeated node equals `rootId`; a malformed cycle not containing the root would continue indefinitely.

**Impact:** normally low because schema/application rules should form a linear chain, but corrupted or manually repaired data can hang the request; long edit histories cause avoidable database round trips.

**Mitigation:** break on any repeated successor, enforce a maximum chain length, and load the chain with a bounded query/recursive SQL where supported.

### FIN-007 — Low — Dead extracted ledger module creates ownership ambiguity

**Location:** `backend/src/services/finance/ledger-summary.ts:1-13`.

**Evidence:** repository search finds no imports of this module; production continues to use `ledger.service.ts#getLedgerSummary`.

**Impact:** maintainers may update or test the wrong implementation and future refactors can drift.

**Mitigation:** remove the unused module or deliberately migrate the production caller and tests to it.

## Performance, reliability, and scalability observations

- OS settlement and pending-return list endpoints have explicit caps (200 and 500 respectively), which bounds response growth.
- Bulk OS return is capped at 50 parcels and runs atomically with a 30-second transaction timeout.
- The OS settlement post path recomputes live eligibility and financial maxima inside the transaction, reducing stale-preview risk.
- List-level query limits should be made consistent; expenses and rider outstanding are the current outliers.
- PostgreSQL concurrency behavior remains a deployment-critical verification area because local SQLite tests cannot prove Serializable retry behavior, row/advisory locking, or pool pressure.

## Positive controls verified

- No remaining source or test imports reference the deleted `finance.service.ts`.
- Controller methods call focused Finance owners directly.
- Server-side authorization reloads the actor from the database, verifies active status and role equality, and applies hub scope.
- Mutation routes retain role middleware; services add checks for high-risk amendment/reversal/superadmin operations.
- Expense, rider settlement, OS settlement, return, reversal, and amendment writes keep related journal/domain records within transactions.
- Database uniqueness exists for journal `(sourceType, sourceId)`, expense idempotency, rider settlement idempotency, OS settlement idempotency, and settlement edit audit idempotency.
- Expense concurrent-key recovery rechecks the original normalized request after a unique conflict.
- OS settlement posting recomputes live batch state/totals and checks active settlement links in the transaction.
- Settlement draft updates and posted amendments use optimistic version checks.
- Reversal/amendment journal lines invert the original entry and retain actor/reason metadata.
- Amounts are integer fields; wallet and editable-component validation is performed at route and service layers.
- Cashbook closed-day checks are shared by the extracted Finance services and migrated external callers.
- Static checks passed: TypeScript typecheck, ESLint, and `git diff --check`.

## Limitations and follow-up

- The working tree changed concurrently during a multi-agent review; findings describe the snapshot inspected around the report timestamp.
- PostgreSQL integration/concurrency tests were not run; local SQLite behavior is insufficient evidence for production race safety.
- No load test or database query-count instrumentation was used.
- Frontend and mobile clients were outside this focused Finance backend audit except for API-contract implications.
- This audit did not re-audit global JWT, CORS, rate limiting, backup/restore, or deployment infrastructure beyond their effect on scoped Finance flows.

Before deployment: fix FIN-001, obtain one uncontended green full backend run, and execute the PostgreSQL Finance/integration suite. FIN-002 and FIN-003 should be resolved before exposing these commands to unreliable networks or concurrent operators; FIN-004 and FIN-005 should be addressed before material production volume.
