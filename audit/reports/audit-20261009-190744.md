# Finance transactions implementation audit

Timestamp: 2026-10-09 19:07:44 Asia/Yangon. Repository HEAD `f68b41a`; reviewed the uncommitted transactions implementation while other agents were editing it.

## Scope and exclusions

Inspected `PROJECT_SPEC.md`, new Finance transactions service, validator, route, controller, React panel, related rider-outstanding service, Prisma journal schema, and focused tests. This was a read-only code review. No production access, external requests, migrations, installs, or load tests were performed. Findings refer to the snapshot at the timestamp above and should be rechecked after concurrent edits finish.

## Executive summary

The API scopes journal rows by hub and restricts permitted roles. It separates noncash OS credits and pending returns from wallet movement and caps CSV exports at 10,000 rows. However, several accounting usability and scaling gaps remain. No confirmed privilege escalation or direct ledger corruption was found in this slice.

## Findings

### F1 — High — Superadmin cannot see rider outstanding

`frontend/src/features/finance/transactions-panel.tsx` lines 49 and 106 explicitly disable and hide the rider-outstanding section for Superadmin. The backend supports that role. A Superadmin reviewing wallet receipts cannot see the agreed outstanding warning, and a multi-hub view would need the selected `hubId` sent to the endpoint. Show the section for Superadmin and pass the selected hub ID.

### F2 — Medium — Statement lacks a running balance and posting chronology

`backend/src/services/finance/wallet-transactions.ts` lines 82–85 sort by business date before posting time; `frontend/src/features/finance/transactions-panel.tsx` lines 100–103 show no balance after each transaction. A late entry backdated to an earlier business date appears away from the actual posting sequence, and the user cannot reconcile a banking-style transaction list with opening/closing balances row by row. Decide whether this is a business-date statement or posting-time audit, label both timestamps, and compute a deterministic running balance for the chosen ordering.

### F3 — Medium — Counterparty and correction attribution is incomplete

`backend/src/services/finance/wallet-transactions.ts` lines 99–125 enrich only pickup advances, rider settlements, OS account payments, and expenses. Wallet-affecting OS settlements, payment voids, transfers, adjustments, opening balances, and ledger reversals fall back to raw descriptions/source IDs. A correction can look like an unexplained money movement, and reversals are not visibly linked to their original item. Resolve those source records and expose meaningful counterparty, recorder, and original/correcting entry references.

### F4 — Medium — Rider/shop filter can produce an unbounded source predicate

`backend/src/services/finance/wallet-transactions.ts` lines 61–75 load every matching settlement/payment/batch ID before the date-bounded journal query and construct an OR predicate per ID, including two predicates per batch. For a long-lived shop this can cause a large DB response and expensive query even for a one-day report. Query bounded IDs by hub/date where possible or use a direct relational source filter/indexed lookup. The journal query's hub scope still prevents cross-hub rows.

### F5 — Low — Opening balance aggregation grows with full ledger history

`backend/src/services/finance/wallet-transactions.ts` lines 77–79 aggregate all wallet lines before the requested start date on every page and every filter change. On a mature ledger, this repeats a full-history calculation. Consider a verified daily closing-balance checkpoint while keeping journal replay as a reconciliation path.

## Positive controls

The new endpoint checks active role and hub scope, validates and limits dates/page size, uses integer wallet movements, and CSV output escapes spreadsheet formulas. Wallet summaries derive from journal entries rather than operational return credits. Export count is limited to 10,000 rows.

## Unverified areas and follow-up

No tests or build were run by this auditor because the implementation was changing concurrently. Recheck F1–F5 on the final diff and run targeted backend/frontend tests plus a database-backed statement check covering a split payment, backdated posting, reversal, and multi-hub Superadmin selection.
