# Parcel location suggestions audit

**Timestamp:** 2026-10-09 13:40:04 Asia/Yangon
**Repository:** `lotaya-pos`, `main` at `594ebaf`, with uncommitted location-suggestion changes.

## Scope and limitations

Reviewed `PROJECT_SPEC.md`, `AGENTS.md`, the new suggestion route, validator, controller, service, auth/CSRF/error middleware, relevant Prisma models/indexes, frontend lookup trigger, and focused tests. This review covers the new parcel location suggestion flow. No production service or customer data was accessed. Database-backed integration and load behavior were not verified.

## Executive summary

The endpoint enforces an authenticated parcel-entry role and constrains history to the selected batch's shop and hub. The main risks are automatic classification of a recycled/shared phone as safe and repeated broad historical reads during phone entry. **Overall posture: moderate risk until the safe-match rule is tightened; no confirmed cross-shop data leak in the reviewed path.**

## Findings

### LOC-01 — Medium — Different customer name can still be `SAFE`

**Location:** `backend/src/services/parcel-location-suggestions.service.ts:38-58`.

**Evidence:** The classifier finds history by phone, deduplicates address/township, then returns `SAFE` when there is one location and no address/township conflict. It never compares a nonblank incoming `customerName` with the historical candidate's name. The PDF flow can bulk-apply `SAFE` rows. A recycled number or shared family phone can therefore supply another customer's location without review.

**Impact:** Wrong delivery address/location may be attached to a parcel, with disclosure of a previous customer's address to an operator as part of the suggestion. This is a correctness and privacy risk, though the operator is already authorized for the shop/hub.

**Mitigation:** When both names are populated and differ after normalization, classify as requiring review rather than `SAFE`. Keep phone suggestions visible for explicit selection. Add a regression case for one phone, one historical location, and a different incoming name.

## Performance, reliability, and scalability

### LOC-02 — Medium — Every lookup loads up to 20,000 historical parcels

**Location:** `backend/src/services/parcel-location-suggestions.service.ts:73-88`; `frontend/src/features/batches/detail/use-location-suggestion.ts:10-20`.

**Evidence:** Each request selects the latest 20,000 nonvoid parcels plus location relations for the entire shop/hub, then normalizes and maps them in application memory. Manual phone entry triggers a request 450 ms after changes to phone, name, address, or township. The route has a 500-row request cap and global 512 KB body cap, but no route-specific request throttle. PostgreSQL `Batch` and `Parcel` models do not provide a direct normalized-phone lookup index.

**Impact:** Large shops can incur repeated database reads, serialization, and heap work even for a single phone lookup. Concurrent operators or repeated authenticated requests could increase latency for parcel creation and other API calls. The latest-20,000 cap can also omit older valid matches without telling the user.

**Mitigation:** Store/search normalized phone (and bounded name/address fallback) with scoped indexes, query only requested keys, and cap/pace lookup requests server-side. Retain a result cap. Until then, instrument query duration and call frequency before production rollout.

## Positive controls verified

- Route requires authentication and one of Superadmin, Operations Manager, or Dispatcher; the service rechecks current active role.
- History query is constrained to the selected batch's `shopId` and `hubId`, and non-Superadmin batch access is hub-scoped.
- Finalized batches and voided historical parcels are excluded; the endpoint is read-only.
- Request rows are capped at 500; field lengths and the app's 512 KB JSON cap bound request size.
- Candidate responses omit historical phone numbers. The API uses Prisma structured queries, with no raw SQL in this path.
- Focused classifier suite passed: 5 tests.
