# Lotaya ERP and Rider App Auditor Review

**Audit date:** 2026-08-11 00:20:23 Asia/Yangon  
**Scope:** Full `backend/`, `frontend/`, and `mobile/` implementation, with focused review of the latest linked-parcel accounting change.  
**Constraint:** No production code was modified. This workspace is not a Git checkout, so the review used current source, schema, tests, and generated artifacts rather than a commit diff.

## Executive Verdict

**FAIL — do not deploy or process real COD money.** The latest linked-parcel implementation introduces a credible double-posting path and does not yet reconcile linked-group fees and commissions with the normal collection and rider-settlement flows. The project also retains previously identified production risks around secret defaults, PostgreSQL migrations, global cashbook scope, retry safety, and unbounded ledger reads.

## Prioritized Findings

### AUD-20260811-001 — Critical — Linked delivery can be posted twice

**Evidence:** When the final parcel in a group becomes `DELIVERED`, `backend/src/services/parcel.service.ts:126-141` automatically creates `LINKED_DELIVERY_COLLECTION` and `LINKED_RIDER_COMMISSION` journal entries. The normal `POST /api/v1/finance/ledger/delivery-collections` path in `backend/src/services/ledger.service.ts:136-155` remains available for every delivered parcel and only checks the per-parcel `DELIVERY_COLLECTION` key; it does not reject linked parcels or recognize the group entry.

**Impact:** An operator can post the normal collection for each linked parcel after the automatic group posting, duplicating wallet/COD/revenue activity and corrupting OS and rider balances.

**Mitigation:** Choose one authoritative linked-group posting workflow. Make collection explicit and idempotent at group scope, or make the automatic event create a pending business event that the collection endpoint consumes. Add a database-backed test that attempts both paths and proves only one balanced posting set exists.

### AUD-20260811-002 — Critical — Linked journal accounts and wallet do not match actual cash flow

**Evidence:** The automatic group entry hard-codes `WALLET_CASH` and credits `CUSTOMER_COD_RECEIVABLE` at `backend/src/services/parcel.service.ts:136`. The normal collection builder uses the selected Cash/KBZ Pay/Wave Pay wallet and clears `OS_ADVANCE_RECEIVABLE`/`OS_COD_PAYABLE` at `backend/src/services/ledger.service.ts:86-99`.

**Impact:** KBZ Pay or Wave Pay collections are recorded as cash, and linked deliveries follow a different receivable model from ordinary parcels. The ledger may remain arithmetically balanced while being economically wrong, so OS settlement and cashbook reconciliation can be false.

**Mitigation:** Persist the actual collection wallet, collected COD, and collected delivery fee as a linked-group event; use the same account mapping as the canonical collection workflow; require explicit reconciliation of advance, COD payable, delivery-fee revenue, and wallet movement before settlement.

### AUD-20260811-003 — High — Linked fee and commission are not propagated to settlement

**Evidence:** `linkParcels` stores adjusted totals only on `ParcelLinkGroup` at `backend/src/services/operations.service.ts:94-99`. Individual `Parcel.deliveryFee` values remain unchanged. `DeliveryWay` commission is created per parcel from the original fee at `backend/src/services/parcel.service.ts:126-127`, while a second group commission journal uses the adjusted fee at lines 131-141. Rider settlement sums parcel fees and `DeliveryWay` commission in `backend/src/services/finance.service.ts:118-129`.

**Impact:** The adjusted linked fee is not reflected in the rider settlement formula, while the separate group commission journal can double-count commission expense/payable. Expected rider remittance and gross profit can differ from posted journals.

**Mitigation:** Define one group-level financial representation and make settlement consume that representation. Either persist allocated adjusted fees/commission per way or settle from the group event, never both. Add end-to-end tests for two and three linked parcels, including rider settlement and cashbook close.

### AUD-20260811-004 — High — Linked-group concurrency is not fully idempotent

**Evidence:** The final-delivery transaction checks for an existing group journal before creating it at `backend/src/services/parcel.service.ts:134-142`, but concurrent final status updates can both observe no entry. The unique constraint may then surface as an unhandled database error rather than returning the existing result. The group has no explicit event key for wallet/collection inputs.

**Impact:** Legitimate concurrent rider updates can produce a 500 response, retries, or ambiguous accounting outcomes.

**Mitigation:** Use a stable group event key with an atomic insert/upsert and handle unique conflicts by returning the existing event. Add concurrent integration tests under SQLite and PostgreSQL transaction behavior.

### AUD-20260811-005 — High — Link endpoint has no request validation or size bound

**Evidence:** `POST /api/v1/operations/parcels/link` in `backend/src/routes/v1/operations.routes.ts:12` has no validator. `linkParcels` immediately reads `input.parcelIds` and performs an unbounded `IN` query at `backend/src/services/operations.service.ts:83-99`.

**Impact:** Malformed requests can become internal errors, and oversized arrays can consume memory/database resources or exceed database parameter limits.

**Mitigation:** Validate an object with a bounded array, unique nonempty IDs, and a maximum group size. Reject unknown fields and return stable 4xx errors. Add API contract tests for missing, duplicate, oversized, and cross-hub IDs.

### AUD-20260811-006 — High — Address matching is raw-string equality, not normalized equality

**Evidence:** `linkParcels` compares `parcel.address !== first.address` at `backend/src/services/operations.service.ts:89-92`, while `PROJECT_SPEC.md:263` requires normalized exact-address matching.

**Impact:** Equivalent addresses with whitespace, casing, or formatting differences cannot be linked; unsafe normalization decisions made later could also link distinct destinations. This creates operational and collection errors.

**Mitigation:** Define and test a deterministic address-normalization policy, retain the original address for display/audit, and compare a normalized/hash key. Require explicit operator confirmation for ambiguous matches.

### AUD-20260811-007 — Critical — Production JWT and database defaults remain unsafe

**Evidence:** `backend/src/config/env.ts:3` defaults `JWT_SECRET` to a development value, defaults `DATABASE_PROVIDER` to SQLite, and does not reject unknown providers. Public registration remains exposed at `backend/src/routes/v1/auth.routes.ts:1` despite the production invite/admin requirement in `PROJECT_SPEC.md`.

**Impact:** A misconfigured production instance can permit forged tokens or run against an unintended local database; open registration expands the attack surface.

**Mitigation:** Fail closed in production for missing/weak secrets, unknown providers, and invalid URLs. Disable public registration by default and require an invite/admin flow. Add startup and deployment-policy tests.

### AUD-20260811-008 — Critical — PostgreSQL migration deployment is not proven and uses SQLite DDL

**Evidence:** `backend/prisma/schema.postgresql.prisma` changes the provider, but `backend/prisma/migrations/20260810120000_cashbook_controls/migration.sql` contains SQLite-specific DDL such as `DATETIME`; `db:deploy:postgresql` uses the same migration directory. Prisma schema validation succeeds, but no PostgreSQL migration deployment was run.

**Impact:** A clean production PostgreSQL installation may fail or diverge from the tested schema.

**Mitigation:** Create provider-native migration histories or a verified provider-compatible migration strategy. Run migration deploy, seed, auth, ledger, and rollback/restore smoke tests against a disposable PostgreSQL instance in CI.

### AUD-20260811-009 — Critical — Cashbook and financial scope remains global across hubs

**Evidence:** `CashbookDay.businessDate` is globally unique in `backend/prisma/schema.prisma:195-209`; close and variance queries in `backend/src/services/finance.service.ts:133-156` aggregate all settlements and journal lines for a date without hub ownership.

**Impact:** Finance users in one hub can close or reconcile a date containing another hub’s money. Wallet balances, variance approvals, and reports can mix independent operations.

**Mitigation:** Add hub/organization ownership to cashbook, journal, wallet, settlement, and close-summary records; enforce it in every query and command. Test cross-hub read, post, approve, close, and reopen denial.

### AUD-20260811-010 — High — Money commands are not uniformly retry-safe

**Evidence:** `backend/src/services/finance.service.ts:64-115` generates random source IDs for opening balances, transfers, and adjustments. The API has no idempotency-key contract. Linked group operations also have no client event key.

**Impact:** Timeouts and operator/mobile retries can create duplicate financial movements.

**Mitigation:** Require a stable idempotency key for every money/status command, persist it with the actor/scope, and return the original result for replay. Make duplicate handling explicit in API tests.

### AUD-20260811-011 — High — Ledger reporting is unbounded and N+1 scoped

**Evidence:** `backend/src/services/ledger.service.ts:221-235` loads all matching journal entries without pagination or a bounded date span, then performs an ownership query per entry through `entryInScope`.

**Impact:** Ledger growth can cause high memory use, slow responses, connection pressure, and denial-of-service risk.

**Mitigation:** Add bounded pagination/date windows, indexes, relational scope predicates, and background/streamed exports. Add performance tests with realistic journal volume.

### AUD-20260811-012 — High — Cookie authentication lacks production cookie and CSRF hardening

**Evidence:** `backend/src/controllers/auth.controller.ts:2` sets an `HttpOnly` cookie without `Secure`; mutating routes accept cookie authentication and there is no CSRF token or trusted-origin enforcement.

**Impact:** Cookies are not hardened for production transport and state-changing browser requests lack defense-in-depth CSRF protection.

**Mitigation:** Use `Secure`, an explicit production `SameSite` policy, preferably a `__Host-` cookie, and CSRF/origin checks for cookie-authenticated writes. Keep bearer and cookie client contracts explicit.

### AUD-20260811-013 — Medium — Mobile linked updates remain online-only

**Evidence:** `mobile/src/lib/api.ts:1-5` has no timeout, retry queue, or mutation idempotency key. The parcel screen posts directly and navigates back after success.

**Impact:** Weak connectivity can cause ambiguous delivery state, duplicate taps, stale linked-group data, and unrecoverable failed submissions.

**Mitigation:** Add request timeout and explicit mutation state, retry only with idempotency, invalidate/refetch assignment data, and define an offline queue policy with device tests.

### AUD-20260811-014 — Medium — Duplicate Expo Router trees and missing operational hardening remain

**Evidence:** Both `mobile/app/(tabs)/` and the literal `mobile/app/'(tabs)'/` tree exist. No application ESLint configuration was found; rate limiting, metrics/error monitoring, backup/restore drills, and real-time alert transport remain absent or unverified.

**Impact:** Route drift, undetected regressions, weak incident response, and uncertain disaster recovery.

**Mitigation:** Remove the duplicate tree, add CI lint/security checks, wire structured redacted logging/metrics, implement rate limits, and verify encrypted backups/restores and alert delivery.

## Release Recommendation

Resolve **AUD-20260811-001 through AUD-20260811-004** before accepting linked parcels in production. Resolve **AUD-20260811-007 through AUD-20260811-012** before deploying the financial system. Then run the full Test Reviewer and Verifier gates against a disposable PostgreSQL database and a concurrency-capable test environment.
